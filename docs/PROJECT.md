# Multi-Repo Coding Agent Harness

**项目描述**

Multi-Repo Coding Agent Harness — 多仓库 Coding Agent 运行与验证框架

基于 Go 设计实现多仓库 Coding Agent Harness，以公共 RPC SDK 不兼容升级的跨仓库迁移为应用场景，支持 Agent 自主完成代码迁移与迭代修复，通过批量执行管理和独立质量门禁，实现迁移任务的可靠执行与可审查交付。

**项目背景**

内部 RPC 库 `rpcx` 发布了不兼容的 v2,并规定 v1 在 90 天后停止维护。数十个业务仓库依赖该库,平台团队需要在期限内推动所有下游完成迁移。为避免各业务团队重复研究 SDK 变更，并统一迁移要求，平台团队负责集中推动此次升级。

这次升级不止是改接口名称。v2 同时改变了运行时语义,例如移除了 v1 隐式的 30 秒默认超时:调用方不显式配置,行为就会悄悄改变,而现有测试通常不会覆盖这一点。各仓库对 `rpcx` 的封装方式也各不相同,同一项接口变更在一个仓库里可能只需改调用点,在另一个仓库里却牵涉整条调用链、错误处理乃至测试代码。查找替换和 AST 改写只能处理确定性修改,通用 Coding Agent 虽能辅助完成单仓库代码适配，但直接将其用于大规模迁移，仍需要解决跨仓库执行管理、统一验收和结果审计的问题。更关键的是,代码能编译、测试能通过,并不意味着迁移后的行为符合预期。

此次迁移的补丁主要由平台团队生成，但最终仍需由各业务仓库的维护者审核和接收。平台团队熟悉 SDK 的变化，却未必了解各仓库的业务逻辑。对于批量生成的补丁，业务维护者不仅需要检查代码修改，还需要判断其中是否存在未经充分验证的行为变化，使得人工审核成为大规模迁移中不可忽视的成本。

此外，各仓库的依赖、构建和测试环境不同，迁移过程可能经历多轮代码修改与验证，执行时间和结果也难以预先确定。数十个仓库需要在明确的升级期限内完成迁移，而各仓库的进展并不一致，部分迁移还可能因构建失败、测试错误或执行异常而中断。批量迁移因此不仅面临代码适配问题，还面临执行资源受限、任务进度不确定以及部分失败带来的管理复杂性。

**项目目标**

构建面向公共 SDK 不兼容升级的多仓库 Coding Agent Harness，驱动各仓库独立完成代码适配与验证，并统一管理批量迁移任务的执行资源、运行状态和迁移结果。

系统不仅要产出能通过构建和测试的补丁,还要依据迁移约束和实际验证证据,区分可进入常规审核的结果与需要重点人工确认的修改,并提供可追溯的变更与验证报告,让缺少对方领域知识的审核人也能判断依据是否充分。批量执行中,个别仓库的失败或中断不应影响已完成的成果,未完成的任务可以单独重试。

项目以候选补丁和审核材料为交付边界,不负责自动合并代码或协调业务服务上线，重点解决异构仓库中的语义迁移、批量 Agent 执行可靠性和迁移结果可信性问题。

**核心能力要求**

1. **迁移规范驱动的 Coding Agent**：根据版本化迁移规范，自主探索仓库、理解代码上下文，完成跨函数、跨文件的接口与语义适配，并通过工具执行与测试反馈持续修复。
2. **基于验证证据的质量门禁**：依据迁移规范中的验收条件和实际验证证据，对候选补丁进行独立判定；对验证不充分或无法确定的语义修改标记 `NeedsAttention`，并生成包含修改依据、验证结果及未解决问题的审核材料。
3. **可靠的多仓库 Agent Runtime**：将批量迁移组织为相互独立的仓库任务，支持隔离执行、有界并发、资源预算、状态持久化及失败重试，确保单个任务的异常不会破坏其他任务及已完成成果。
4. **评测与效果度量**：构建与运行时质量门禁隔离的分层评测体系，通过构造任务检验机制，通过半真实仓库评估迁移效果与结果可信性，并可选使用真实开源仓库检验工程适用性；统计有效自动成功率、错误放行率、需人工确认率、执行成本及失败原因分布。

> 注: 错误放行率：被运行时质量门禁判定为 `ReadyForReview` 的结果中，未通过独立离线评测的比例

**设计原则与边界**

1. **独立执行，统一管理**：各仓库的迁移任务相互隔离，由 Harness 统一管理执行过程和资源。
2. **生成与验证分离**：Agent 负责代码修改，独立验证机制负责结果判定，Agent 不得改变验收依据。
3. **可信性优先**：不将验证证据不足的结果认定为成功，执行过程和结果应可追溯、可复验。
4. **故障隔离与可恢复**：单个 Target 的失败不影响其他 Target，历史 Run 的记录与成果应得到保留，并支持重新执行。
5. **通用能力与场景逻辑解耦**：Harness 的核心运行机制不依赖特定 SDK，迁移作为具体应用场景。

**范围边界**：以 Go 仓库中的 `rpcx` v1→v2 迁移为验证场景，采用单机执行；不做自动 PR、合并部署、分布式调度、IDE 集成及复杂外部测试环境编排。

**实施路线**：按 Harness 能力划分 M0—M5，阶段范围、可测验收与最低交付见[里程碑](MILESTONES.md)。首版以 T1/T2 和默认超时变化这一代表性 T3 场景验证系统；下文其他 SDK 变化作为扩展方向。评测贯穿开发，最后按冻结协议完成正式验收。

**当前交付重心（2026-10-22）**：已有可复验的工程开发版；批量预算与隔离、中断审计、受控单代重跑和资源清理已在声明范围交付。四任务有限真实评测与助手复核已完成，原有效自动成功 1/4；其后 GHCLI 误拒分类修正另作开发回归，不改变原实验。当前以[项目首页](../README.md)、[离线演示](DEMO.md)和[交付说明](DELIVERY.md)统一入口，后续按具体缺口优化验证支持；Translation 扩展暂缓。原人员口径、严格未见留出及总体验收条件仍保留，不将有限样本结果当作普遍效果或阶段全部通过。

**核心术语**

| 术语       | 含义                                         | 关系               |
| ---------- | -------------------------------------------- | ------------------ |
| `Campaign` | 一次跨仓库迁移批次                           | 包含多个 Target    |
| `Target`   | 一个仓库在指定 Campaign 中需要完成的迁移目标 | 包含一个或多个 Run |
| `Run`      | 针对某个 Target 的一次独立执行尝试           | 属于一个 Target    |

**技术选型与运行约束**

- **模型服务**：首版使用 DeepSeek API，模型接口保持可替换。
- **资源预算**：支持单次任务和批次级的 Token、执行步数限制，具体阈值根据实际运行数据确定。
- **迁移规范**：由平台团队维护并进行版本管理，Agent 仅可读取；每次执行需记录所使用的规范版本，以保证结果可追溯。

**v1 → v2 的变更清单(难度递进)**

| 层级            | 变更                                                         | 为什么难                                                     |
| --------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **T1 机械**     | 导入路径变为 `rpcx/v2`;`NewClient` 改名为 `Dial`             | 只需精确替换                                                 |
| **T2 签名**     | `Call(method, req)` 变为 `Call(ctx, method, req)`            | 调用点要找到可用的 ctx,没有就得往上层传,可能连锁改多个函数签名 |
| **T3 语义**     | 隐式 30s 默认超时被移除,必须显式设置;重试默认关闭            | 要保持行为等价:在没有显式配置的调用点补上等效的超时选项,而不是随手写一个值 |
| **T4 错误处理** | 字符串错误变为类型化错误(`errors.As(&rpcx.StatusError{})`)   | 要理解调用方的错误判断意图,改写逻辑                          |
| **T5 结构**     | `Client` 拆成 `Caller` 和 `Streamer`;配置从结构体变为函数选项 | 测试里的 mock 实现了旧接口,需要同步改;有的仓库自己封装了一层 |
