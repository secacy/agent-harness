# ADR-007：任务输入与宿主验证 Profile 分开管理

- 状态：Accepted（2026-10-19，首版仅支持已有两个 rpcx Profile）。
- 相关模块：internal/task、scenarios/rpcx/runner；后续 Campaign 接入。
- 依据：[M3.2 取舍与实施记录](../worklog/2026-10-19-m3-batch-runtime.md#11-m32显式-target宿主场景配置与生成前基线检查)。

## 背景与问题

调度需要明确每个仓库任务的输入身份，现有 Runner 和验证器则依赖 demo-orders 的布局、测试适配与业务探针。若只把目录和命令变成用户参数，旧探针可能被用于不适用的业务代码；只增加 Target ID 又无法表达实际消费的输入。

## 方案与取舍

采用通用 Target 输入描述加宿主维护的验证 Profile。相比将验证要求全部交给任务配置，这增加了每个仓库的可信接入工作；相比通用插件/规则引擎，又能直接复用现有代码，不提前抽象未知业务语义。

首版以源码内的 profiles.json 注册既有 T1/T2、T3 两种配置，保存各自的基线、SDK、规范摘要、布局、默认构建配置、必需测试身份和验证实现标识。候选和普通 Target 不得覆盖这些规则。任意业务仓库或语法形态的支持仍需新的验证证据，不因指定一个 Profile ID 就自动成立。

## 决策

Target 描述固定仓库、只读依赖及规范快照，并引用 Profile 与构建配置；通用任务包不导入 rpcx。宿主负责认证受支持的 Profile、输入摘要和输出边界，按配置组装 Agent 工具、基线检查和独立门禁。Agent 只看到必要工作副本、SDK 与规范，不看到宿主 Profile、用例预期或 oracle。

生成前实际执行基线构建及测试，核对必需测试与包终态。未证明基线可用时不调用模型、不发布候选质量判定，保留任务执行失败及诊断。该检查不替代提交后的独立质量验证；门禁仍认证自己的实际基线和候选。

Profile 材料与实际输入写入 Run 并绑定摘要。已使用的 Profile 内容变更发布新 ID，保留旧材料；不能原地重签同一个 ID。源输入物理位置可变化，内容身份及验证范围不能因此改变。首版不允许自由提交一个新的输入摘要来让旧业务探针接受任意仓库。

## 验证与限制

Target/配置拒绝、输入缺失或漂移、基线失败/缺事件/跳过/取消和零模型准入由机制对照验证；正常基线在可信本地及真实 Docker 下执行，确认构建、十个原测试、材料/日志摘要与执行顺序。完整回归结果见上述 worklog。

M3.2 不提供任意仓库验证配置或新的 L2 仓库；T1/T2 Runner 的输入范围因此明确收窄为受支持的快照，直接 Evaluate 机制接口保留。真实业务仓库的可信检查接入与独立评测仍归后续单元。

本决策固定的是输入身份与验证规则的所有权，不永久固定 JSON 字段、模块目录名或静态注册方式。

## 重新评估条件

当 L2 证据表明每仓库接入出现稳定重复结构时，比较可复用的测试变换、可信探针装配或经认证的外部 Profile 文件；仍保留规则由宿主选择、证据绑定实际输入和未知不放行的约束。不得用删除摘要认证或放宽必需检查解决接入成本。
