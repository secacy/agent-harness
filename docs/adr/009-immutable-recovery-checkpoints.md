# ADR-009：恢复准备采用不可变检查点与单一提交标记

- 状态：Accepted（2026-10-20；停止后的控制状态准备，不包含任务激活）。
- 日期：2026-10-20。
- 相关模块：internal/recovery、internal/audit、internal/budget、internal/campaign。
- 依据：[M4.2b 工作记录](../worklog/2026-10-20-m4-recovery.md#11-m42b恢复控制检查点)。

## 背景与问题

恢复需要保留旧 Run、原始控制记录和全部请求占用。若原地逐个推进 Campaign、预算、Target 和汇总，恢复再次中断时会留下多种新旧组合；文件 rename 只提供单文件发布边界，不能把多文件写入变成一个事务。

## 方案与取舍

原地推进能复用现有路径，但需要为每个合法中断前缀定义重入与审计。数据库可以管理控制事务，但不能同时提交现有文件形式的 Run/报告，还会引入新的存储依赖。关联新 Campaign 则需要额外解决继承预算的唯一后继和防分叉。

当前不需要在恢复准备中执行 Agent，选择先保存不可变检查点，再用单一 head 提交。接受原根目录仍表示旧尝试、准备状态需要单独展示的代价，以减少发布窗口和历史改写。

## 决策

协作写者始终遵守 ADR-008。停止并检查来源后，将控制文件原文字节、审计来源摘要、确定性生成的预算与尝试历史写入 `recoveries/checkpoint-<id>.json`；文件及目录同步后，再发布绑定其路径和摘要的 `recoveries/head.json`。原控制文件、账本及 Run 不改写。

相同 ID 重入只核对和补齐发布，不能重复转换；冲突 ID 或不自洽材料拒绝。检查点存在且没有 head 是 Pending，head 完整绑定才是 Prepared。写入结果不确定时不声称已提交，重入读取磁盘并重新校验。Prepared 只表示控制准备完成，不表示任务重跑、付费准入或迁移成功。

检查点中的账目继承原两级限额和逐请求归属，reserved 转 unknown 保持总占用及调用次数；不清空未知成本，不从供应商可能仍在执行的请求推断退款。多 Run 历史和预算 v2 目前作为待激活数据，不能直接打开成为运行账本。

## 验证与限制

已通过预算幂等/损坏反例、发布前后失败重入，以及目录/检查点/head 三个真实 SIGKILL 窗口。rpcx 的模型在途、报告已写但 Run 未终态、Run 已终态未索引分别验证保留占用、Interrupted 和 Adopted。测试使用受控模型与本地离线执行，没有供应商请求或 Agent 重跑。

首版每个原 Campaign 最多一份检查点，不支持分叉、连续多代激活或通用资源清理；资源静止仍需宿主证据。摘要只能证明当前材料自洽，不能防止整套材料及摘要被一致改写。掉电与存储损坏不由 SIGKILL 测试证明。

## 重新评估条件

任务激活或多代恢复需要修改原控制路径时，必须先明确已提交检查点、运行账本、尝试收据和新代次的所有权，发布新格式；不能把 Prepared 静默解释为正在执行。若控制事务前缀仍难以有限枚举，再比较事务数据库，不无限叠加标记。
