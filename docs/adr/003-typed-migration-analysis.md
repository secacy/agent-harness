# ADR-003：迁移分析使用类型身份，并与行为证据组合

- 状态：Accepted
- 日期：2026-10-18
- 相关模块：rpcx M2.3 迁移完整性分析，正式门禁尚未实现
- 依据：[方案对照记录](../experiments/2026-10-18-m2-analysis-study-01.md)、[工作推进](../worklog/2026-10-18-m2-evidence-gate.md#14-m23分析选型的最小对照)

## 背景与问题

迁移检查需要识别真实 SDK 调用、上下文派生函数及超时常量，不能按 `Call`、`ctx` 等名称作结论。项目同时要求有范围的自动放行、明确违规拒绝、证据不足需关注。常量表达式、导入别名和跨文件字段属于合理的基本写法；不宜仅因这些写法增加人工确认。

## 方案与取舍

有限 AST 原型已经可以识别直接调用、导入别名、同名非 SDK 方法与一类局部遮蔽。要覆盖常量表达式、命名常量、类型别名及跨文件字段，还需实现额外的绑定、常量求值和类型展开。并非 AST 无法做到这些，而是项目会承担这部分语言规则的维护责任。

`go/types` 原型利用方法对象、选择表达式与常量值处理了上述样例；代价是必须获取可靠的包、构建配置及依赖导出信息。选型时验证了离线本地加载，后续固定环境的 Docker 加载与有限规则见 [ADR-004](004-analysis-execution-boundary.md)；其他工具链与更多仓库环境仍待验证。收益是把语言层的身份与常量判断交给 Go 类型系统，把自己的代码集中在迁移规则及证据范围。

类型信息也无法自行证明 helper 的 context 传播、接口动态分派或任意控制流。立即引入 SSA 和跨函数摘要可能扩大支持范围，但目前没有必须为此承担复杂度的验收要求。因此暂不引入；遇到超出边界的形态保留缺口。

## 最终决策

使用 AST 加 `go/types` 信息实现首版有边界的迁移分析。SDK 身份依据包和对象，常量依据类型检查结果；生产代码不得降级为名称匹配后放行。没有可靠加载结果时不给分析通过结论，并依据原因区分候选构建问题、未支持范围和执行错误。

采用结构/覆盖证据与独立行为证据组合。调用清单或识别到 30 秒常量不独自支持质量通过；探针通过不代表所有相关位置已覆盖。动态调用、未覆盖配置和未证明的传播关系必须显式进入缺口。已知违规仍优先拒绝，并保留其他未知，沿用 ADR-002。

本决策不锁定包加载库，也不承诺完整 Go 语义分析。`go list` 加导出数据是已验证的本地原型路径；若生产接入需要 `go/packages` 等其他加载方式，按实际构建与隔离要求另作比较。

## 验证与限制

开发样例中，遗漏分支通过当前行为探针，但新增 SDK 位置可被清单发现；吞错候选拥有与正确候选相同数量的 SDK 调用和 30 秒常量，但行为检查失败。它们支持组合分工，并未证明一套完整组合门禁已经可用。

helper 正例的行为检查通过，类型查询也能识别其常量，却仍缺传播关系证明。原型不输出 ReadyForReview，不统计实际错误放行率。独立副本能排除候选测试入口的干预，不能排除生产代码干预，也不证明原断言保留。M2.3 的测试完整性方案及完整 L1 验收仍需完成。

## 重新评估条件

如果实际仓库大量使用合理的间接调用并因此需要人工关注，先用这些样例比较扩大支持范围与引入数据流分析的收益。如果类型加载在目标执行环境中不可靠或成本不可接受，重评加载方式与支持范围；不能隐藏加载失败或降低证据要求。
