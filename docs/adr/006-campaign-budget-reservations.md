# ADR-006：批次模型调用采用前置预留与保守结算

- 状态：Proposed。
- 日期：2026-10-19。
- 相关模块：拟议 internal/budget、Campaign 模型组装、模型适配器。
- 依据：[M3 具体设计第 4 节](../worklog/2026-10-19-m3-batch-runtime.md#4-批次预算调用前预留调用后结算)。

## 背景与问题

现有单 Run 调用次数限制和调用后 usage 记录不能阻止多个 Run 同时超过批次额度。超时、断连与缺少 usage 也不代表服务没有消费。项目要求付费并发建立在调用前预留之上，重试与中断不能使额度凭空恢复。

## 方案与取舍

响应后检查会发现得太晚；按字符或经验分词预估只能提供估计，缺少协议开销及服务端行为的上界证明。按整个 Run 最坏消耗预留容易锁住大量闲置额度。拟采用逐调用预留，降低 Run 级占用，同时保留保守的单次上界。

首版按经核实的模型 context 与输出限制预留；具体上界、端点、模型与请求模式绑定，实际用量合法时释放差额。接受预留偏大、低余额时无法继续调用及未知费用长期占用的代价。未来精确计数只有在能够覆盖实际协议并提供可信上界时才可替换，不能以一次实测未超额代替证明。

## 拟议决策

每次付费调用前，在 Campaign 与 Target 两级账本原子取得请求次数及 Token 额度，成功持久化后才允许模型请求。实际生成客户端必须无隐式重试；每个额外尝试都需新的预留。批量 Runner 只持有受预算控制的模型接口。

Token 记输入加输出，已知消耗、在途预留和未知占用合计不超过批准上限；未知不是零，重复结算不重复释放。请求错误仍可能有成本。超过预留或账目不一致时保留原始观测并停止新增调用，不能裁剪观测值来维持表面不变量。

请求身份与配置、Run 绑定。发送前的持久化占用在中断后仍存在；恢复时不因缺少响应而释放。M3 不恢复旧 Campaign，M4 再实现受控恢复和重跑，不能以新建空账本绕过旧批次累计预算。

首版只承诺经核实服务契约下的请求次数与 Token 控制，不宣称实时货币账单封顶。无法获得上界依据的模型配置不能启用严格 Token 预算的付费批次。

## 验证与限制

尚未实现。转 Accepted 前，至少验证并发竞争、两级额度、未知/非法 usage、重复结算、写入失败先于网络、取消和适配器无隐藏重试；单 Run 实际接入不能绕过预留。真实付费启用还需保存对应供应商能力依据并验证请求配置。

单进程锁与快照只是首版落地方案，详见 worklog，不由本 ADR 固定数据库或调度方式。单机账本不能约束外部使用同一 API Key 的消费，也不能保证服务端超出声明契约时的账单行为。

## 重新评估条件

保守预留明显阻碍正常任务时，比较可认证的精确计数及更紧上界；需要多进程/多机执行时，重新选择原子预留与持久化机制，但保留调用前取得额度和未知消耗不释放的约束。若需求变为严格金额预算，另行明确价格版本、附加计费项与服务端限额能力。
