# ADR-008：Campaign 从创建时持有内核写锁

- 状态：Accepted（2026-10-20；macOS/Linux 可信本地文件系统）。
- 日期：2026-10-20。
- 相关模块：internal/writer、internal/campaign、internal/recovery。
- 依据：[M4.2 设计与实施](../worklog/2026-10-20-m4-recovery.md#10-m42a写者排他与只读恢复检查)。

## 背景与问题

恢复不能仅凭 Running 状态、PID 不存在或审计 pass 判断旧写者已经退出。两个恢复进程同时读取剩余额度，也可能各自写回一份合法但合计超额的账本。原有单进程 mutex 和新目录独占创建不能保护重开目录的场景。

## 方案与取舍

O_EXCL 文件会留下需要处理的陈旧占用；PID 和超时可能将复用的 PID、暂停中的活进程或权限错误误判为可接管；租约还需要跨每次写入的 fencing。当前仅单机、协作写者和本地文件系统，不需要引入租约服务。

采用内核非阻塞排他文件锁，进程终止后由内核释放，代价是平台与文件系统范围有限，且所有写入方必须遵守同一协议。

## 决策

新 Campaign 自计划发布前就取得固定 `.writer.lock` inode 的锁，持有到任务回收、预算结算和控制记录收尾结束。锁文件不删除或替换，不向执行子进程继承描述符。恢复只打开已有锁，不提供 TTL、PID 抢占或 force 开关。

Campaign v2 声明 `writer_protocol=flock-v1`，该版本仍是单 Run 契约；未来多尝试和事务字段另发版本。旧格式只读兼容，事后补建锁不能证明旧程序曾遵守协议，因此不直接写恢复旧格式。

取得写锁只证明协作控制写者排他，不证明命令、容器或供应商请求停止。资源静止另由可信宿主核对；无法确认时拒绝重跑。只读审计仍不取得锁，也不授予恢复许可。

## 验证与限制

真实进程对照验证双进程仅一个取得锁、SIGSTOP 不释放、SIGKILL 后原 inode 可重新取得、正常退出释放，以及存活执行子进程不保留锁。真实 Campaign 在控制屏障被杀后的检查不改原账本或文件；这些是受控机制证据，不是通用崩溃恢复、资源清理或业务迁移验收。

不约束绕过协议的宿主写入、目录复制后的消费、网络文件系统、多机或掉电。schema 声明和摘要本身不是防伪凭据。具体失败记录、源码和验证范围保存在 worklog。

## 重新评估条件

需要多机、网络文件系统或独立 worker 协调时，重新比较中心事务存储与 fencing；仍保留每个预算所有者只能有一个有效控制写者的约束。需要导入旧批次时，另设可证明旧系统停止且完整继承费用的接管流程，不能通过补一个锁文件绕过。
