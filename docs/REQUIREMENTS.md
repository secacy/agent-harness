## 1. 目标与成功标准

**目标**:把项目从“迁移任务的验证工具”升级为“有数据支撑的 Agent 运行时基础设施,以代码迁移为验证负载”。

**成功标准(最终要能写进简历、并经得起追问的数字)**:

- 故障注入下的恢复成功率,以及相比整代重跑节省的 token 与时间
- 三组对比(裸 Agent / 无门禁 / 完整系统)的自动成功率、**错误放行率**、成本
- 在未见仓库上的一次性评测结果(无论好坏都如实记录)
- 越权用例的拦截情况

**重要原则**:数字比功能数量重要。某个实验结果不好看时,照实记录它实际证明的结论,不要调参去凑。

## 4. P0:Trace 与离线回放

**为什么重要**:它是检查点(要存什么状态)、基线对比(成本与步数数据)、失败归因的共同地基,也是 AgentOps 的核心能力。

**需求**:

- 每次 Run 产生结构化 trace,span 类型至少包括:run、step、llm_call、tool_call、budget_reserve/settle、gate_check
- 每个 span 记录:run_id、step_id、父子关系、起止时间、状态、错误类别;llm_call 额外记录模型、prompt/completion token、成本;tool_call 额外记录工具名、参数摘要、结果状态
- 存储先用 JSONL,字段命名参考 OpenTelemetry 风格即可,不强求接入 collector
- **离线回放**:读取已记录的 trace,用已记录的模型响应重放整个 Run(不再调用模型),得到相同的最终判定
- **失败归因统计**:按类别汇总失败原因(编译错误、测试失败、预算耗尽、门禁拒绝、工具错误等)

**验收**：选定并登记 5 个历史 Run，replay 得到与原记录一致的执行终态及最终质量判定（包括无判定）；统计表给出各失败类别占比；按唯一模型调用去重的 token 与账本一致，金额单独按冻结价格来源核对。

**评审补充：回放与计量边界**

- 一个 step 定义为一次模型请求及其返回的整批工具调用/结果；无工具的最终回复也是一个 step。run 级 span 的 `step_id` 可为空。统一使用 `trace_id/span_id/parent_span_id`，并绑定 Run、配置/源码版本和输入身份。
- 参数摘要只能用于查看，不能支撑重放。另存可核对摘要的完整模型请求、响应（含 finish reason、usage、错误）、工具参数与结果、初始输入/工作区、门禁证据及配置。模型凭证不进入记录；公开导出材料与受控回放材料分开处理。
- 最小回放采用记录的模型响应及工具/执行结果作为外部输入，重新运行控制流和判定聚合，逐步核对调用顺序、参数和产物身份；禁止调用真实模型或重放外部副作用。不能只读取原 verdict 后声称回放成功。重跑编译、测试或门禁探针是另一个复验范围，不承诺环境相关结果天然确定。
- 旧 `agent.json` 不含完整调用元数据与逐步持久化保证。先检查归档覆盖度，缺失字段标为 unknown/unreplayable，不伪造时间、finish reason 或模型结果。若无法找到 5 个可完整回放的历史 Run，记录 P0 验收缺口；新采集 Run 可验证机制，但不能悄悄替换历史 Run 条件。
- JSONL 追加写须明确持久化边界：调用前记录开始/意图，完成后持久化结束记录；校验序号与摘要，截断尾行不影响此前已确认记录。仅内存缓冲或 close 时写入不满足中断要求。
- 仅 `llm_call` 按唯一 `call_id` 统计实际用量；父 span 的汇总值、reserve/settle 的额度变化不得再次累加。known、reserved、unknown 分列；未知用量不记零。现有账本是 token/call 账本，金额需冻结币种、价格版本及缓存计价规则；估算和供应商账单分列，缺失不补零。
- 失败归因表每 Run 给出一个主因及可选次因，明确总 Run 数、失败 Run 数和未完成数；编译、测试、预算、门禁、工具、模型/协议、取消/超时、设施与记录损坏分别列项。无失败时占比无定义，不制造 0/0。

## 5. P1:基线与消融

**为什么重要**:这是整个项目目前最大的证据缺口。没有基线,“生成与判定分离”只是主张,不是结论。

**实验设计(先定义再跑)**:

| 组         | 定义                                                         |
| ---------- | ------------------------------------------------------------ |
| A 裸 Agent | 同一模型、同一预算、同一读写与命令工具;无结构化错误反馈、无独立门禁 |
| B 无门禁   | 完整 harness(含反馈修复循环),但不使用独立门禁,任务完成即视为放行 |
| C 完整系统 | 完整 harness + 独立门禁                                      |

**关键要求**:

- **真值(ground truth)必须独立于被评估的门禁。** 否则门禁既当裁判又当运动员,结论循环论证。真值来源:人工复核,或事先写好的隐藏验收测试与行为检查。
- 每组每个任务**重复至少 3 次**(模型输出有随机性),报告均值与范围
- 先冻结模型版本、提示词、预算、工具集,再开跑,中途不改
- 指标:自动成功率、**错误放行率**(被放行但真值判错 / 被放行总数)、误拒率、单任务成本、步数、耗时

**评审补充：主实验协议与指标**

- A、B 均以预算内正常提交固定候选为放行；无提交、取消、预算耗尽或执行失败不算放行。构建/测试仍可作为生成中的工具反馈，不能在提交后给 A/B 偷加一层独立验收。C 只有正常交付且门禁为 `ReadyForReview` 才放行；`NeedsAttention`、`Rejected` 均未放行。
- A 禁用迁移专用结构化诊断与修复策略，保留普通工具输出；B/C 复用同一完整生成配置，仅最终独立门禁开关不同。现有诊断只覆盖部分任务且按需触发，不能写成已有通用“门禁拒绝后自动修复”闭环。确切提示、工具差异、完成策略和预算通知必须在冻结清单中逐项列明。
- 主实验每组每任务至少 3 次独立生成，不复用 B/C 候选充作独立重复；按预定顺序交错执行。旧方案的同候选配对可作为另列的门禁策略分析，不替代 36 次主实验，也不混入主表或重复计费。
- 所有组共用模型、任务信息、普通读写/命令工具、隔离和硬预算。实现复用现有循环和 Runner，以配置表达差异，不另造一套 Agent。生产默认仍启用完整门禁；实验放行字段独立记录，A/B 不伪装为生产 `ReadyForReview`。
- 模型可用版本、源码 commit、提示、输入、镜像、工具、预算、时限、采样参数/供应商默认值、价格依据、真值和复核安排均须冻结；无法固定的供应商内部版本明确披露，不能以模型别名保证完全可复现。
- 四个已见样本是 Goddd、Translation、Workouts、GHCLI。现有独立参考可复用，但需逐项审查独立性并人工复核；既有助手复核不自动替代本版人工要求。先保存放行决定，再对全部固定候选（包括未放行者）评测。真值含 pass/fail/unknown，不能使用门禁 verdict 作为正确性标签。
- 设 N 为预定尝试数，R 为放行数，S/F/U 分别为放行且真值 pass/fail/unknown 的数量：自动成功率 S/N；错误放行率 F/R；R=0 记 N/A，U>0 同时报未知数及可能范围 [F/R, (F+U)/R]。未知不视为正确，也不视为已确认错误。
- 误拒率定义为“真值 pass 且未放行的固定候选数 / 全部真值 pass 的固定候选数”，同时拆出明确拒绝、证明不足和设施失败；无正确候选时为 N/A。未提交/未启动仍保留在 N 中；基础设施错误与候选错误分开归因。
- 自动成功主指标衡量放行且候选正确；交付说明准确性单列，旧完整交付指标继续保留，不与本轮直接合并。逐任务和总体报告均值、最小值–最大值、原始分子分母；重复运行不把 4 个仓库变成 12 个独立仓库。
- 成本至少包括实际 token、模型/工具次数、step、墙钟与价格口径；生成、门禁、离线真值/人工复核分别记账。报告小样本限制，不要求 C 获胜，不按结果追加重复或挑选最好一次。

## 6. P2:检查点恢复与故障注入

**为什么重要**:JD 明确写了长任务可靠性与检查点恢复。你已有中断审计与预算继承,这是自然升级;现状是“整代重跑”,不是 step 级恢复。

**检查点内容**:

- 消息历史(含已完成的工具调用及结果)
- 工作区快照(建议基于 git commit 或目录差异)
- 预算账本(已预留、已结算、在途)
- 当前 step 序号与配置版本

**写入时机**:每个 step 的工具结果落盘之后,先写检查点再进入下一步(write-ahead)。写入必须原子(临时文件加重命名)。

**必须想清楚的设计点(也是面试会追问的)**:

1. **工具调用分类**:只读工具可直接重放;工作区写入类可由快照回滚后重放;任何有外部副作用的操作需要幂等键或在设计上禁止
2. **不重复扣费**:预算采用“预留-结算”两阶段,恢复时依据账本判断每笔预留的状态
3. **在途 LLM 调用**:调用已发出但未收到响应时,保守按已预留金额计入,恢复后重新发起,并在 trace 中标注
4. **检查点写入过程中被中断**:恢复时要能识别并丢弃不完整的检查点
5. **恢复后的一致性**:恢复后的运行与无故障运行,最终判定应一致或差异可解释

**故障注入点**:LLM 调用进行中、工具执行中、检查点写入中、容器被杀、进程被杀、预算耗尽的边界。

**评审补充：恢复的一致性边界**

- 现有 `RecoveryCheckpoint` 是批次中断控制快照，不能当作本阶段的 step 检查点。新格式同时绑定 Run/恢复谱系、step、完整消息与工具 ID、工作区快照摘要、配置/输入版本、累计调用计数及账本 revision。一次 step 的全部工具结果持久化后提交，提交前禁止下一次模型请求。
- 不直接恢复旧账本快照覆盖较新的结算。以持久化账本为准对齐检查点；已结算不重复扣费，已预留但结果未知保守保留。重发 LLM 是一次新的实际调用，分配新 ID 并关联前驱；这可能产生额外供应商费用，不能声称 exactly-once 计费。
- 原子重命名之外须同步文件和目录，并校验版本、内容及工作区/账本绑定。未提交临时文件可丢弃，已发布但损坏的检查点须报错；不能静默跳到旧状态重复外部操作。容器/写者未静止或归属不明时不开始 resume。
- 只读工具仍可能依赖外部变化；回放使用已记录结果，恢复重执行则核对输入身份。工作区写入在快照回滚后重试；构建/测试也可能有副作用，按实际执行范围分类。无法幂等或回滚的外部操作默认禁止自动重试。
- 六类故障注入每类至少 3 组、合计至少 20 组，具体分配、触发 step 和预期在运行前冻结。每组关联无故障对照、step 恢复与整代重跑；累计成本均包含中断前消费，另列中断后的增量。预算耗尽应正确停止，不通过追加预算制造恢复成功。
- 恢复成功率必须列分子/分母：可恢复注入中正确续跑的比例、全部注入中的终态分布，以及预期安全停止/不支持情况分别报告。无故障与故障使用受控响应校验确定性；真实模型续跑存在随机性时记录差异，不要求不可证明的字节一致。
- 此前持久化故障测试可复用机制与夹具，但不冒充本轮 ≥20 组恢复收益实验。未见收益或负收益如实报告，不能用机制测试数量作为节省量。

## 8. P4:沙箱越权切片
