# 需求：运行时可靠性与评测验证

目标是构建**有数据支撑的 Coding Agent 运行时基础设施，以代码迁移为验证负载**。本文件规定目标、范围与验收；当前进度见[开发入口](README.md)。实现方案在进入对应阶段时确定，可依据代码和实验修订。

## 成功标准

最终需要有来源、可复核的数字：故障恢复成功率及相对整代重跑的 token、成本和时间节省；三组对照的自动成功率、错误放行率与成本；严格未见仓库上的结果；越权用例的拦截情况。

数字比功能数量重要。无收益、负收益和未知都如实记录，不根据结果调参、追加尝试或挑选最好一次。

## 范围与推进规则

范围是 trace/回放、基线/消融、检查点恢复、未见样本评测、有限沙箱越权测试和复现材料。

本阶段不做更多 rpcx 门禁规则扩展、完整 K8s、第二沙箱后端、CLI/SKILLS 产品化、系统化上下文工程、IDE 集成或自动 PR。必要的实验与复现入口随功能实现提供。

P0 是 P1/P2 的共同前提，默认按 P0 → P1 → P2 → P3 推进。每阶段达标即停止该阶段扩展；P0–P3 达标后转入 P5。P4 保持有限切片，是否作为最终发布硬门槛在进入该阶段前明确；未完成时必须披露。

## P0：Trace 与离线回放

需要记录一次 Run 的模型、工具、预算和门禁过程，支持离线回放与失败归因。

- 结构化记录覆盖 run、step、llm_call、tool_call、budget_reserve/settle、gate_check。
- 记录身份、父子关系、时间、状态和错误类别；模型调用补充模型身份、token 与成本，工具调用补充工具名、参数摘要和结果状态。
- 记录足以驱动回放的模型响应、工具交互和输入/配置依据；只有摘要或原 verdict 不足以证明回放。
- 回放不再调用真实模型，能核对控制流与最终判定。写入中断时，已确认持久化的记录仍可读取。
- 输出失败归因表，至少区分编译、测试、预算、门禁、工具及设施错误。

**验收**：5 个历史 Run 回放得到一致的执行终态和最终质量判定；失败归因有计数与占比；调用用量与预算账本可核对。若历史材料不足，先报告缺口，不伪造缺失数据或替换验收样本。

**设计待定**：JSONL 为首版存储候选；具体 schema、step 边界、完整载荷、持久化策略及工具/门禁回放方式，需经材料核对后确定。

## P1：基线与消融

| 组 | 定义 |
| --- | --- |
| A 裸 Agent | 同模型、预算与普通读写/命令工具，无迁移专用结构化反馈及独立门禁 |
| B 无门禁 | 完整生成/反馈修复流程，关闭独立门禁，正常完成提交即放行 |
| C 完整系统 | 完整生成流程及独立门禁，正常交付且为 `ReadyForReview` 才放行 |

- 使用 Goddd、Translation、Workouts、GHCLI 四个已见样本，每组每任务至少 3 次，报告均值、范围及原始计数。
- 运行前冻结源码、模型、提示、预算、工具、时限、样本、真值与重复次数；不能固定的供应商参数如实说明。
- 真值独立于被测门禁，来自人工复核或预先准备的隐藏验收/行为检查；四个样本的真值须逐一人工复核。
- 各组通过配置复用已有实现；隔离、输入保护和硬预算一致。精确策略差异、是否采用配对分析及费用计算，在执行前确定；共享候选不能充当独立生成重复。
- 所有固定候选均进入独立评测，包括未放行者；失败、未提交、未启动及未知结果保留，不删除预定分母。

**指标**：自动成功率、错误放行率、误拒率、单任务 token/金额、模型/工具调用数、step 与耗时。

**验收**：有完整三组对比表、独立真值与诚实结论，明确四仓小样本限制；不要求门禁提高成功率或任何一组获胜。旧单次消融草案不作为执行协议。

## P2：检查点恢复与故障注入

需要从已完成的 step 继续，保留历史工作和累计预算，并测量相对整代重跑的收益。

- 恢复状态覆盖消息及工具结果、工作区、预算账本、执行位置与配置版本。
- 已完成工具结果持久化后，先提交有效检查点再进入下一步；中断写入可识别，不把残缺状态当有效检查点。
- 按副作用分类工具；外部副作用需要幂等依据，否则禁止自动重试。恢复前核对工作区、账本和执行资源。
- 已结算调用不重复结算，在途/未知调用保留保守占用；重发模型请求是新调用，可能产生新费用。
- 覆盖 LLM 在途、工具执行、检查点写入、容器被杀、进程被杀、预算边界六类注入，每类若干次、总计不少于 20 组，分配与预期先冻结。
- 对比无故障、恢复与整代重跑，统计中断前后累计成本及增量；预算耗尽应正确停止。

**验收**：恢复成功率有明确分子分母；无重复结算或占用丢失；token/成本/时间节省有对照；一致性差异可解释，列出无法恢复的情形。已存在的整代重跑不代替本阶段验收。

**设计待定**：检查点格式、快照方式、原子提交/持久化协议、恢复接口与故障注入实现，在 P2 确定。

## P3：未见样本评测

- 选择 3–5 个新仓库，预先登记标准、输入版本、真值、接入规则与固定运行次数。
- 评测前冻结 harness 配置和 tag；运行后不调参、不挑结果，所有失败保留归因。
- 继续使用独立真值；记录每仓接入的人工耗时、墙钟及手工工作。
- 已见或参与过校准的仓库不能冒充留出。接入若必须修改核心实现或规则，记录不支持/协议偏离，修复另作开发，不回写本轮。

**验收**：一份无事后调参的完整结果与每仓接入成本。与 P1 同表时标明数据集及配置差异，不直接合并口径。

## P4：沙箱越权切片

验证 CPU、内存、进程数和磁盘限额、默认断网或白名单、凭证隔离；不做多后端抽象。

至少 10 项越权用例，覆盖宿主路径、受保护测试/验收材料、外网、环境密钥、docker.sock、进程耗尽、磁盘写满及规范修改等。每项记录尝试、预期、实际和证据，区分实际阻止与事后检测；未拦截项修复或列为已知限制。

**验收**：完整用例表和限额生效证据，明确工具、容器和宿主的实际保护边界。已有 Docker 参数不代替实测结果。

## P5：发布与复现

在已有证据基础上整理：问题与架构概览、结果表、复现入口、2 分钟 trace/恢复 demo、故障注入和基线对比脚本，以及已知限制。后续方向可记录多 worker、上下文工程、轨迹导出和后端抽象，不作为当前承诺。

## 数据与结论口径

- 自动成功是按组策略放行且独立真值通过 / 全部预定尝试；错误放行是已放行且真值失败 / 全部放行。
- 误拒率是独立真值通过但未放行的候选 / 全部真值通过候选；区分拒绝、证明不足和执行故障。
- 零分母记 N/A；真值未知不当作通过或已确认错误，单列数量及影响范围。候选正确性与交付说明准确性分别记录。
- 模型调用用量去重，预留、已知结算和未知占用分别核对；父级汇总不重复累加。金额注明价格依据，缺失记未知；token 账本不是供应商账单。
- 恢复统计覆盖注入前成本，明确可恢复分母、预期安全停止及不支持项。配置的并发上限不能当作实测规模。
- 实验结果不好看时调整结论，不为改数字继续扩展门禁。P3 暴露的门禁正确性缺陷可以另作修复，冻结结果保留。
