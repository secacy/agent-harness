## 问题与条件

需要决定身份/常量识别是否使用类型信息，并验证结构与行为检查、可信测试副本是否有可观察的互补收益。优先避免已知假成功，其次让基本合法写法可识别，再控制实现及加载成本。

使用 Go 1.26.5、darwin/arm64、CGO_ENABLED=0、默认无额外 tag；未激活配置另有 `extra` tag 对照。通过现有 Local 后端，在临时目录运行本仓库定义的可信单包模块，依赖复制自冻结 T3 v2 SDK。离线环境、只读依赖解析、独立缓存；未调用模型、未使用凭证、未运行 Docker。SDK 及三个实验源码文件的内容摘要记在首条 STUDY 记录，完整材料由 Git 保存。

先进行两次开发联调，记录保存在 `runs/m2-3-study-dev-01.jsonl` 和 `runs/m2-3-study-dev-02.jsonl`。最终增加接口分派、tag 激活和生产 init 对照，并要求预期反例确实出现对应失败原因、提前退出确实返回 0；最终结果使用本文所指的新记录。开发记录未覆盖或替换。

两个识别原型使用同一份由 Go 工具选出的活跃文件。AST 原型使用导入关系、parser 词法对象、参数/接收者/字段及简单复合字面量绑定，支持整数乘 time.Second；类型原型使用 go/types 的方法对象、Selections 和常量值。依赖导出信息来自 `go list -deps -export -json`，没有通过 import 路径猜测缓存文件。

## 身份与常量结果

| 样例 | 有限 AST | AST + 类型信息 | 对正式分析的意义 |
| --- | --- | --- | --- |
| 直接调用 | SDK 调用、30 秒可识别 | 相同 | 两者均能支持最简单写法 |
| 导入别名 | 可识别 | 可识别 | 不能仅凭别名样例声称 AST 不可用 |
| 同名非 SDK Call | 排除非 SDK 方法 | 同样排除 | 名字相同不等于迁移对象 |
| 局部 c 遮蔽 | 区分内层 Other 与外层 Client | 同样区分 | AST 原型使用了实际词法绑定，非字符串搜索 |
| (15+15)*time.Second | 常量未知 | 30 秒 | 类型系统已提供求值结果 |
| 命名常量 time.Minute/2 | 常量未知 | 30 秒 | 无需自行跟踪常量声明与求值 |
| 类型别名 | 接收者未知 | SDK 调用可识别 | 使用类型身份减少别名特例 |
| 跨文件 Client 字段 | 接收者未知 | SDK 调用可识别 | 包级绑定是工程中需要承担的能力 |
| helper 派生 context | 方法及 helper 内常量可识别 | 相同 | 两者都没有证明跨函数传播关系 |
| 取出方法值后调用 | 识别取值位置，间接调用未知 | 相同 | 识别对象不代表已追踪调用路径 |
| 接口 Call | 接收者未知 | 明确标记接口分派未知 | 不能把接口方法误记为无关的非 SDK 调用 |
| 未激活 build tag | 活跃位置 1 个，列出被忽略文件 | 相同 | 单配置成功不能覆盖其他配置 |

显式启用 `extra` 后，类型查询得到两个 SDK 位置，其中一个位于先前被忽略的文件。依赖缺失时加载报错且没有可消费的类型结果；取消保留 context.Canceled。本原型只证明错误不会继续进入识别查询；正式门禁还需结合构建结果区分候选错误、范围缺口与基础设施错误。

初次加载约 1849ms，同批后续加载 81—106ms；类型检查时间按毫秒取整均为 0，表示小于该记录精度，不能解释为零成本。首个命令可能构建依赖，同批共用缓存；两个原型共享文件选择结果，本轮没有单独测量 AST 的无导出数据加载路径。这不是公平性能基准，不能据此宣称类型方案速度与 AST 相同。

**选择：采用 AST + go/types。** 已实现的 AST 方案并非全无价值，但补齐常量、别名与跨文件关系需要自行维护语言规则；类型方案在当前离线约束下已提供这些信息。接受加载和配置管理成本，优先减少常见合法写法的未知。没有证据支持立即引入 SSA；类型查询之后仍需有范围的规则分析。加载库与 Docker 数据传递尚未最终选定。

## 结构与行为的互补结果

行为探针执行 Run 的默认路径，检查实际 RPC 次数、方法和参数、30 秒期限、错误传播及返回后的 context 释放。每个样例最多观察 250ms 的期限窗口；窗口过宽会使实验失败，不会算候选通过。此参数沿用开发观察边界，并非新的时间稳定性证明。

| 样例 | 结构事实 | 默认路径探针 | 能推出的结论 |
| --- | --- | --- | --- |
| 正确直接写法 | 1 个 SDK 位置、1 个 30 秒常量 | 通过 | 是后续有限规则的正例，尚未由正式门禁放行 |
| 正确 helper | 相同数量的位置与常量 | 通过 | 不能因无法分析 helper 就声称行为错误；传播证明仍待补或记未知 |
| 吞掉后端错误 | 相同数量的位置与常量 | 失败，lost backend error | 仅凭调用/常量清单无法区分，应加入行为证据或更强规则 |
| 未执行分支漏超时 | 2 个 SDK 位置、1 个 30 秒常量 | 通过 | 探针没有触达所有位置，需要覆盖清单及缺口处理 |

最后一个样例另用控制探针执行 alternate=true，实际报 missing deadline，确认它存在行为问题。默认探针并未发现此问题，结构清单也只揭示了额外位置，不能单靠数量不等直接判定违规。

选择组合验证的依据是两个方向的真实缺口，而非静态/动态标签本身。这里没有实现三套完整判定器，不统计“仅分析/仅探针/组合”的项目错误放行率，也不宣称组合已经能够给出 ReadyForReview。正式阶段必须把每个位置与规则证明、行为覆盖或未知原因关联起来；无法支持的位置需关注。

四次默认探针命令分别约 1425/651/660/708ms，包含编译和 Go 进程开销。没有真实 30 秒等待，没有重复采样或性能优化结论。

## 可信测试组织结果

| 干预 | 与候选测试混跑 | 仅生产代码 + 宿主测试 |
| --- | --- | --- |
| 正常候选测试 | 可信测试实际通过 | 通过 |

| 测试 init 直接 os.Exit(0) | 退出 0，但可信测试事件缺失 | 通过 |
| 未激活 tag 下的测试 init | 默认配置通过 | 默认配置通过 |

副本从混跑目录读取实际生产字节，复制 client.go 与 go.mod，并核对逐文件摘要；该小样例的生产集合只有这两个文件，不能把这里的固定清单直接当作一般仓库复制器。各副本使用相同可信 SDK。宿主测试不引用候选测试 helper。

因此当前场景选择独立生产副本作为可信测试组织方式，同时必须验证必需测试事件。代价是额外副本、独立测试装配和生产绑定检查；收益是候选测试入口不能直接阻止可信检查。这不防止任意生产代码伪造，也不证明候选保留了原断言。

**仍待验证：**合法 ctx 适配、删除断言、等价 helper 重写及构建语义注释的受限变换比较。本轮没有实现这个比较器，测试完整性方案不能填写已验收。
