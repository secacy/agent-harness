# M4.2：恢复与受控重跑设计

- 日期：2026-10-20。
- 状态：M4.2a、M4.2b 检查点与 [M4.2c 单代受控重跑](2026-10-21-m4-controlled-rerun.md)在声明范围验收；连续多代、通用资源清理与付费恢复未实现。
- 对应里程碑：[M4](../MILESTONES.md#m4运行可靠性与恢复)。
- 当前结论：新建 Campaign 持内核写锁；恢复准备已能封存原文、在检查点中保守转换预算与生成尝试历史，并通过单一 head 幂等提交。原根账本不改，检查点不单独授予付费或重跑权限；M4.2c 另用首次计划的次数/期限约束激活一次受控执行。整体目标保持同批次内完整重跑，不续接 Agent 会话。
- 代码基线：d9b15b9 加当前未提交的 M4.1 工作区；前置证据见 [M4.1c](2026-10-20-m4-readonly-audit.md#12-m41c真实进程中断验收)。第 1—9 节保留设计过程，本轮实现与验收见第 10 节；没有读取 .env、发模型请求或改旧运行产物。

## 1. 问题、目标与范围

M4.1 已证明：基线后、模型在途、报告后及 Run 终态后的真实进程中断可以留下合法记录，审计不应误报完成。但“记录自洽”不等于“允许继续写”。当前仍有四个具体障碍：

| 现有实现 | 恢复时的问题 |
| --- | --- |
| [Campaign.Run](../../internal/campaign/run.go)拒绝已有目录，无跨进程写锁 | 不能排除旧写者或两个恢复者同时运行 |
| [Account.RunID](../../internal/budget/types.go)只允许单 Run；[bind](../../internal/budget/ledger.go)拒绝另一 Run | 改绑会使旧 call 失去归属，或意外重置 Target 累计额度 |
| [TargetRecord](../../internal/campaign/types.go)只有一个 Attempt，Running 时尚不保证 Run 身份 | 不能可靠表达旧尝试、新尝试和恢复自身再次中断 |
| [Docker](../../internal/execution/docker.go)仅有通用执行标签，Local 的进程组回收依赖宿主正常收尾 | Harness 死亡后可能仍有命令或容器；取得文件锁不代表这些资源已停止 |

目标优先级：禁止重复写入和额度恢复、保留可解释的历史、再提供受控重跑。首版继续单机可信宿主，不支持多机协调、网络文件系统、恶意宿主、复制整个批次后并行消费、服务端请求续接或费用对账退款。

本设计中的“恢复”包含两类动作：采纳已经完整发布但未被上层引用的终态；或者为未完成任务分配新 Run，从冻结基线重新开始。选择 Target 必须显式，默认不自动重试所有失败任务。Completed 下的 Rejected / NeedsAttention 已是完整交付，不因质量不理想自动重试。

## 2. 为什么在原 Campaign 内恢复

同一个例子用于比较：上限 250，已知消耗 20，旧请求预留 100，余量 130；恢复后仍只能使用这 130。三个数字都是机制算例。

| 方案 | 对这个例子的行为 | 得失与结论 |
| --- | --- | --- |
| 继续旧 Agent 会话、复用旧工作树 | 必须判断最后一次模型/工具调用是否已经发生 | 可能节省生成成本，但无服务端幂等凭据；replace_text 等操作也不能盲目重放。不采用首版 |
| 新 Campaign、空账本 | 新账本又有 250，原来的 120 占用被绕过 | 实现少但违反 ADR-006，不采用 |
| 关联的新 Campaign、继承旧占用 | 单个分支可保留 120；两个分支可能各自再花 130 | 需额外建立父级额度所有者及唯一后继/分支分配，才能避免重复花费；当前没有分叉需求，不为重跑增加第二层预算域 |
| 同一 Campaign、保留旧 Run、累计预算、新 Run 重跑 | 仍保留 120，新的请求继续检查两级余量 | 首版拟采用；代价是必须升级控制记录和账本格式，支持恢复事务与历史审计 |

这里的选择依据是现有预算所有者已经是 Campaign。关联批次并非错误方案，只是在当前单机、单写者、无分叉需求下，它需要解决的全局问题更多。若以后需要跨机器重分配任务或分叉实验，再比较中心预算服务与关联批次，不通过拷贝 JSON 实现分叉。

## 3. 写者排他、兼容性与资源静止

### 3.1 拟采用内核文件锁，不用 PID 或过期时间代替

新格式 Campaign 自首次创建起，持有固定 `.writer.lock` 文件上的非阻塞排他锁；新建、恢复、后续受控清理都遵守同一协议。锁持有范围覆盖读取校验、恢复事务、调度、预算结算和收尾。macOS/Linux 本地文件系统为首版范围，具体锁调用与文件描述符生命周期在 M4.2a 用真实子进程验证后确定。

锁文件存在本身不是占用证明；不删除或 rename 锁文件来抢占锁，否则不同 inode 可以同时被锁住。拒绝符号链接，固定规范化根目录和文件身份，锁描述符不得传入执行子进程。记录 PID/启动时间可以帮助诊断，不作为放行依据。

恢复只打开新建流程已经创建的锁文件，不使用 O_CREATE 为历史目录补锁；缺锁文件或缺协议声明直接拒绝。新建流程在发布任何可接纳任务的记录前创建并取得锁；锁就绪前的初始化残片只能诊断。

备选：O_EXCL 锁文件会在 SIGKILL 后留下需要判定的陈旧锁；PID 检查有复用和权限问题；租约/超时可能把暂停中的旧进程误判为死亡，还需要每次写入的 fencing。内核锁在进程退出时释放，适合当前同机排他；接受它是协作协议、不能防止绕过协议的程序直接改文件的边界。

**旧版本边界：**目前所有 M4.1 实验及 M3 归档都没有写锁协议。给它们补一个锁文件不能证明旧二进制曾经持锁，因此首版只读审计兼容旧格式，写恢复拒绝旧格式，不提供 force 参数。恢复验收使用新格式从创建到强杀的完整链路。旧 SIGKILL 材料继续保留为 M4.1 证据，不能原地升级来冒充新协议实验。将来若必须导入旧批次，需单独设计停止旧系统及继承费用的人工接管流程。

### 3.2 取得锁后仍要满足独立准入条件

在锁内重新读取来源，不把锁外保存的 audit pass 当许可。至少核对：支持的写锁/格式版本；原计划与输入 pin；完整账本及逐调用重算；Run/Target/报告关系；是否存在未完成恢复事务；可信宿主/验证器能否处理冻结材料；所选 Target 的次数、额度和协议限制。

未知格式、依赖材料缺失、完整性停批、漂移或无法解释的多 Run 都拒绝生成。初始化只留下 plan、没有完整账本的情况首版仅诊断，不重建零账本；后续若支持，需另证明确实尚未开放生成准入。检查失败可在独立新目录发布诊断，不修改旧 Run、旧账目或尝试创建模型请求。

资源静止另行判断：原命令已退出并完成回收，或者可信宿主能提供精确归属的停止证据，才允许新执行。默认不是“已静止”；Docker daemon 不可用、存在未决 create、只有通用标签、仅查不到某个 PID，都不能凭此通过。不得按标签批量杀掉所有 Harness 容器。

M4.2 先在无活动执行命令的受控 Unix 屏障验证恢复 API。通用 Docker 中断重跑依赖后续资源归属与清理工作；在此之前该路径拒绝启动，不添加 `assume-clean` 绕过。若要提前支持真实 Docker 恢复，必须先补上命令启动前持久化归属、在途创建的处置及精确回收验证。不能把这项依赖藏在“已取得写锁”里。

## 4. 新记录契约：历史与当前控制分开

以下为最初完整恢复格式草案。M4.2a 实际发布的 Campaign v2 只增加写锁声明，尚无代次/多尝试；后续字段必须另发版本，不能原地改变 v2。预算 v2 等仍未发布，差异见第 10 节。

| 记录 | 拟变化与不变量 |
| --- | --- |
| Campaign 后续版本（原草案 v2） | 固定写锁协议与计划 pin；新增执行代次 generation、恢复 ID 和 Recovering/Executing 阶段。Status 的执行完成含义不变，不表示业务成功 |
| 计划 | 声明每 Target 的 MaxAttempts，总尝试数包括首次；默认 1。恢复不能临时把上限调大；有原协议一次尝试限制时仍拒绝重试 |
| Target v2 | 有序尝试记录和明确的当前尝试引用；每次分配先保存 ordinal、唯一 Run ID、原输入 pin、恢复 ID 和前驱，再创建 Run 目录/执行。不能按 mtime 选“最新” |
| budget v2 | 每 Target 保存累计 Totals、Run 绑定集合及唯一可准入的 ActiveRunID。旧 call 永久绑定原 Run；切换当前 Run 不清空 Totals、Calls、Rejections 或两级 Limits |
| 旧 Run | 不改 run.json、候选、日志、证据或报告；Running 仍保持原始 Running。恢复记录另存 observed_status=Running、resolution=Interrupted、来源摘要和恢复 ID，不伪造历史 Cancelled |
| 新 Run | 使用唯一目录、全新缓存/消息/工作树；从原已认证基线开始，重做实际基线检查与完整门禁。新增尝试的身份在调用 Runner 前已落盘 |

目前 Runner 自己用 MkdirTemp 分配 ID，需要为 Campaign v2 增加可信宿主预分配身份入口；旧单 Run 入口保持。仅在回调返回后登记身份不足以覆盖“目录已建、第一条记录未发布”的中断。先持久化尝试收据再创建目录；若这期间崩溃，收据也消耗一个尝试名额并以 Abandoned/Interrupted 保留，不悄悄重用 ID。这个保守选择可能耗掉未真正执行的尝试，换取无歧义归属。

“历史保留”不表示根目录所有文件永远不变：当前 Campaign/Target/账本是可推进的控制文件，恢复前先把它们的原始字节和引用摘要封存到恢复记录。旧 Run 全树、封存快照和已发布旧汇总不改；新汇总按代次另存并由当前控制记录引用。验收分别比较这些不可变材料，不能声称恢复写入后整个 Campaign 的摘要仍不变。

### 4.1 按实际发布状态选择动作

| 实际状态 | 拟恢复动作 |
| --- | --- |
| 原 Target 已 Finished，所引 Completed Run 的材料完整 | 保留，不生成；不因 Rejected / NeedsAttention 自动重跑 |
| Target 索引未完成，但所属 Run 已 Completed 且所有报告/预算/证据检查通过 | 补齐当前索引并记录 Adopted；零新模型调用，不重判质量 |
| 已有 Failed / Cancelled Run | 先保留其失败事实；只有请求显式选择、原因允许且仍有名额和额度时，创建新 Run |
| Run 仍 Running，即使 report 已写 Completed | 记录 Interrupted，不能把 report 晋升为 Run 终态；所选任务从基线新开 Run |
| 尝试收据已发布，Run 目录/首记录尚未就绪 | 保留未启动完整的尝试收据；不复用该 ID，不把缺文件当成从未接纳 |
| 原 Pending / Skipped 且未有尝试 | 显式选择后启动；未选择保持未执行说明，不能从汇总分母中消失 |
| 身份冲突、未知版本、完整性错误、终态声称完成但缺必需证据 | 拒绝恢复，不用新 Run 掩盖违规 |

Interrupted 是控制层对旧尝试的处置，不是一个质量 verdict。v2 汇总另列 Interrupted/未执行数量与所有尝试成本；选择一个当前结果的同时保留完整尝试列表，不挑最佳结果。结束本次受控操作时，未选中的中断尝试可以作为已处置的执行失败保留；不能算作成功交付。v2 审计需理解这种历史 Running + 已提交 Interrupted 处置的关系；旧 v1 规则仍原样保留。

## 5. 预算恢复：只改变分类，不退还占用

在排除旧写者并满足准入后，旧 reserved 请求不再是可等待响应的在途调用，将它原子转换为 unknown，outcome 记录 `interrupted`，关联恢复 ID；保留原 call_id、Run ID、输入摘要、Q、创建时间，不填写虚构 usage。转换覆盖本批次全部未决调用，不限于本次重跑选择的 Target。

恢复前后同时满足：Calls 不减，Known 不变，`Reserved + Unknown` 不变，两级上限与 Profile 不变。每个 call 只转换一次。旧快照原文在恢复档案中保留；当前账本不继续把它列为可能唤醒等待者的 reserved，否则余额不足时可能永久等待一个已不存在的调用。

例如 M4.1c model_pending 的 Calls=2、Known=20、Reserved=100、Unknown=0；新格式等价案例在恢复后应为 Calls=2、Known=20、Reserved=0、Unknown=100，绝非把 100 还给余额。新 Run 的一次请求仍须另预留 Q，同时检查 Target 累计额度和 Campaign 额度。Unknown 以后不凭聊天记录、工作树或补交一份本地 usage 释放；供应商对账与退款不在首版范围。

| 旧事实 | 拟处置 |
| --- | --- |
| settled + 合法 usage | 原样保留，不重复结算 |
| unknown | 原样保留整额占用 |
| reserved，来源和额度完整 | 在恢复事务中转 unknown，收费尝试数不变 |
| invalid / HaltReason / 不一致累计值 / 写入结果无法验证 | 停止准入，保留原始观测；不清除 halt 来重试 |
| 余额不足或 MaxAttempts 用完 | 不发请求，记录确定拒绝；重启不增加额度或尝试数 |

budget.OpenExisting 拟先严格解码并重算，不能直接反序列化后继续用存储的 Totals。基础账目校验由 budget 内的纯函数提供，audit 可复用；跨记录与业务证据检查仍在审计/宿主层。budget 不反向导入 audit，避免当前 audit → campaign/budget 的依赖环。

每 Target 的注册 Run 集合用于历史归属，ActiveRunID 仅用于新的准入。旧 Run 的模型句柄不得对新代次预留，也不得再结算已作为 interrupted 固定的调用。恢复事务之外不允许随意改绑；网络失败、超时或受控重跑都不自动追加额度。

## 6. 恢复自身中断：先封存，再单向完成事务

多份 JSON 不能靠若干 rename 形成整体事务。首版拟用一个可重复完成的恢复记录，不引入通用事件溯源引擎。所有步骤持有写锁且关闭生成准入；恢复中断后只能继续同一事务或报告阻塞，不能再叠加一个新事务。

```text
campaign/
  .writer.lock
  campaign.json                     # 当前代次、阶段、恢复引用
  plan.json                         # 原计划，不改预算和任务身份
  budget/budget.json                # 当前累计账本
  targets/<id>/target.json          # 尝试收据/历史/当前引用
  targets/<id>/runs/<run>/          # 旧 Run 不写，新 Run 独立目录
  recoveries/<recovery-id>/
    intent.json                    # 原代次、来源摘要、选择和确定动作
    before/                        # 原控制/账本原文字节、来源清单
    after/                         # 本次恢复转换后的控制/账本检查点
    committed.json                 # 本次事务完成，绑定 before/after/intent
  summaries/<generation>/...        # 逐代次汇总，旧文件不覆盖
```

拟发布顺序：

1. 锁内校验和静止检查；生成动作清单，封存 before 与 intent 并同步。来源复核不一致就停止；尚未被根记录引用的草稿不授权任何写入或请求。
2. 原子发布 Campaign 的 Recovering 阶段及 intent 引用，清除当前 summary 引用，记录原代次；旧 summary 原文件已保留。**这是恢复事务生效点**，之后禁止按旧代次调度。
3. 原子推进账本：转换 reserved、记录本恢复 ID 和下一代次，关闭旧准入绑定；再推进 Target 历史与需要采纳的索引。每次重入检查恢复 ID、原代次和动作，不重复转换、不重复追加历史。
4. 封存 after 检查点，写 committed 标记并同步。标记引用的是封存检查点，不要求未来可变账本仍等于此时摘要。
5. 发布 Campaign 新代次的 Executing 阶段和同一恢复引用；仅此后可为显式选择的任务分配新尝试、绑定预算及执行。先提交 Target 收据，再登记账本 Run，再创建 Run 目录；任一步失败均不调用模型。

写失败或同步结果不确定立即停止；重新持锁读取磁盘，区分“旧状态仍在”“该动作已经完成”“无法解释的冲突”。不能猜测写入失败一定没有生效。Recovering、账本已转换但 Target 尚未更新、committed 后根记录尚未推进，都必须有明确合法前缀及测试；只有临时文件不能视为提交。

SQLite 可以减少多文件控制事务的手工协议，但目前业务报告/Run 仍在文件系统，使用它并不会消除跨文件发布边界，还要新增依赖及迁移。本轮先保留小型、确定动作的快照事务；代价是需要维护前缀识别。若两个实现单元后仍无法把前缀和重入规则写成有限断言，停止叠加标记，重新比较 SQLite 控制库；不以“暂时不会再崩溃”当假设。

## 7. 模块边界、输入与付费入口

拟将恢复编排放在 campaign，复用调度与结果核验；可信宿主注入停止后检查和资源静止能力。campaign 不导入 rpcx 或 audit；CLI/runner 组装现有场景检查。写者生命周期放在一个小型内部组件供 Campaign 与后续清理复用，不创建通用工作流插件框架。

概念流程如下，函数名不是已实现 API：

```text
Recover(原目录, 计划摘要, 显式 Target 清单, 可信宿主服务)
  → AcquireWriter
  → 检查或完成上次恢复事务
  → InspectStopped + VerifyResourcesStopped
  → CommitRecovery(封存、预算转换、历史处置、索引采纳)
  → AllocateAttempt → RegisterRun → 从冻结基线执行
  → 发布新代次汇总 → 释放写锁
```

不能直接复用原 batch 启动路径：它会创建新目录、查询能力再组装全新计划。未来恢复命令只消费原计划，拒绝修改 SDK、规范、门禁、输入摘要或上限。原来源路径失效时，可从旧 Run 的已认证输入副本准备新工作区，但必须按可信 Profile 重算完全相同的输入身份；副本缺失则停止，不使用旧候选作为基线。当前宿主不能验证冻结材料时拒绝恢复，不静默替换 verifier。

真实付费入口还需重新核实服务能力及授权范围。新查询材料另存；有效的 endpoint/model/模式/C/O 若不再满足原 Profile，停止而不是改旧账本 Q。即使语义一致，也保留原 Profile 身份和新的核实材料，不能只因 VerifiedAt 不同重写原计划。初始尝试上限、绝对生成截止时间（若协议有）、原预算和重试规则跨恢复仍有效；每 Run 时间限制可独立计时，但不能替代跨重启的批次截止时间。

原 l2-dev-eval-v0.1.0 是一次尝试实验且使用旧格式，本设计不启动或授权它的重跑，不改原 Enrollment、指标或人工复核记录。新的恢复实验先用确定性模型；付费恢复以后另定协议，不把工程恢复追加成原实验的最好成绩。

### 实施选择与设计细化

新增 [writer](../../internal/writer/README.md)，采用固定空常规文件上的 flock，非阻塞返回 Busy。Create 只用于新目录，Open 不含 O_CREATE；两者拒绝链接、硬链接、特殊文件、非空锁和路径身份变化。创建后同步文件及目录，关闭时不删除锁文件。CLOEXEC 防止执行子进程继承锁；Lease.Verify 复核同一根目录和 inode，Close 幂等。

Campaign 在独占创建根目录后、写 plan 前取得锁；释放 defer 早于所有发布/收尾 defer 注册，因此最后才执行。模型工厂仍须遵守不生成的可信宿主约定，预算、执行回收和控制终态全部在锁范围内。锁失败留下初始化残片，不删除目录冒充未运行。其他平台明确返回不支持；本轮实际运行平台为 macOS，Linux 只做编译检查，不能宣称已实测内核行为。

Campaign v2 只新增 writer_protocol=flock-v1，继续单 Run、budget v1、Run v2。没有提前发布尚未实现的 generation 或历史字段；M4.2b 若改变契约，必须发布下一版本。审计工具升级为 campaign-audit-v2，显式兼容 Campaign v1/v2；v1 不能声明新协议，v2 必须有匹配声明及原始空常规锁文件。审计仍 writer_state=not_checked，不尝试取得锁或制造活性证明。

新增 [recovery.Check](../../internal/recovery/README.md) 组装检查：先拒绝无所有权协议的旧格式，仅打开已有锁；持锁复核头部和预期计划身份，拒绝尚未支持的 recoveries；由可信宿主只读确认资源静止，再调用现有完整审计；随后复核账本来源摘要、HaltReason、头部及锁身份。没有资源检查回调时默认拒绝，不提供“假设已清理”配置。成功返回已释放锁，只是一份检查结果，后续实际恢复必须持锁重新验证。

本单元只检查静态记录与所有权前提，尚不选择 Target、不判断新尝试名额/下一请求余额，也不重新核实供应商能力；这些必须在 M4.2b/c 的实际恢复准入补齐，不能把 Check 成功当作可重跑许可。

准入组装放在独立 recovery 包，原因是 audit 已经导入 campaign/budget，直接在 campaign 调 audit 会形成依赖环；相比复制审计规则，新增这个小型组装层更能保留唯一证据规则。实际调度仍留给后续复用 Campaign；没有新增通用插件或工作流框架。这细化了原来“全部恢复编排放 campaign”的设想。

### 从多文件就地推进改为单一提交点

原第 6 节拟原地逐个写 Campaign、预算、Target，再靠恢复事务解释任意前缀。它保留现有路径，但每个控制文件都可能处于新旧组合，且审计必须理解这些组合。现阶段尚无激活后的执行需要，因此先封存一个包含 before 原文、after 账本和历史的检查点，再原子写 head。只有 head 是提交依据；检查点存在而无 head 是待提交，临时文件没有权限含义。

这减少了本单元的发布窗口，不需要改写或回滚旧控制文件；代价是旧根目录仍描述原尝试，检查点另描述恢复后的控制状态。两者必须在审计中明确分开，不能把 head 当作新 Run 已完成。M4.2c 才选择已提交检查点激活执行，届时需发布新的运行格式。Campaign v2 的单 Run 含义不改，恢复检查点独立 version=1；after 中的预算 v2 支持跨 Run 归属。

首版每个停止的 Campaign 最多提交一份恢复检查点；相同 ID 重入幂等，不同 ID 或未提交检查点冲突时拒绝，不挑最新、不分叉。预算限额、已知用量、调用次数及未知总占用继承；reserved 转 unknown 不归还 Q。没有生成入口，原来一次尝试的实验和付费授权均不因此扩展。

验收计划：校验两级账目和跨 Run 身份，反复转换不重复记账；正确采纳完整终态、记录未完成/未启动；检查点/提交标记的发布故障及真实 SIGKILL 后重入；重复/冲突 ID、篡改 before/after/来源/标记、未知版本拒绝；源 Run/原控制全树不变，旧审计与正常 Campaign 回归。通用资源静止仍由可信宿主提供，默认未知即拒绝。

### 实现与记录契约

新增 [budget/recovery.go](../../internal/budget/recovery.go)：ValidateSnapshot 按逐调用记录重算两级账目，检查身份、限额、整数边界、usage、拒绝记录和历史 Run 归属。RecoverSnapshot 是纯转换：先校验，拒绝 halt，保留 Calls/Known、限额、Profile 及旧 call/Run 身份；reserved 按原 Q 转 unknown，并绑定 recovery_id。budget v2 用 RunIDs 保存历史、RunID 表示当前绑定，准备时关闭当前绑定。RecoveryIDs/RecoveryRevision 约束同 ID 重入，发生新活动后不得复用旧 ID 跳过转换。合法同 ID 返回独立副本，输入不修改。此处没有 OpenExisting 或模型准入。

[campaign/checkpoint.go](../../internal/campaign/checkpoint.go)发布独立的 checkpoint/head v1 数据类型；Campaign v2、TargetRecord、根 budget v1 和 Run v2 的契约不变。Before 使用 base64 保存控制文件的原始字节，避免 RawMessage 再格式化改变空白身份；空文件仍显式编码为字符串，不伪造 null。原文总量最多 4 MiB，整个检查点最多 16 MiB；大输入在创建恢复目录前拒绝。Before 不复制业务树或缓存，Sources 固定审计已读文件、目录成员与缺失路径的身份。

新增 [recovery.Prepare](../../internal/recovery/prepare.go)：复用 M4.2a 的锁内检查，继承相同计划 pin、RunInspector 和可信资源静止检查，再确定性生成检查点，文件同步→rename→目录同步；检查点确认后再同样发布 head。已存在文件只比较、同步，不覆盖；读取不明、发布失败或 sync 结果不确定立即返回错误。Prepared 只表示 head 已确认，错误仍可能发生在发布后；Unknown 不推断没写入。相同 ID 重入读取已保存的时间和原文，完成同一发布；其他 ID 拒绝。两个包内测试缝隙仅用于发布故障和持久化边界暂停，不暴露给 CLI。

After 的 Target 历史明确区分：已索引终态 Recorded、完整但未索引终态 Adopted、仍 Running 的 Interrupted、缺首记录的 Abandoned、未执行的 Unstarted。当前 Campaign 来源仍是单 Run；数据结构允许保存多次尝试，预算 v2 的跨 Run 归属由纯状态反例验证，但没有实际分配或运行第二次尝试。Failed/Cancelled 的既有事实保留，质量 verdict 不重判。仅有 Completed report 的 Running Run 不采纳。

审计工具升为 campaign-audit-v3，新增检查点来源/原文/after/head 的绑定检查，结果用 recovery_pending / recovery_prepared 描述。它从实际来源重新推导 expected after，而不是只信任 head 的摘要。发现与其依赖的来源绑定；来源复核漂移时仍按原规则降级。审计不写检查点、不取得写锁，也不把 Prepared 升格成 execution_state=completed。根 Campaign 的旧状态与历史质量保持。
