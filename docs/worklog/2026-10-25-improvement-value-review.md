## 3. 为什么此前观察没回答改进效果

1. **触发条件没有被固定。** 测试诊断修复价值时原测试已 preserved，测试末轮策略时任务提前结束；这两轮有行为发现，却没有遇到改动所针对的状态。测试结构诊断之后的目标违规修复机会和真实末轮触发次数均为 0，效果仍未知。
2. **目标被新现象不断转移。** 断言修改→新增测试失控→未提交→结构证明不足，每项有局部理由，但没有持续围绕一个瓶颈建立可比较证据。下一项不能因为又观察到一个现象就自动扩范围。
3. **实现验证与收益验证的进度容易混在一起。** 节点篡改、故障和兼容检查是必要的工程验收；它们不增加自主迁移样本。已验证路径只有出现新改动、失败或未解决疑点时才追加相关检查。
4. **完整指标隐藏了失败位置。** 不同层次均可使完整成功归零。保留总指标的同时列明原因，才能判断修复控制缺口、减少证明未知和提升生成正确性各自的收益。

最近全量观察有助于发现问题，但再次执行的边际信息不足以默认抵偿生成、独立参考与收尾成本。本次撤回“当前版本已改动，所以再跑一次四任务观察”的默认推进理由。

| **设计既有测试结构诊断的针对性修复对照** | 已有真实断言修改、不可变基线、可定位反馈和最终验证入口；可明确保证修复问题存在，新增机制较少 | **选择作为下一项设计，尚不启动实现或真实调用** |
| 整理当前工程版后停止优化 | 已有可演示的工程闭环和失败分析，适合项目交付；保留效果未证实的限制 | 始终是可接受的结束点，不要求通过额外实验才能交付 |

选择诊断修复问题依据是现成反馈与已知触发条件带来的可回答性，不是声称它在总体故障中最常见或收益最大。Workouts 的生产语义错误同样重要，目前样本不足以按生产频率排序。

### 下一份设计必须回答的具体问题

待检验假设：**面对相同的原断言修改和相同的基线/规范，机器提供的测试结构定位能否帮助 Agent 在有限预算内恢复原测试约束，并正常提交？**

当前 [migration_check](../../scenarios/rpcx/runner/diagnostics.go) 对历史条件修改只返回 unknown、TEST-001 和声明位置；不会证明“29 秒变为 0 秒”。[真实候选机制对照](../../scenarios/rpcx/runner/diagnostics_test.go)已有定位断言；脚本修复对照则是明确删除断言后的固定恢复，不能代替真实模型面对 unknown 的自主判断。这个差距是下一项要回答的问题，不能先升级规则为 fail 来让试验更容易。

设计应先写清相同起始候选、规范/基线、预算和终止条件下的比较方式，固定完整尝试数和报告规则，再评估是否值得执行。至少区分：没有机器诊断但保留原文/测试工具的对照，以及增加现有机器定位的条件。不能把参考补丁、复核答案或目标替换文本送入生成上下文。

成功不能只看诊断变为 preserved：要核对原断言及其他原测试保留、允许的 API 适配、完整测试结果、候选中是否新增生产改动和是否正常提交。两种条件均保留失败、未知及实际用量；单次成功只证明该次修复可行，小规模结果不能称稳定增益。强制注入诊断只回答反馈使用效果，不回答 Agent 是否会自主选择该工具，二者需在设计中明确。

固定错误候选的注入方式、两组对照的提示差异、模型配置/顺序、重复数、资源上限和执行入口尚未确定。它是基于已见缺陷的开发修复对照，不能混入从原始仓库迁移的成功率分母。用户确认具体设计后才实现或准备协议；新消费另按具体范围授权，本轮没有此授权或执行。

### 停止和改选条件

- 若现有反馈不能准确定位目标声明，先处理定位问题；不启动完整迁移等待碰巧发现。
- 若固定起始状态需要重建通用工作流、修改认证基线或引入多轮恢复，先缩小试验入口并重新权衡，不扩展主系统来服务一次观察。
- 若两组都能修复，或有反馈仍反复失败，如实记为未见增量/当前无效；不自动加预算、提示或新工具直到得到通过。
- 若目标已被直接回答，则结束该工作；新增测试、性能、更多仓库等现象进入待办，不自动串成下一轮实现。
- 实验是否值得运行，在具体成本与可获得结论明确后决定；现有工程交付可以先完成，不依赖不断追加模型观察。
