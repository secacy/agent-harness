# 预算末轮的候选交接设计

- 日期：2026-10-24（Asia/Taipei）。
- 状态：已实现，受控机制与交付验收通过；尚无新策略的真实模型效果结论。
- 代码基线：`4b64e75`。
- 前置证据：[Translation 诊断观察 01](../experiments/2026-10-24-translation-diagnostics-real-model-01.md)、[已有预算提示设计](2026-10-18-budget-awareness.md)。
- 已确认方案：新增显式启用的 `final-response-v1` 策略，最后一个可用模型调用只用于最终回复；工具额度恰好用完时也进入该模式。先解决“没有后续调用却继续执行工具”的边界，更早冻结编辑及业务范围判断留待证据。

## 1. 问题、证据和本步目标

最新 Translation 原 Run 在第 33 次完成双配置本地测试，第 34 次诊断 preserved，第 36 次在剩余 5 次调用时新增临时探针，随后遇到编译与断言错误。第 40 次已收到最后一次调用提示，仍继续修改，之后以 limit_reached 结束，独立质量门禁没有运行。原测试保留、生产行为在事后参考中通过，新增测试失败。

这里有两个问题，所需证据和实现成本不同：

1. **末轮仍可执行工具。** [Loop](../../internal/agent/loop.go)始终将完整工具集合交给 Model，末轮仍分派工具；“Prefer a final response”只是提示。这个控制边界可以确定性验证。
2. **临近预算仍扩展工作。** 目前无法从 replace_text 的参数可靠判断一次编辑是必要修复还是可选扩展。本次只有一个已见样本，不能据此认定剩余 5 次时所有新增测试都应禁止，也不知道先前候选是否能通过完整门禁。

本步优先解决第一个问题：在原次数上限内保留一次仅用于交接的模型调用机会；模型有效结束后，由已有 Runner 固定当前候选并进入独立验证。更早阶段继续允许修复，接受“新增错误可能在末轮之前发生”的限制。

目标可测为：**启用策略后，进入仅回复模式便不再执行任何工具；合法 stop 才进入既有提交路径；请求、预算和失败事实可核对。** 不承诺模型一定有效回复、网络一定成功、Token 额度充足或最终门禁通过。“提交保障”因此收窄为候选交接机会，不作为迁移成功保证。

## 2. 取舍：为什么选择这个范围

优先顺序：预算及失败记录真实、候选质量仍独立判定、交接边界可执行和可审查，然后才是正常完成比例。接受少一个可用工具轮次，优先避免最后一次编辑后没有任何模型回复机会。

| 方案 | 对当前问题的作用 | 代价与本次选择 |
| --- | --- | --- |
| 继续只加强提示，提前到剩余 5 次收尾 | 可能减少第 36 次的可选探针；实现最少 | 已有末轮提示未被遵守，阈值 5 缺一般依据；可作以后独立提示对照，本步不只靠它 |
| **最后一次调用只允许最终回复** | 将末轮从“可继续操作”改为明确交接；宿主能确保不再执行工具 | 少一个修复/检查轮次；末轮前的错误仍保留，最后回复也可能失败。首版采用，显式启用 |
| 剩余若干次时禁止写入，保留读取/检查/提交 | 可在更早位置阻止新增探针 | 需要定义阈值、读写工具分类；会阻断检查刚发现的必要修复。本次证据不足，暂缓 |
| 为最终回复在共享账本长期预留 Token/调用额度 | 在其他 Target 竞争时也可保留费用容量 | 改变预算分配、等待与恢复语义，仍不能保证网络/时间；当前失败不是 Token 或共享额度不足，暂缓 |
| 超限后由宿主自动采纳当前或历史快照进入验证 | 即使模型未提交也能回收候选 | 改变候选交接主体、状态及指标口径；历史本地测试通过也不代表完整门禁通过。作为独立能力再设计 |
| 增加调用次数或失败后另开总结请求 | 多一些修复/交接空间 | 改变成本与授权范围，仍可能再次扩展工作；本步保持原总上限 |

选择末轮约束，依据是现有接口已能传递空工具集合，Runner 已有明确的正常提交后验证路径，因此可用有限改动验证一个真实控制缺口。若验收只得到更多 Completed/Rejected，而有效自动成功与可审查程度没有改善，应如实报告；不能把退出标签变化当成迁移效果提升。

这不是完整“收尾阶段系统”：不加入阶段调度器、修复必要性分类器、自动回滚、历史最优候选选择或插件接口。也不同时调整软提醒阈值，保留当前剩余 3 次的提醒条件，便于区分硬边界与提示改动。

## 3. 调用契约与状态

策略仅接受两个值：缺省空值沿用当前行为；`final-response-v1` 启用本设计；未知值在请求模型前拒绝。开关属于执行策略，不塞入数值 Limits，也不由 Agent 修改。

启用后，在每次请求前、取消及模型次数硬限制检查之后计算：

```text
modelRemaining = MaxModelCalls - usedModelCalls
toolRemaining  = MaxToolCalls - usedToolCalls
finalResponseOnly = modelRemaining == 1 || toolRemaining == 0
```

预算消息仍记录包含本次的剩余次数。启用时明确告知“最后一次调用只用于最终回复”，并显示剩余可使用工具的模型轮次（在工具额度非零时为 modelRemaining - 1）。仅回复模式说明：工具已关闭，总结现有改动、实际检查和未解决项，最终回复提交当前候选；报告问题不妨碍提交。

| 状态/事件 | 拟议行为 |
| --- | --- |
| 未到边界 | 使用原工具集合与执行流程；可以提前正常提交，不强制用满预算 |
| modelRemaining=1 | 本次 Complete 的 tools 固定为 nil；模型次数仍计入原上限 |
| toolRemaining=0 且仍有模型次数 | 下一次请求立即采用仅回复模式，不继续发送已无法执行的工具；有效结束后不再消耗剩余调用 |
| 仅回复模式收到合法 FinishStop、无 tool_calls | 按现有 ExitCompleted 契约返回；Runner 固定当前候选并独立验证。回复文本不证明候选正确，沿用既有 stop 判定，不新增内容评分器 |
| 仅回复模式仍返回 tool_calls（包括声称 stop 却附调用） | 保留原回复，返回协议错误；不执行任一工具、不生成虚假工具结果、不增加 ToolCalls 执行尝试计数；不追加纠正请求 |
| 截断、未知 finish、模型错误、取消/超时 | 沿用现有失败分类及 usage 记录，不自动变成提交 |
| 整批工具请求超出剩余工具额度 | 保持当前整批拒绝/limit_reached；不部分执行，不额外发起收尾请求。本策略只覆盖正常到达边界的机会 |
| MaxModelCalls=1 | 第一轮就是仅回复模式；允许提交未改候选供门禁拒绝，不承诺完成迁移；配置检查展示该后果 |

仅回复模式下，关闭工具集合和宿主拒绝执行同时生效：没有工具 schema 不等于模型不可能产生非法调用。已有 DeepSeek [编码器](../../internal/deepseek/protocol.go)会在工具集合为空时省略 HTTP tools；历史 tool_call/工具结果保留完整，不为了收尾删除对话。首版不扩展 agent.Model，也不添加供应商专用 tool_choice 字段。

现有消息历史在一次工具批次执行完后才进入下一请求，本设计沿用这一顺序。前一轮已执行编辑的结果会进入末轮上下文；仅回复模式关闭读取和检查，因此倒数第二轮编辑后可能没有本地复验机会，模型必须如实披露，由提交后的独立门禁实际验证。宿主不能声称刚刚的编辑已被旧检查覆盖。

## 4. 预算、时间和失败边界

“保留一次”只指 Loop 的调用安排，不表示预先取得了付费额度。末轮仍经过同一个 [budget.Model](../../internal/budget/model.go)，按原 Q=C+O 原子预留、持久化与结算。工具为空不能据此缩小保守预留，不另开裸客户端或绕过共享账本。

若共享/Target 调用数或 Token 先不足，末轮可以被拒绝；若 context 已超时、工具执行失败或批次取消，也可能根本到不了该轮。已有 Run Timeout 覆盖基线、生成与独立验证，本步没有为门禁保留墙钟时间，所以有效提交后也可能在验证阶段超时。这些都保持失败记录，不能用“最后一轮已保留”宣称完成保障。

仅回复模式的一次请求成功、用量未知、协议错误或服务失败，均由现有包装器处理实际费用；缺 usage 继续保守占用。已有预算拒绝返回 ErrModelBudget/limit_reached，Loop 尝试次数与账本准入数仍可能不同，分别记录。

当前真实案例只说明调用次数与工作范围的矛盾，没有 Token 超额、工具额度耗尽或宿主超时，因此本步不调整账本预留、Run 时限或验证时间分配。

## 5. 接口、记录及兼容

拟增加小型 `agent.CompletionPolicy` 字符串枚举和 `Loop.CompletionPolicy`；只有空值与上述 v1，没有注册表或动态策略。沿 Runner.Config、Campaign.Target、batch Target JSON 的 `completion_policy,omitempty` 传递，并写入 Run Input。单 Run Go API 与 batch 入口先支持；现有单仓库 CLI 不另增开关。

Campaign 的实际 Plan 包含该字段，现有 SettingsSHA256 对整个计划取摘要，启用/关闭都会改变新协议身份。空值必须 omitempty，旧 Plan/设置摘要的既有序列化保持一致；旧协议与旧样本不原地更新。恢复时使用冻结 Target 策略创建新 Run，不通过恢复收据切换策略或补一次费用授权。

Agent Result 拟增加一个可选 `FinalResponseAttempt`，只保存本地模型尝试序号与调用前 Messages 前缀长度；没有进入模式时省略。它在调用前记录，因而表示“尝试进入”，不是“已发 HTTP 请求”或“已提交”。完整消息/usage、退出原因及账本继续保存实际结果。合法提前 stop、在末轮模式下 stop、末轮未准入/失败可据此区分，不改变原 ExitReason 或 Completed 的含义。

调用前始终选择规范的 nil 工具切片，便于按现有 Go JSON 输入摘要重建 `{Messages: prefix, Tools: null}`。模型接口摘要与 HTTP 字节摘要保持区分。审计应核对：

- Plan、Run Input 的策略一致；缺省旧记录没有新增要求，未知策略拒绝消费。
- 可选记录的序号/前缀长度与实际预算通知、剩余计数及历史配对一致；正常到达边界不能漏记，提前完成或基线失败不能虚构进入模式。
- 有预算准入/拒绝记录时，核对同一 Target/Run 与末轮输入摘要；无准入时不能报告“已发请求”。取消/设施错误可能没有准入或拒绝记录，按原失败证据与未知边界处理。
- 完成结果必须有无工具调用的合法最终回复；仅回复请求后出现工具执行结果属于违规。模型违规提出但未执行的调用必须与执行次数区分。
- 新失败、提前完成和边界完成在审核材料中明确展示；旧诊断/旧 Campaign 审计继续可读。

未来轨迹分析不能再假定每次请求使用相同 tools.json：新协议需按实际策略和尝试记录选择正常集合或 nil。旧 [Translation 分析器](../experiments/translation-diagnostics-dev-v0.1.0/analyze.py)及其冻结协议保持不变，新实验另版准备。首版实现验收应已有请求摘要重建对照，不到真实实验才发现取证缺口。

## 6. 实现顺序与可测验收

确认后按一个完整工作单元推进，设计与实现一起提交：

1. Loop 的显式策略、空工具末轮、宿主分派约束及最小尝试记录；保留现有默认行为。
2. Runner/批次配置与计划身份、报告/审计接入，以及预算包装器和本机模拟 HTTP 的联调。
3. 用脚本模型经真实工具交付三类候选，验证该控制边界与独立门禁协同，再决定是否准备新真实观察。

| 验收主题 | 必须断言的行为 |
| --- | --- |
| 缺省兼容 | 原末轮仍执行工具并 limit_reached 的测试继续通过；旧设置摘要、历史审计不变 |
| 正常到达末轮 | 前 N-1 轮可用工具，末轮 nil；总 Complete 不超过 N，无新增重试或预算外请求；提前 stop 不多调用 |
| 工具额度恰好归零 | 下一轮仅回复；上一轮批次完整配对；余下模型额度不用满；超额整批仍按旧规则拒绝 |
| 禁止分派 | 替身在仅回复模式返回单个/多个工具、stop 附工具等：执行器零调用、候选不变、回复保留、协议失败，计数不虚报 |
| 异常边界 | N=1、末轮截断/模型错误、调用前后取消、Token/次数拒绝及未知 usage；终态和账本保持真实，不能伪完成 |
| HTTP 与费用 | 本机模拟服务收到完整历史且没有 tools 字段，账本预留先落盘；实际输入摘要按 nil 工具匹配；失败请求仍正常结算 |
| 候选交接 | Translation 固定 correct / alternate-missing-timeout / mapping-helper 的受控新 Run 依次保留 ReadyForReview / Rejected / NeedsAttention；只因合法 stop 才进入独立门禁 |
| 错误局部化 | 并发受控任务中，一个末轮非法工具请求只使本 Run 失败，其他任务与预算归属不变 |
| 审计与身份 | 篡改策略、末轮序号/消息前缀、工具执行结果、账本请求摘要均可定位；新完整批次与旧真实批次可读 |
| 原失败轨迹解释 | 原最后一次 edit 在新模式下会被阻挡的脚本对照只计机制证据；不能把旧请求改写后当作新的真实模型结果 |

以上均是计划，尚未执行。只跑与改动相关的机制、集成和兼容检查；独立质量门禁失败必须保留，不能把生成收尾测试通过等同迁移成功。

## 7. 效果判据与停止条件

先区分机制验收与效果研究。机制验收回答“末轮是否仍能执行工具、有没有绕过预算、是否真实交接给门禁”。效果研究才回答“真实 Agent 是否更容易交付有效候选”；如要运行，需要新协议、固定源码/预算/输入及本版授权，旧单次许可已消费。

新观察至少记录：提前/末轮提交及失败数量、独立门禁是否实际完成、末轮前后的最后编辑与检查、原自动成功/错误放行/需人工确认、已知与未知成本。Completed/Rejected 增加只表示形成更多已判定交付，自动成功仍要求 ReadyForReview 加完整独立评测。使用已见开发样本不能给出泛化或严格因果结论。

改选信号：

- 若模型在没有工具 schema 时仍频繁返回调用或请求被真实服务拒绝，先检验适配契约，停止扩展，不补发预算外请求。
- 若新增策略只是把大量 Failed 变成 Completed/Rejected，应回到候选质量及更早工作范围问题，不能以提交率代替效果。
- 若必要修复经常恰好落在被关闭的末轮，或批次 Token/时间更早耗尽，再分别评估提前阶段控制、预算分配或墙钟预留；不把它们一次并入本单元。
- 若局部策略必须依赖大规模工作流重构才可落地，先收窄方案并报告原因。

本设计形成局部、显式的实验策略，先在 worklog 保留取舍；确认实施并决定长期默认采用后，再判断是否需要 ADR。当前不默认改变所有已有运行。

## 8. 本轮设计核对

本轮读取了 Loop/消息与退出类型、Runner 生成及验证边界、模型协议编码、预算包装器、Campaign 配置、协议设置摘要和现有审计，并对照实际失败轨迹及 2026-10-18 的早期取舍。新的建议重评的是当时暂缓的“强制末轮总结”，依据是已有软提示下再次出现末轮工具执行，仍未证明所有任务需要提前冻结编辑。

设计阶段仅新增文档及进度入口，未修改 Go、冻结协议、候选或运行产物；没有读取 .env、调用模型或执行新迁移。当时按既有约定等待确认，未单独提交。确认后的实现见第 9 节。

## 9. 确认后的实现与验证

用户确认后实施 `agent.FinalResponseV1`，沿 Loop、Runner、Campaign、batch JSON 传递，缺省序列化省略新增字段。末轮传 nil tools，宿主在分派前拒绝附带工具调用的回复；只保留一次本地尝试标记，不新增供应商字段、请求或自动采纳路径。提示的软收尾阈值仍是三次。

新增历史核对器复核预算通知、完整工具配对、本次工具计数、末轮序号/消息前缀及完成边界。Runner 审计再检查 Plan/Input 的策略与次数一致，并将末轮 nil 工具输入摘要对应到同一 Target/Run 的准入或拒绝记录；没有准入的取消/设施失败保留事实，不伪称服务收到请求。审核报告展示提前提交、末轮尝试和未到达边界；batch `--check` 说明一次调用配置没有工具轮次。
