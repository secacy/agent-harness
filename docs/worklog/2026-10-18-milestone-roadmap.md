## 问题与目标

M1 已在受控 T1/T2 场景完成一次真实模型闭环，但原里程碑只记录 M0/M1，缺少整体交付边界。需要先确定后续阶段解决什么、如何验收、时间不足时能够交付什么，再进入下一项实现。

本次仅维护路线文档，不实现新的门禁、批量 Runtime、恢复或评测命令。Harness 能力、T1—T5 场景难度、L1—L3 评测层次分别表达，避免用增加 SDK 迁移规则代替系统能力建设。

## 方案与取舍

| 方案 | 收益 | 代价与判断 |
| --- | --- | --- |
| 先完整多仓库 Runtime，再增强判定 | 尽早暴露并发、资源和运行管理问题 | 异构输入需要提前建设 L2；完整恢复工程会推迟对质量判定方法的检验，不采用 |
| 先小批量闭环，再判定，最后补批次预算和恢复 | 缩短首次批量演示路径 | 付费并发没有批次预算预留，无法满足总量约束；判定风险仍延后，不采用 |
| 先判定，批量与预算一起交付，再恢复与审计 | 在现有 demo-orders 上优先检验语义错误和证据不足；并发开始即受批次预算约束 | 多仓库能力稍后出现；限制 M2 分析范围，以一个代表性 T3 场景开始，采用 |

M2 的交付是判定与证据组织能力，T3 是验证该能力的场景。完整性分析不能承担任意 Go 程序的正确性证明；无法覆盖的情况显式记录，防止这一阶段无限扩张。

M3 为最低项目交付点：批量闭环、初步 L2 数据和成本指标共同形成可展示成果。它仍不等于项目全部完成，可靠恢复、审计和正式评测分别由 M4/M5 验收。

本次是开发顺序与验收范围的确定，没有固定新的运行架构或技术实现，不单独新增 ADR。预算预留、状态恢复等后续重要技术选择仍需在实现前权衡，必要时形成各自 ADR。

## 评审中确定的边界

- 评测从 M2 持续推进；M3 首次统计前定义指标，留出样本从准备时独立管理，M4 最终冻结协议，M5 执行一轮正式评测。
- 批次预留是付费并发的前提，覆盖输入与输出；未知用量、在途请求、重试和重启不能使额度凭空恢复。Token/金额上界及结算协议待具体设计，不能以估算宣称严格费用封顶。
- Skipped 属于任务或检查状态，不增加为候选质量判定；必要检查未完成、明确违规和基础设施故障分别处理。
- “故障不影响其他任务”用固定候选或确定性替身、足够资源与预算证明。共享预算耗尽会产生预期影响，另行验证；真实模型轨迹变化不作为机制一致性断言。
- 故障注入要区分执行子进程、独立 worker 和整个 Harness；当前 Run 为函数调用，不预先假定每个 Run 都有可单独强杀的进程。
- 恢复可以从同一 Target 的新 Run 完整重跑开始。候选固定、验证、终态持久化及预算结算边界均需覆盖；保持旧记录和成果。
- 审计同时测试正常记录和被破坏的记录；零违规不能作为唯一测试。合法中断可识别为待处理，审计不替代语义验证或自动修复。
- 机制回归、门禁判定和独立离线评测分开统计；无放行、未知用量、未完成评测不能伪装成零错误或零成本。
