## 1. 目标、优先级与范围

这一工作要回答：三个样本有什么真实差异、为什么选它们、裁剪之后还保留什么、什么情况下必须退回重选。样本用于检验同一 rpcx 迁移在不同业务结构上的执行与判定，不承担开源项目生产适用性证明。

选择优先级依次为：可追溯的原业务逻辑与测试、已有远程调用边界、互补的调用结构、可离线准备的有限依赖。仓库知名度、行数和当前门禁是否容易通过不作为入选依据。三个来源本身都是示例或模板工程；裁剪并植入 rpcx 后称为 **L2 半真实开发样本**，不能称为三个生产仓库的自然 SDK 升级。

本轮只读取公开的固定版本源码、目录树、模块要求与许可，制定输入与验收计划。没有执行上游代码、生成迁移补丁、改动旧冻结数据、注册新 Profile 或调用付费模型。以下描述的基线和对照均为后续准备要求，不是已经通过的实验结果。

## 2. 为什么选择业务切片

| 可行方案 | 在本次候选上的具体得失 | 选择及代价 |
| --- | --- | --- |
| 整仓接入 | Wild Workouts 包含 Firestore、云服务和端到端测试；go-clean-template 包含数据库、消息系统和代码生成工具链，环境问题会先于迁移问题出现 | 暂不采用。若裁剪使主要调用结构消失，再考虑整仓支持，不能以大规模删测试伪造可运行整仓 |
| 保留业务切片，替换既有出站边界 | 可保留货运路由、翻译存储顺序、取消训练规则及原测试；把传输边界替换成本地 SDK，可脱离外部服务运行 | 采用。接受裁剪、依赖准备与业务保真复核成本；结论只覆盖保留的切片 |
| 从零编写三个小仓库 | 离线最容易，但业务结构、断言与迁移答案可能共同设计，不能提供已有项目的异构证据 | 用于故障注入/L1，不计入这三个 L2 样本 |

不设“裁到 300 行才算完成”的目标。依赖闭包、原测试和业务路径决定大小；若只能靠重写领域逻辑或替换原断言才能达到输入限制，应停止该样本准备并记录改选理由。

## 4. 三个样本的准备契约

### 4.1 l2-goddd-booking：跨接口传播 ctx

- 保留：根领域类型与原领域测试，booking 服务及 5 个原测试，路由接口、booking 的日志/指标装饰器、HTTP booking 入口及必要 mock/inmem 代码。server 按 booking 路由裁剪，移除其他功能时逐文件记录。
- rpcx 植入位置：`routing/proxying.go` 的出站路线查询。保留 RouteSpecification 到 itinerary 的业务映射；在准备阶段用本地 rpcx-v1 替换 HTTP/Go-kit 传输与熔断设施，不伪称仍验证原 HTTP 或 Hystrix 行为。
- 应保留的迁移难点：`requestRoutes(r)` → `RequestPossibleRoutesForCargo(id)` → 装饰器 → `FetchRoutesForSpecification(rs)`。后两者原本无 ctx；迁移须修改接口、实现、调用者和相关测试，直到使用 `r.Context()`，不能沿用客户端长期保存的 Context 充当请求上下文。
- 原测试锚点：`TestBookNewCargo`、`TestRequestPossibleRoutesForCargo`、`TestAssignCargoToRoute`、`TestChangeCargoDestination`、`TestLoadCargo`。根领域测试属于完整保留清单的一部分，不能只保留这五个名字就称全部原测试保留。
- 行为边界：未知货物返回空路线，不发起远程请求；远程失败原本表现为空路线。迁移不擅自把公共返回值改成 error。取消是否传到远端需在后端观测，不能仅靠服务返回空列表判断。
- 不纳入：Mongo、其他服务路由、UI、完整部署。它们的测试列为裁剪范围外，不记为跳过后通过。
- 退回条件：为离线化必须重写 booking 规则或抹掉装饰器/无 ctx 调用链。旧 Go-kit 依赖的准备难度要实测，不能先保证低成本。

### 4.2 l2-clean-translation：已有 ctx、生成 mock 与构建配置

- 保留：entity、翻译 usecase、仓储/WebAPI 接口、生成的 `internal/usecase/mocks_repo_test.go`、原 `TestHistory` 与 `TestTranslate` 的 5 个具名子例，以及所需 tracing 包装。用例已有 ctx，不人为删除它来制造 T2。
- rpcx 植入位置：`internal/repo/webapi/translation_google.go` 的远程翻译调用；保留请求/结果映射和 `%w` 错误链。原用例的“翻译成功才 Store”、错误不存储等行为继续由原 mock 测试检查。
- 边界：以 usecase 的 ctx 入参为请求入口；不接入完整 REST、认证、数据库、消息系统和生成工具链。原 mock 测试不会走真实适配器，因此另加可信的实际 rpcx 路径探针；不能把原测试通过当作 T3 证明。
- 生成代码保护：原生成 mock 的接口已有 ctx，预期此次升级不需要重生成；将实际参与测试的该文件设为受保护路径。若准备时接口范围改变，先完成准备并重新生成、记录工具版本，再冻结输入；不能让迁移候选任意改 mock。
- 显式构建配置：准备两个互斥的 RPC 适配器实现，默认实现与 `rpcx_alternate` 实现；两者遵循相同翻译契约、各自包含 RPC 调用点，运行相同业务/探针测试。标签及第二实现是**人为植入的配置挑战**，不声称上游天然具有该构建矩阵；从同一来源派生，仍只计一个样本。
- 为什么增加配置变体：只保留上游默认构建，不能检验“默认配置过了，但另一实现漏迁移”；选择第三个带基础设施依赖的整仓仅为获得原生标签，首批成本更高。接受这一维度是构造的限制，不把它作为真实项目多配置效果的证据。
- 退回条件：生成 mock 被移成不参与构建的装饰文件，或双配置最终编译的是完全相同的唯一 RPC 调用点。必需配置列表要固定为 default 与 rpcx_alternate，每个配置都构建、测试、分析和运行探针。

### 4.3 l2-workouts-cancel：回调与条件远程调用

- 保留：trainings 的取消 command、领域 training、原取消测试与其真实依赖闭包；common 模块保留 decorator/logs/metrics 的必要部分及许可证。保留两个模块的原关系，通过本地 replace 连接；不为省事把 command、领域与装饰器重写成一个文件。
- rpcx 植入位置：从 TrainerGrpc/UsersGrpc 的服务方法裁出此次取消路径需要的适配器，分别连接教练与余额本地后端；去除该切片已不使用的 gRPC 生成/连接依赖，记录对应替换。Schedule/Move 等其他业务功能不计入本次范围。
- 结构锚点：`Handle(ctx, cmd)` → `UpdateTraining` → `func(ctx, tr)` → 条件余额更新 → 教练取消。保留 command/service 接口及泛型装饰器，已有 ctx 原样传递；请求入口定义为 command 的 Handle。
- 原测试锚点：`TestCancelTraining` 的 4 个子例，分别覆盖学员/教练取消、24 小时内的余额规则；保留调用次数、余额数额和训练时间断言，以及依赖的领域测试。不能把无 RPC 的余额零变化分支当成遗漏路径。
- 行为边界：余额失败时不再调用教练；远程副作用顺序、错误包装及仓储回调的成功/失败提交行为保持不变。不声称两次远程调用具有事务原子性，后一步失败不能凭空回滚前一步。
- 不纳入：Firestore 实现、服务启动、HTTP/云端组件测试、部署。`service/component_test.go` 没有可用的离线隔离标签，不能简单执行整模块测试并声称它会自动跳过；准备切片时明确排除该服务包及列出损失的覆盖。
- 退回条件：为了适配分析器而把回调改为直线函数，或去掉条件判断/其中一个远程依赖。门禁不支持这些形态时，应扩展有限证明或报告缺口，不能改样本来迎合门禁。

## 5. 共用迁移条件与接入缺口

### 新 L2 SDK 数据，不改旧夹具

当前 T3 SDK 的 Request 固定为 SKU/Quantity，Call 仅返回 error。用字符串或库存字段编码路线、翻译结果会扭曲原业务；给三个样本分别发明 SDK 又会混入三个迁移契约。因此拟为 L2 准备一套共用、单独版本化的 SDK 对：

```go
// v1：迁移前仍由 SDK 提供 30 秒默认超时。
NewClient(addr string) (*Client, error)
Call(method string, request any, response any) error

// v2：由调用者显式传入请求上下文与超时。
Dial(addr string) (*Client, error)
Call(ctx context.Context, method string, request any, response any) error
```

response 使用调用者提供的响应指针，测试后端按业务类型填充；仅是内存 SDK 契约，不引入网络序列化框架。三个样本共享同一对 SDK、相同模块路径和 T1/T2/T3 变化：导入/构造器、ctx 传递、显式保留 30 秒上限且不覆盖父上下文更早的截止时间与取消。30 秒是**植入的 rpcx-v1 语义**，不是这三个上游项目原有超时的事实。

这是待首个样本验证的接口方案。代价是适配分析器的调用签名及可信探针，并新增 L2 规范；不能直接套用固定 demo-orders 的测试/请求规则。旧 `v0.2.0` 规范和冻结夹具不修改。L2 规范、数据、宿主 Profile 各自发布新身份，不能仅换目录或删除基线 pin。

### 准备不等于迁移

每个样本保留三层关系：固定上游 U → 可离线业务切片/植入 v1 的基线 B → Agent 迁移候选 C。U→B 是人工数据准备，不计为 Agent 成绩；B→C 才是评测任务。先记录 U 的原测试/断言清单，完成 B 的保真复核及全部必需配置基线，再冻结 B，之后才制作正确/错误/未知对照和运行 Agent。不能从正确候选反向生成基线。

保真范围是保留的业务规则、参数/响应映射、错误与副作用顺序；替换传输所引入的超时、取消和连接行为变化要列为明确的植入差异。U 与 B 不承诺完整行为等价，尤其不能将新增的 30 秒约束说成原服务契约。

准备记录至少包含：上游 commit 与许可、保留/修改/重命名/排除/新增文件映射、逐项裁剪原因、原测试与子例身份、断言变动说明、模块和依赖版本、离线材料摘要、构建环境、所有必需配置及运行证据。新增适配器测试与原测试分列。裁掉的功能不能算覆盖；业务断言改变必须单独解释，单纯测试名集合不够。

### 运行前仍需解决的工程问题

| 现状 | 接入要求与验证 |
| --- | --- |
| 当前 Profile 仅接受两份 demo-orders 固定输入 | 新样本注册新的宿主 Profile 与业务检查材料；正反例验证前不得以旧 Profile 放行 |
| Runner 只有单一 build_config；分析请求虽有 Tags，不代表端到端支持矩阵 | translation 的两种必需配置必须绑定同一候选、分别保存证据，缺一种不得放行；报告和指标按仓库计一次 |
| 当前 SDK 调用形状与新增响应参数不同 | 先对新签名验证类型身份、ctx/deadline 和完整性检查；保留旧签名的 L1 回归 |
| 上游测试依赖 testify/gomock、日志/追踪等模块；当前执行器断网且 `-mod=readonly` | 准备阶段固定并获取最小依赖闭包，优先验证只读预置模块缓存＋每 Run 独立可写构建缓存；不得依赖开发机缓存或执行时下载 |
| Workouts 需要 common 本地模块 | 作为有摘要的只读依赖提供；连同业务模块、两个 SDK 的相对路径在真实 Docker 下验证 |

依赖不直接复制成数十份本地 replace，也不为了绕过依赖重写 testify/gomock。整仓 vendor 会带入大量未用工具，且当前 `-mod=readonly` 不会自动变成 vendor 执行；先验证最小只读模块材料的装配成本。若现有执行/输入限制无法承载，单独记录执行材料方案取舍，再实现；不在本轮假定已有离线供应能力。材料大小、文件数与容器工具链必须实测后才能转为 ready。

## 6. 划分、留出与访问边界

开发样本固定为以上三个，同源组分别为 goddd、go-clean-template、wild-workouts。Go-kit shipping 与 GoDDD 同组；同一仓库的服务、tag 或 fork 不能拆到两侧。全部已查阅来源及版本写入清单的 surveyed_sources，后续不能悄悄将其改称开发者完全未见的样本。

留出名额 `l2-heldout-01` 状态为 `awaiting_independent_preparer`，source/group/commit/摘要均为空。它不计入已准备样本数，也不占正常迁移分母。用户已选择暂不安排独立准备者，本轮只固定准入条件：

1. 由未参与提示/门禁调优的人准备和保管；与已见来源及其派生工程不同组，有明确许可、固定版本与原业务测试。
2. 使用同一 L2 SDK 契约及已声明的支持边界；至少保留已有出站调用、可追踪的请求 ctx 来源和原业务错误/副作用检查。允许不同组合，不刻意选门禁容易通过的结构。
3. 独立准备者按相同流程做离线基线、裁剪保真与参考标准检查，保存完整材料和访问记录；开发侧仅接收任务标识、身份摘要、许可、环境要求等必要元数据。
4. 开发期间不读取留出源码、候选、结果或答案来调优；正式评测时再按协议向被测 Agent 提供必需输入。留出出错后若开放给开发调试，该版本转为已见，不继续报告严格未见成绩。

M4 冻结评测协议时必须复核这个依赖。如果仍无独立准备者，显式说明严格留出缺失；只有另行决定并如实标识，才可降级为固定外部验证集。不能把名额当样本、把计划摘要写成实际摘要，或用子代理冒充独立保管者。

本次选择清单记录的是来源选择版本，不是已冻结的可执行数据集。后续准备证据另存，选源/划分发生变化发布新的选择版本并保留原因；不覆盖本清单。迁移调试前冻结实际数据，沿用 [ADR-005](../adr/005-versioned-evaluation-data.md) 与 [ADR-007](../adr/007-host-owned-task-profiles.md) 的数据、工具和宿主配置边界。

## 7. 样本进入真实生成前的验收

每个开发样本至少需要已知正确、明确违规、证据不足三类候选；不能仅把所有复杂候选判为 NeedsAttention。用独立参考结果评估运行时门禁，oracle 与预期判定不进入 Agent 或门禁输入。各类对照属于验证器校准集，不混入真实 Agent 成功率分母。

| 验收对象 | 准备时要做的对照 | 必须观察到的证据 |
| --- | --- | --- |
| 输入可用与业务保真 | 原测试保留/排除映射、基线全部必需配置构建测试、独立离线复跑 | 基线通过；所选业务断言未削弱；断网且无宿主缓存仍可运行；基线失败时模型零调用 |
| 三个样本的共同 T3 | 漏超时、Background 兜底、父 deadline 更短、父 ctx 已取消、正常无 deadline | 调用点与规范条款关联；正确的 30 秒上限和取消传递可观测；不靠真实等待 30 秒作主要断言 |
| Goddd | 未知货物、正常路线、远端错误/取消；漏改接口装饰器 | 路线映射、零调用分支和错误返回行为保留；request ctx 传到后端；调用链遗漏不可放行 |
| Translation | WebAPI 失败不 Store；真实适配器漏超时但 mock 测试仍过；只迁移默认 tag；改生成 mock | 额外探针发现 mock 掩盖的错误；两配置各有证据；保护路径修改拒绝 |
| Workouts | 两类余额规则、无需余额分支、余额服务失败、教练服务失败 | 调用顺序/次数、正确请求参数和回调提交行为保留；每个实际调用都满足超时/取消；不制造回滚保证 |
| 未知与反作弊 | 超出当前可证明形态的 helper/间接调用；删子例、改断言、跳过必要检查 | 可确定违规按规则拒绝；无法证明保留 NeedsAttention 和具体缺口，不以编译或原测试通过代替证明 |

可信运行时探针与独立参考可以检查同一规范，但不能只用同一实现的同一个结果互相证明。独立参考应核对业务事件和截止时间，并结合人工规则复核；其准备成本也计入样本接入成本。

## 8. 实施顺序、停止条件与本轮核查

下一步先准备 **Goddd 单个样本的 U→B 和离线基线**，同时验证共用 L2 SDK。理由是它天然保留无 ctx 的多层接口与原测试，能最先揭示旧 demo 专用验证的接入成本；先不同时引入构建矩阵和多个业务模块。完成其保真/环境验收、冻结输入后，再接新 Profile 与三类候选。然后依次准备 translation 的配置矩阵、workouts 的回调及模块关系，最后汇入 Campaign 开发评测。
