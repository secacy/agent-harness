## 方案与实施边界

保留上游根领域文件、十个领域测试、booking 的五个业务测试与日志/指标装饰器、routing 接口、inmem/mock 和 HTTP booking 处理函数。裁剪 server 装配中的 tracking/handling/Prometheus，保留 booking 路由及错误编码；出站 HTTP/Hystrix 替换为本地 rpcx-v1，保留路线响应到 itinerary 的映射和远端失败返回空路线的行为。现存无 ctx 调用链保持迁移前状态。

源文件以固定 commit 的实际内容为依据。原样保留的源码（包括上游注释）不做翻译，以便字节复核；新写或替换部分使用中文注释、英文错误。逐文件映射注明保留/修改/排除/新增及原始/准备后摘要；业务测试原文件不改，不把裁掉的其他服务测试计为通过。

### 依赖材料的取舍

| 方案 | 当前 Goddd 的具体影响 | 本步选择 |
| --- | --- | --- |
| 删掉装饰器或用自写替身替换第三方库 | 可以零依赖，但失去需要传播 ctx 的真实层次，甚至改变 UUID 行为 | 不采用 |
| 将依赖 vendor 到业务仓库 | 容易与业务一起分发，但当前执行器固定 readonly 模式；未来迁移还要同步 v1/v2 的 vendor 内容 | 不采用 |
| 固定版本的独立模块缓存 | 保留原模块和源码、业务仓库不携带依赖源码修改；需要显式挂载和完整性清单 | 采用，先在已有 Executor 的宿主命令参数中显式设置 GOMODCACHE，不扩展通用执行 API |

先整理仅该切片需要的 go.mod，保留上游直接及间接版本。准备可联网获取模块，验证时 GOPROXY/GOSUMDB 关闭，使用独立空构建缓存和只读材料；不读取宿主模块缓存。选择清单里的模块缓存方案到本步才接受实际检验。模块源码必须带许可，准备材料有完整文件摘要；不把部分包源码冒充完整模块发布。

共用 SDK 延续已讨论的 `Call(method, request, response)` → `Call(ctx, method, request, response)`；v1 创建 30 秒上下文并释放，v2 直接传入调用者上下文，不隐式添加超时。response 为类型化响应指针，由内存后端填充，不实现序列化或强行终止忽略 ctx 的后端。SDK 自身测试覆盖请求/响应/错误、期限与取消；它们属于 SDK 契约验收，不是候选补丁 oracle。

保留的三个原测试文件字节完全一致：cargo_test.go、itinerary_test.go、booking/service_test.go，共 15 个测试。新增 routing 映射/失败/空响应测试和 HTTP booking 经两个装饰器到 RPC 的成功/未知货物/远端失败对照；Goddd 合计 22 项测试及子测试。SDK v1 的 5 项检查与 v2 的 10 项检查验证独立契约，未等待实际 30 秒到期；本步证明上下文期限的设置/释放，不宣称已做候选的真实到期验收。

依赖最终固定为 7 个上游已有版本：go-chi/chi、go-kit/kit、pborman/uuid、VividCortex/gohistogram、go-logfmt/logfmt、go-stack/stack、kr/logfmt。准备时首次 tidy 解析了较新间接版本，已恢复上游 go.mod/go.sum 中的版本；公共校验服务曾发生 EOF，使用固定上游已有校验和补齐，最终下载和离线复跑成功。没有因此升级业务依赖。kr/logfmt 的 MIT 许可在 Readme，按原件保存。

完整缓存包含 516 个文件、展开 4,783,818 字节，确定性归档压缩为 1,451,224 字节。选择完整模块内容加必要缓存元数据，避免把裁掉文件的模块伪称完整发布；代价是保留了 Go-kit 原包中未执行的 metrics/debug.test。每个模块源码、许可和缓存文件都有摘要。运行只执行 Go 工具与本次夹具测试，不执行依赖包的预编译测试文件。该材料由宿主在 Run 下展开和核对，不进入可写业务仓库，也不更改 Executor 的全局缓存/网络策略。

复验工具位于 [baseline](../../scenarios/rpcx/l2/baseline/verify.go)，通过现有 execution.Executor 启动 Go，不另建执行后端。默认 Docker，可信本地须显式选择；工作副本、模块材料和缓存按新 Run 创建。模块缓存由宿主通过命令前置 env 参数绑定绝对路径，Docker 挂载为 /workspace/modules；全部原始环境清理、断网与只读挂载仍由已有 Executor 负责。后续 Profile 如何承载这份宿主依赖材料尚需接入设计，不能把这次复验入口当成 Runner 已支持该仓库。

### 发现的问题与修正

首轮机制测试发现归档中的 go.mod 变成自动整理后的内容，与固定上游摘要不一致；触发改写的进程未确定。此前本地报告 `runs/rpcx-l2-baseline-1228437173/report.json` 虽显示 accepted=true，但旧入口只检查冻结字节和构建/测试，没有检查来源映射内部的一致性，因此不计为本次验收。报告保留原样，失败输出摘录见 `runs/m3-4-goddd-preparation/first-mechanism-failure.txt`。

修正为把审查原件存成 .txt，避免被当作活动 Go 模块；复验入口在执行任何代码之前额外校验原件摘要、交付文件摘要、保留/修改关系以及所有夹具的来源覆盖。新增回归确保原件改写即拒绝。首次冻结属于本次尚未提交的数据准备过程；最终发布只引用修正后的固定摘要，不回写已有报告或改变已提交的数据版本。

最后评审补充了终态保护：只有全部命令和证据检查完成后才允许 accepted；宿主 panic 仍向调用方传播，收尾报告必须保持未验收并写明中断。新增故障测试覆盖这一分支，最终本地与 Docker 都用更新后的工具完整复跑。
