## 3. 代码复核与问题清单

### R1：公共命令取证存在四份维护副本

四个 `evaluation.command` 分别位于 [Goddd](../../scenarios/rpcx/goddd/evaluate.go)、[Translation](../../scenarios/rpcx/translation/evaluate.go)、[Workouts](../../scenarios/rpcx/workouts/evaluate.go)、[GHCLI](../../scenarios/rpcx/ghcli/evaluate.go)。它们重复执行前快照、90 秒限制、Executor 调用、stdout/stderr 与 command 记录、资源异常及执行后漂移检查；相邻 `save/saveJSON` 又重复绑定与写入。

静态计数分别为 28、29、34、32 个物理行，共 123 行（含签名、空行，不是复杂度或工时）。Translation/GHCLI 显式合入 `ctx.Err()`，Goddd/Workouts 没有同一行。这是副本分化的实证，**不是已复现的错误放行**：[Local](../../internal/execution/local.go)和[Docker](../../internal/execution/docker.go)本身也返回取消错误；端到端后果需要针对触发时序验证。

保留的业务差异是必要的：Workouts 额外挂载 common，并避免重复 root；GHCLI 可以额外挂载可信材料；Translation 的不同配置在上层编排。共享实现应接受显式挂载/参数，不根据仓库名称猜配置。收益是公共错误路径只维护一次，而非声称能消除业务验证工作。

### R2：Runner 的接入选择分散，但尚不足以重建插件框架

[profile.go](../../scenarios/rpcx/runner/profile.go)选择 HostMaterials 校验，[run.go](../../scenarios/rpcx/runner/run.go)分别选择 Evaluate 与 PrepareBackend；[审计适配](../../scenarios/rpcx/runner/audit_evidence.go)另处理材料格式，GHCLI 还有观察消费。新增 Profile 要同步检查这些入口，存在漏接的维护风险。

当前全部属于 rpcx 宿主层。静态扫描 `internal/` 的 54 个非测试 Go 文件未发现直接导入项目 `scenarios/` 包；Campaign 的执行接口也不含 rpcx Evaluation。这支持主要边界仍成立，不能据此声称整个依赖图或所有运行语义已形式验证。暂保留显式选择；若下一次仓库接入仍需重复选择多处，可考虑小型静态注册表，暂不引入动态插件或规则 DSL。

### R3：证据维护义务容易遗漏，已修问题不再列待修

[GHCLI C 验收](2026-10-23-ghcli-runtime-response-design.md#10-单元-c预算工具交付与实际-campaign-审计)发现并修正了审计 Finding 未完整依赖消费日志/SDK 的问题；当前 [audit_behavior.go](../../scenarios/rpcx/runner/audit_behavior.go)已收集来源。它说明新证据需同时考虑写入、审核导航、只读消费与来源稳定性。下一项公共维护应复用这些验收义务，不重新制造一个通用证据框架，也不把已修缺陷重复算作新发现。

接入成本至少分为：来源裁剪/离线依赖、可信业务规则/原测试适配、Runner 与审计接线、故障和交付验证。当前已能定位这些工作的位置，但没有完整活动计时，因此本次不报“每仓库节省多少小时”。四个仓库也不足以证明接入成本随规模可控。

审核材料可定位、有完整链路，不等于审核更快。实际人类活动耗时仍未知，助手复核不能填成用户的人类计时。后续效果设计须同时记录成功、未知、错误归因和成本；缺少实际人员时可以完成工程复验，保留人员指标空缺。

## 4. 下一项选择：有限统一命令取证

当前目标排序是：保持已验收交付与可信性，降低跨场景机制维护分歧，然后获取新的效果/成本证据。

| 可行下一项 | 收益 | 当前代价与取舍 |
| --- | --- | --- |
| 继续扩展 GHCLI/helper 或 Translation 证明 | 可能减少特定形式的未知 | 缺少预先固定的覆盖收益依据，容易继续围绕已见候选开发；暂缓 |
| 立即追加模型评测 | 可观察当前版本的真实行为 | 不解决已经可见的机制副本，且新增消费；不是不能做，但不作为本次默认下一项 |
| 重建通用工作流/验证插件体系 | 潜在统一更多接入点 | 仍只有一个 SDK 领域，容易提前固化错误抽象；不选 |
| 统一四个场景的命令取证流程 | 一处维护取消、日志、绑定、漂移与设施失败处理，跨仓库收益明确 | 材料摘要会变，需要兼容与三类交付回归；选择这个有限单元 |

拟优先在已有 `scenarios/rpcx/gate` 中实现小型公共函数/记录器，复用 `execution.Executor` 和现有证据结构。尚未锁定具体 Go 签名：实现前核对依赖方向，禁止形成导入环。`internal/execution` 继续只执行命令，不承担 rpcx 报告格式。场景负责显式参数、挂载、命令名称和检查结论；共用代码负责执行记录与证据。业务探针、AST 支持范围、Policy 和冻结数据不随此工作扩展。

第一步先以受控后端固定取消/设施异常的预期行为；若能复现误判，单独说明触发条件和修复，不用“纯重构”掩盖行为变化。然后迁移四个场景，最后完成下面的契约验收，作为一个完整工作单元提交。

| 完成条件 | 计划验证 |
| --- | --- |
| 公共错误语义只有一个实现 | 四场景均调用同一取证流程；成功、非零业务退出、取消/超时、OOM/输出限额、保存失败、输入漂移的机制对照；业务非零退出仍可被上层归因，设施错误不得产生质量成功 |

| 交付和历史消费兼容 | 受影响场景的正/反/未知对照，代表性真实 Docker 交付与离线审计；旧冻结归档只读消费仍通过；材料哈希随新代码变化，旧报告不改 |

### 依赖与接口选择

在已有 `gate` 包新增 [Recorder](../../scenarios/rpcx/gate/command.go)，由每次 Evaluate 独占使用，引用同一报告的 Commands/Evidence 切片。它负责 Save/SaveJSON 和 Run；场景继续明确提供命令、工作目录、挂载与缓存。这样四个场景无需各自维护日志保存和错误分支，也不需要把整个 evaluation 类型统一。

公共记录器需要命令的 JSON 类型。让 gate 导入 checks 会使场景共用文件工具依赖完整验证入口，因此把原 Command 结构移到 gate，`checks.Command` 保留为类型别名。JSON 字段与旧调用方式相同，现有 M1/T3 仅使用该类型别名，执行路径未迁移。没有新增接口插件；Run 接受的执行器仍是现有 Executor 加 Environment 方法，兼容已使用的 ModuleBackend。

材料保存仍使用已有缩进 JSON、末尾换行、文件路径、证据 ID 与 Spec/基线/候选绑定。公共源码通过既有 gate.Materials 进入四个场景的新工具摘要，旧输入、规范、Profile 和独立参考保持；审计根据归档材料核对原身份，不要求它等于当前源码摘要。

### 行为边界

业务非零退出原样返回，由具体检查归因；负退出码、OOM、输出超限、执行器错误、证据写入失败或挂载输入漂移返回 error。保存多个产物时保留所有错误，成功写入的诊断证据仍可引用；不得因一项失败把部分材料说成完整交付。

统一后的流程在执行前检查 context，且执行器返回后显式合入 context 错误。Goddd/Workouts 此前依赖后端返回取消错误，现在和其余场景一致；取消后仍保存已返回的输出并核对输入。受控后端可复现“取消后返回成功结果/nil”的局部触发条件，新公共实现返回取消错误；这验证接口行为，不声称已复现旧生产门禁错误放行。90 秒命令上限、四种场景挂载选择及上层质量规则保持既定含义。
