## 具体取舍

原 usecase 和接口已有 ctx，原翻译测试通过生成 mock 绕过真实出站实现；保留它们才能检验“业务测试通过但 SDK 语义遗漏”。不为了让迁移更难而删除 ctx，也不把 mock 移到不参与编译的位置。原 mock 同时包含 Task/User 接口，故保留原 repo/usecase contracts 及所需 entity 类型，连同实体已有测试；不重生成或裁掉 mock 的部分方法。无关服务实现、数据库与消息系统不纳入切片，逐文件标明损失的覆盖。

| 问题 | 可行选择及本样本的得失 | 选择与代价 |
| --- | --- | --- |
| tracing 闭包 | 删除包装可少装依赖，但改变 usecase 与 WebAPI 的真实调用层次；引入完整 OTLP 启动器又会增加外部服务闭包 | 保留两层原 tracing 包装与原版本 otel 依赖；不装配未被切片调用的 exporter 启动代码。接受固定依赖与许可准备成本 |
| 第二配置 | 两个 tag 指向同一函数无法检验遗漏；整仓另找天然配置会偏离已选样本；独立互斥出站实现需额外维护 | 保留默认适配器路径，植入 rpcx_alternate 文件，各自直接调用 rpcx。固定预期活动/忽略源文件，并用 go list 实际核对；同源变体仍只计一个样本 |
| 基线工具 | 复制 Goddd 复验程序最快，但来源、归档和事件检查会分叉；通用插件/命令 DSL 超出两份数据的需求 | 在现有 baseline 包增加静态数据描述和配置列表，复用认证/归档/执行/事件核对；旧 Verify 保留 Goddd 默认，新增按发布版本选择的入口。不将此准备接口当作 Runtime 已支持构建矩阵 |

业务切片保持翻译请求到结果映射、原 ctx 预检查、错误链，以及 usecase 的“远端成功才 Store”。两种配置必须执行同一组原测试和实际适配器测试，不用 tag 排除原测试。第二实现及 30 秒默认超时均为植入条件，不宣称是原上游的自然依赖或配置。

## 实施与验收计划

1. 固定来源 d1f46523e9a8435713aabb70222c6189564d4501；原文件存为审查用 .txt，原业务测试、生成 mock 和保留文件逐字节认证。与先前选择材料的摘要对照。
2. 复制共用 rpcx-l2-sdk-v1，字节不变；两个 RPC 适配器均处于 v1 基线。整理仅保留切片所需的 go.mod，保留 Go 1.26.0 及上游依赖版本，不引入自写第三方替身。
3. 新增实际 RPC 路径测试验证映射、错误与存储顺序，并验证原取消预检查；明确 v1 并不向后端传播请求 ctx。两个配置分别核对 go list 的活动/忽略文件、构建、原测试和新增测试完整事件。
4. 来源补丁能从审查原件重放成基线；依赖完整模块/许可/校验和独立归档。正式复验关闭代理和自动工具链下载、空构建缓存，Docker 再证明断网和只读挂载；前后材料不变，记录容器并核对回收。
5. 缺配置、错误活动文件、缺/跳过测试、失败命令或输入漂移都不得 accepted；旧 Goddd 基线工具继续回归。一个可验收工作提交，不按文件拆小提交。

尚无迁移规范、候选补丁、可信运行时门禁或独立 oracle。双配置基线通过后才进入新 Profile/门禁的设计，不能把本步测试结果记成模型自动成功率。

## 实际实现与材料

发布 [rpcx-l2-translation-v1](../../scenarios/rpcx/l2/data/rpcx-l2-translation-v1/README.md)，52 份受清单保护的材料，加 freeze.json 共 53 个文件；freeze SHA-256 为 `d1e0e20608fed9e45212a6fb5010834028ab82228573a391c78a1500f7be8bdd`。业务基线有 20 份文件：14 份原样保留、3 份修改、3 份新增；共用 SDK 八份文件逐字节复制，原选择清单、Goddd 数据和历史报告不变。原件逐一核对 Git blob 身份；选择阶段已查阅的六份文件也与原 SHA-256 一致。

原翻译测试保持完整，两位顶层测试及五个子例；原实体测试再提供八项，合计 15 个原测试及子测试。生成 mocks_repo_test.go 保留原字节，实际被原翻译测试调用。新增 11 项边界测试/子测试，检查已选实现标识、请求/响应、v1 期限设置与返回释放、取消/过期前置拒绝、可解包错误，以及真实 usecase→tracing→RPC→Store 的顺序。每配置固定 26 项，两个配置是同一来源的一次配置矩阵；SDK 的 5/10 项各执行一次，因此配置化执行计数为 `26×2+5+10=67`，不能把它们称为 67 个独立业务任务。

默认 translation_google.go 和 rpcx_alternate 文件各自直接 Call，互斥标签只选择其中一个；一个用局部值响应，一个用指针响应与独立请求变量。没有把两个标签都接到相同的唯一 RPC helper。原两层 tracing 包装不改写，用例已有 ctx 也保留，准备只更换出站传输/构造器并增补测试。

### 依赖范围的实测调整

完整选中模块图的源码约 44.6 MB，超过现有 32 MiB 展开上限。直接提高通用上限会扩大所有输入的资源承诺；裁掉 otel 模块里未用的语义约定版本又会把局部包源码冒称完整模块。最终用两个配置的 `go list -deps -test` 合集确定实际代码闭包：分发 10 个完整模块，其余 13 个模块只提供图元信息及许可，`source_included=false` 明示差别。保留实际构建依赖在上游 go.mod 中的版本；未使用的工具依赖不作为切片代码闭包。缓存保留各模块图所需的 .mod/.info/.ziphash，不能据此声称整个工具链也能离线编译。

归档包含 1,313 份实际文件、展开 31,455,065 字节、压缩 4,137,641 字节，所有源码/元信息/许可证均有摘要，保持既有 8 MiB 单文件、32 MiB 总量和归档路径约束。准备阶段允许从公共代理下载，正式执行使用独立装配的只读缓存与空构建缓存，不使用宿主模块缓存；原 OTLP exporter 初始化器仅作为审查原件保留，不参与构建。

### 准备工具的落实

现有 `Verify` 仍以 Goddd 为默认；新增 `VerifyVersion` 和 `-dataset`，只选择宿主静态发布列表。配置列表、活动/忽略的 RPC 文件、原 mock 的选择均由宿主确定，原数据里的 expected/oracle 不参与。Go list 的包输出、构建和完整测试事件分别保存，任何必需配置失败都会终止且 accepted=false。

发布版本同时固定 freeze.json 摘要，既验证内容完整，也拒绝“改内容后重算同名清单”；这沿用 [ADR-005](../adr/005-versioned-evaluation-data.md) 的版本边界，不另建准备工作流 DSL。最后核查补上命令返回后的 context 状态：即使受控替身忽略取消并返回 0，也不能将取消后的矩阵算为通过。最终本地/Docker 正式复验均使用这一版工具。
