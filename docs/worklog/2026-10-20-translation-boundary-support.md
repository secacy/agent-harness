## 2. 为什么先处理类型边界

优先保证证明强度和边界可解释，再考虑减少人工确认；复用已有能力排在这两者之后。仅先改诊断文字最容易，却不会暴露较难的期限/准备关系；先做结构归约而没有类型边界，则容易不得不按名字猜 ctx 绑定，或凭行为通过跳过未知。

因此先解决有独立价值的类型边界：SDK 调用、父 ctx、派生变量、cancel、常量和原始位置仍由隔离的 go/types 分析证明。此单元完成后可交付新的有限分析能力，即使场景结构与测试还为 unknown，也不应临时放宽它们。

这不是把多条微小函数拆成提交。计划两个完整工作单元：第一项交付带协议验证和隔离对照的类型边界；第二项交付场景结构/测试证据及完整双配置校准。每项实现与验收作为整体提交。

## 3. 类型边界的方案选择

| 方案 | 在当前目标上的具体得失 | 选择 |
| --- | --- | --- |
| 所有前置准备继续 unknown | 不新增分析复杂度，但当前简单请求/响应构造仍需人工确认 | 保留为超出新边界时的默认结果 |
| 往后搜索任意 WithTimeout，直接复用 pureLocal 跳过前面语句 | 改动少，但现有 pureLocal 是派生之后的局部构造筛选，会接受动态索引、指针字段读取等形态，不能冒充超时前任意表达式的充分证明 | 不采用 |
| 仅在宿主 AST 中移动 WithTimeout，再把改写副本交给 Inspect | 复用现有规则，但分析事实描述的是另一个程序；将隐藏定时器的实际位置与前置操作 | 不采用，分析和执行始终使用原字节 |
| 在 Translation 自行重复 SDK/ctx/常量的名称与绑定判断 | 少改共享模块，但会复制类型规则，并可能按 rpcCtx 等名字放行 | 不采用，沿用现有类型身份职责 |
| 任意纯度分析、CFG/SSA 与跨函数摘要 | 支持面广，但对 helper、动态分支和可能阻塞的操作承担新的证明责任 | 暂缓；当前两个直接边界不需要这部分复杂度 |
| 在 worker 内增加按对象绑定的受限准备语句，保留原直线边界 | 直接解释原程序，可复用类型加载和派生/释放检查；代价是支持语法很窄，需承担共享规则回归与协议更新 | 首单元采用 |

这里选择的是受限语法及对象关系，不将“没有普通函数调用”当成一般无副作用证明。若后续主要需求变成指针、集合索引、helper 或分支，先评估收益，再重选分析方法，不继续堆名字例外。

## 4. 首单元的支持契约

### 4.1 原有条件继续必需

仅扩展真实 v2 SDK 的直接四参数 Call。保留既有类型认证的可选 ctx.Err 提前返回；随后允许零至两条受支持准备语句，再接标准库 WithTimeout、对应 defer cancel 和原直接 RPC/结果处理形态。

父 ctx 必须是本函数 context.Context 参数，RPC 实参必须是派生的同一 Go 对象；同一 cancel 对象的 defer、30 秒常量求值、非间接/动态调用和实参效果限制继续必需。提前取消、重绑、错误父 ctx、helper、额外分支及未覆盖调用不能被准备语句规则吞掉。已确认的错误时长仍为 violation，不能退成 unknown。

### 4.2 准备语句只覆盖请求和响应

每条只能声明一个新的、非空白局部变量，使用 types.Info.Defs 确认新声明，不接受赋值/重绑定。每个对象只能声明一次，且必须直接对应本次 RPC 的请求标识符、响应标识符或取址响应；不能仅因语句形态安全就跳过任意不相关变量。两个角色的声明数给出最多两条的自然边界，不设置任意可调扫描长度。

允许的构造：

- `var response T`：无初始化值，T 为下面限定的结构体。
- `request := T{Field: value, ...}`：带字段名的结构体字面量；value 仅为类型检查已求值的常量，或本函数按值结构体参数的直接字段读取。
- `response := new(T)`：new 必须绑定 Go 内建对象，参数为类型表达式；不接受同名用户函数、别名 allocator 或任意工厂函数。

T 的底层类型须为非嵌入、字段均为布尔/数值/字符串基本类型的平坦结构体；允许命名基本字段类型。参数字段读取也限定为此类按值结构体，FieldVal 选择无隐式指针解引用、无嵌入路径；不从全局或其他局部对象取值。

不接受 map/slice/channel/interface/指针字段结构、动态索引、解引用、用户调用、闭包、接收、类型转换、无字段名的字面量、多声明、有初始化值的 var、额外 defer/go/控制流。它们不一定错误，但不在新自动证明范围。new 允许分配，不承诺耗时为零；候选计时器保持原位置，不据此声称任意前置准备都无耗时或与移动定时器等价。

### 4.3 与后续 RPC 的组合

分析器须同时检查：前置声明的对象关系、原位置的派生/释放、以及从派生到 RPC 的既有直线路径。响应可能已在派生前声明，不能继续要求它只在派生后出现；实现中可构造只读语句视图复用响应声明与控制流检查，但不得修改 AST 的原位置、重新排列待分析源码或放宽实参/取消检查。

原先派生后支持的局部构造不因本工作自动获得“派生前许可”。新语法检查独立于现有 pureLocal；旧路径不借这次扩展扩大到任意前缀。

## 5. 实现位置、协议与失败行为

主要修改 analysis/worker/rules.go；从已有 boundary 分解识别派生位置、有限准备与对象关系，继续复用标准库函数身份、父参数、派生/取消和常量检查。不是新增场景插件或可由候选控制的放宽开关。

拟保留 Call 结构与 schema 字段，新增明确的 covered 原因 `prepared_local_timeout_boundary`，原 `direct_timeout_boundary` 继续表示旧形式。宿主 inspect.go 的 validateFacts 必须同步只接受这两个已知原因，并继续约束 SDK、direct、30 秒、输入/工具摘要、活动文件和配置。不能删除原因校验以兼容新结果。未知和 violation 仍遵循原事实/Gap 及质量优先级；协议不一致、输入漂移、执行/保存错误仍失败封闭，不能产生可用通过结论。

新理由标明使用了哪种有限证明；原始源码行、整个模块/SDK 摘要、实际 worker 材料与命令仍保存。首单元不增加跨函数绑定对象序列化协议，也不扩大 worker 的文件/工具可见范围。是否需要更细的准备节点证据，在场景范围证明单元内按原文件位置生成，并绑定同一类型报告，不把 Go 内存对象地址当成可持久化身份。

这一选择延续 [ADR-003](../adr/003-typed-migration-analysis.md) 的类型身份与有限证明、[ADR-004](../adr/004-analysis-execution-boundary.md) 的隔离分析边界，不另建 ADR 重述它们。若实现需要跨进程对象摘要或一般效果分析，再单独比较长期技术选择。

## 6. 其余两类缺口的后续方向

以下是已选择的职责方向，详细节点/发布实现仍需第二单元的原型和边界测试；不能作为当前已支持行为。

### 6.1 场景生产范围

沿用 Goddd 的“局部事实＋完整剩余比较”，但不直接复制其整文件规则。Translation 存在共享常量、不同局部变量及两个互斥配置，所需条件不同：

1. 只有固定两个 adapter 方法和共享 translation_types.go 获得新归约。共享常量为全新未导出名，单个 `30 * time.Second` 声明；全部生产快照中只对应声明及两个 adapter 的期限参数三处，两个活动配置各自证实真实绑定和值。不能因为当前配置未激活另一文件，就忽略其结构或引用。
2. 只有在同一候选/工具/配置的类型报告覆盖该 SDK 调用后，才将该次 RPC 的指定派生实参节点映射回宿主适配的原 ctx；只移除该对派生/defer。新的局部名字须满足受限声明与用途，其他同名节点不能作字符串替换。
3. 只在比较副本消去已解释常量及其单独需要的新增 time 导入；保留其他导入、adapterVariant、请求/响应、错误链、取消 guard、tracing 和全部剩余声明。类型事实不代替完整业务结构比较。
4. 先提取并核对语义指令的内容、顺序和关联位置，再忽略普通注释。两个包前 build tag 必须保持既有配置语义；新增/移动 go 指令、line/export 等不能按普通文案差异消失。

预计将新范围判定放在配置分析之后，保留经 Inspect 认证的候选报告供其消费，避免从名字自行补造类型结论。旧模板直接匹配仍保留，缺类型证据的新归约为 unknown，不因另一配置通过而放行。实现前验证这种阶段顺序不使构建失败/blocked 丢失范围诊断。

新场景证据须分列每配置的类型报告引用、原文件/节点摘要、局部事实和完整剩余指纹；候选摘要始终来自原字节。不得把归约结果写成读取候选前已生成的原始期望模板。

### 6.2 原测试诊断

选择宿主从认证基线生成两份完整测试适配：原提示，以及限定失败分支中的固定新提示。仅在 TestTranslationRoundTrip 的期限判断分支，替换无参数副作用的单个字符串字面量；条件、Fatal 接收者/退出方式、调用、其他字符串与整个原声明都保持。

理由是整份固定变体可复用既有 CompareAdapted，并保留原候选测试摘要；无须让共享 testintegrity 忽略所有 Fatal/Errorf 字符串。相比“任意文字只影响诊断”的宽规则，接受更多无害提示仍为 unknown 的代价。两份完整报告不得拼凑通过，明确删除/Skip 不得被另一个变体掩盖；选中 adapted-tests 与可信执行必须一致。

此处先固定具体宿主适配，再运行测试比较，不由原候选文字反向生成期望。这个选择解释的是已见诊断差异，不能把任意断言改动改称提示变化；TEST-001 原约束不放宽。

## 7. 最小原型的实际结果

材料在 runs/translation-boundary-design-01/：独立编写的 probe/preparation.go 与 preparation_test.go 只解析、类型检查构造程序并检查有限准备语法/对象关系，不调用 SDK、Inspect 或质量聚合，不执行候选 init/业务/测试，也不运行 Docker 或真实模型。

21 项语法对照为 5 项许可、16 项拒绝；7 项角色对照为 4 项许可、3 项拒绝，共 28 个对照、30 项测试及子测试通过。包含真实候选使用的字段字面量、new、零值声明，以及 helper、指针字段、动态索引、接收、全局读取、方法、转换、闭包、无字段名字面量、非平坦响应和重绑定反例。刻意保留“任意安全形状局部声明”的语法正例，再由角色检查拒绝不相关前缀，证明不能只依赖第一层语法筛选。

结果见 preparation-results.json 与 probe-final.jsonl；probe-first.jsonl 是增加角色检查前的通过轮次，不能重复计数。原型尚未实现 boundary 组合、SDK 识别、实际加载器、covered 原因协议或双配置查询，不能声称上述整体分析已完成；同名 new、嵌入字段等更多边界仍属于生产实现的必测项。

## 8. 实现顺序与可测验收

| 工作单元 | 可审查交付 | 停在这里得到什么 |
| --- | --- | --- |
| 首先：受限准备语句的类型边界 | worker 对象/位置证明、严格宿主协议、新旧形态与错误/未知对照、实际双配置 Inspect | 能解释原位置的直接 RPC 期限边界；场景结构和测试未知仍保留，不据此交付新的整体放行结论 |
| 随后：Translation 场景结构与测试证据 | 常量/绑定/指令与完整剩余比较、固定诊断变体、原字节证据、完整双配置 Evaluate 与 Docker 校准 | 在声明范围内区分可审核、违规和证据不足；原样候选只有全部必需检查通过时才可能放行 |

首单元的实施验收必须包括：

- 旧直接形态、请求/响应分别或同时在派生前的正例；常量在共享文件、导入别名及合法不同局部名字仍按对象判断。
- 角色/声明/字段边界反例：无关局部、重绑定、多对象、shadowed new、指针/嵌入/全局/索引/接收/函数调用、额外流程；不按 WithTimeout 名称扫描后跳过。
- 同一受支持前缀下，5 秒仍 violation；错误父 ctx、错 RPC ctx、缺/错 defer、提前取消、额外 cancel 使用、helper/动态调用仍不 covered。保留原原因语义或逐项说明新增原因，不静默修改冻结预期。
- validateFacts 接受真实新理由，拒绝伪造的 SDK/kind/时长/理由/位置与未绑定材料；不能只测 worker 然后把宿主校验关闭。
- 使用实际隔离 Inspect 在原样候选副本分别查询 default、rpcx_alternate，绑定相同模块、SDK、工具及标签，记录活动/互斥文件；不移动候选源码来取得覆盖。这里的成功只指分析事实充分，不生成整体质量成功数字。
- 共享规则的原 worker/Inspect/调用对应回归及既有 T3/L1、Goddd、Workouts、Translation 校准按影响验证；旧已知违规不得放行，既有未知不得无解释改变。真实 Docker 至少覆盖新正例、错误时长与越界前缀，核对输入不变和回收。

第二单元还需完整七项冻结 Translation 校准、两配置逐项检查、新结构/诊断正反例、被隐藏修改与材料发布故障，以及不受新规则覆盖的 mapping-helper 对照。需要实际到期的完整 Evaluate 按现有契约执行；本轮设计不预填这些结果。

**停止条件：**准备语法不断扩张才能表达普通请求，或新理由不能与原位置/配置可靠绑定时，先缩小支持范围；出现旧假成功被放行时先修证明，不能靠把 scope/test unknown 暂时忽略完成整体验收。

## 9. 身份与完成边界

本轮没有生产 Go 修改、可用新命令、Profile 重签或规范变更；不更新原三仓实验成功率，不补填人类复核。后续实现使用新的工具材料摘要，已发布 Profile 字段若要改动则另起 ID，沿用 [ADR-007](../adr/007-host-owned-task-profiles.md)。原独立留出依赖和 M3 总体验收仍未完成。

下一步实施并验收首单元的完整类型边界，不先提交零散 helper 或依赖未经验证的新范围给整个 Translation 放行。

本轮收尾核对：原 default 类型报告确认为 covered / direct_timeout_boundary / 30 秒，alternate 仍为 unknown / unsupported_timeout_shape；仅消费已保存报告，没有重新运行 Inspect。当前 Campaign 的 6141 份文件与本轮开始快照完全一致，冻结输入、规范、Profile、共享/场景 Go 规则和原协议均未变。四份文档的 104 个本地链接目标、代码围栏及 git diff --check 通过；材料和原型身份保存于 runs/translation-boundary-design-01/verification.json。未运行项目 Go 回归、Docker 或新的质量判定，它们属于后续实现验收。
