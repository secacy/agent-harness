# M4.2c：激活检查点与受控完整重跑

- 日期：2026-10-21。
- 状态：单代受控完整重跑在下述范围验收；再次中断后阻塞，未实现连续多代恢复。
- 前置：[M4.2b 检查点](2026-10-20-m4-recovery.md#11-m42b恢复控制检查点)。

## 目标与边界

在原 Campaign 写锁内，读取已提交检查点，继承两级累计账目，为显式选择的未完成 Target 分配新 Run，从原固定输入重新构建、生成和独立验证。完整交付的 Rejected/NeedsAttention 不自动重跑。原控制、检查点与 Run 不覆盖。

本轮使用受控模型，不读取 .env、不发真实供应商请求。通用残留资源清理、付费恢复、连续多代恢复不在范围。若新的恢复执行再次中断，首版只审计并阻塞，不把重入当作又一次执行许可。

## 实现前取舍

| 问题 | 备选方案及代价 | 选择与理由 |
| --- | --- | --- |
| 活跃状态放哪里 | 原地升级根控制会破坏检查点来源；另起全新 Campaign 容易重置额度；原 Campaign 下单独执行代次需明确双层状态 | 使用 recoveries/execution 的单代状态及累计 budget v2，旧根继续描述原尝试。审计分别描述旧根和恢复执行，不混写两者 |
| 谁允许重跑 | 恢复调用时指定次数/时限最方便，但会扩展原授权；首次计划冻结会要求新实验重新建批 | 新计划可选 RecoveryPolicy，冻结 MaxAttempts（包括首次）及绝对 GenerationDeadline；缺省只允许原尝试，旧批次不能后补权限 |
| 再次中断怎么办 | 完整多代调度需要新事务、在途转换和代次链；直接重复执行会双花和覆盖 | 首版每检查点只激活一次，先持久化全部选择和 Run 收据，再调用执行函数；有收据而无完成结果时拒绝重复执行。允许只读重入已完成结果，不自动补跑 |
| 恢复并发 | 复制调度器容易形成两套故障语义；立即重构现有首次调度影响面大 | 本代显式选择串行执行，复用 Campaign 的 Execute、结果核验及共享执行槽。串行仍满足原并发上限，接受恢复吞吐较低 |
| 冻结输入来源 | 用旧候选续跑违背完整重跑；回退旧副本需额外认证与路径映射 | 首版继续使用计划中的固定输入，Runner 重新认证全部摘要；来源缺失则失败，不拿旧候选替代 |

## 契约与验收

激活前必须重新取得原锁、核对计划与检查点、验证资源静止，检查原 Policy、选择、尝试次数和截止时间。所用模型必须重新经可信宿主核实，Profile 与原预算一致；该回调不是付费授权替代品。原计划无 Policy、已过期、次数耗尽、完整已交付 Target、重复/未知选择均拒绝，零生成。

执行先落盘不可变 activation.json（含检查点 pin、选择、预分配 Run ID、ordinal、前驱）、再创建继承预算、再发布 started 标记，最后才调用宿主执行函数。启动后不重开账本或重复执行。中断后仍可审计：没有 started 是准备残片；有 started、没有 result 是执行中断；result 仅在核验新 Run 终态、报告和账本绑定后发布。所有发布在同一原 Campaign 锁内，错误或不确定写入立即停止。

预算转换不退未知占用，新调用继续按原 Q 预留。截止时间同时约束执行 context 和模型准入；重启不延后。新 Run 使用收据 ID 独占创建目录，旧 Run 不能再次绑定生成。审计核对预算继承前缀、所有新调用的 Run 收据、历史与当前 Run 关系，并独立调用场景 Inspector。

验收包括：两级预算继承与不足零请求、一次尝试/过期/选择错误拒绝、旧成果不变、已完成重入零请求、激活发布失败或强杀不重复执行、真实 rpcx 子进程强杀后新 Run 完整交付、仅采纳终态零生成、旧 CLI/审计和首次运行回归。测试输出保存在 runs/m4-rerun-01，不将替身用量作为供应商账单或迁移成功率。

## 实际实现

[recovery.Execute](../../internal/recovery/execute.go)复用同锁检查，要求已提交检查点，并校验原计划的次数、期限、显式选择及下一请求余额。完整已交付 Target 拒绝重跑；无尝试权限仍可用显式空列表采纳现有终态，不创建模型或运行账本。模型工厂只创建状态，VerifyModel 是可信宿主重新核实原配置的接口；没有该回调拒绝生成，本轮仅注入受控模型验证，不发能力查询或生成请求。

激活时发布固定收据和检查点引用，再由 [budget.Activate](../../internal/budget/activate.go)独占创建继承账本，持久化绑定后发布 started；后续只调用原 Campaign.Execute，并复用 CheckAttempt 的磁盘终态/报告核验。恢复串行执行，但仍共用原 K 限制的 Executor。Config.RunID 由 rpcx 独占建目录，默认首次 Run 自动分配身份不变；所有新 Run 从原认证输入准备，未使用旧候选。账本、模型 context 与首次 Campaign context 均遵守原绝对期限，父取消仍保留结果并返回错误。

恢复记录独立于 Campaign v2 和 Run v2，根控制与检查点不覆盖；Plan.Recovery 为可选首建字段，缺省不授予第二次尝试。budget v2 保留所有旧调用、拒绝、RunIDs、已知/未知占用及两级上限，新增调用继续 C+O 预留；commit 增加 revision 溢出拒绝，不能写负版本后继续生成。新结果中的费用已经累计旧费用，不应与根账本再次相加。

分配后无结果时返回 ErrInterrupted；目录初始化残片同样保守阻塞，不打开已有账本。相同选择且已有完整结果时，在新一轮完整审计后只读返回，不调用模型工厂、VerifyModel 或 Execute；不同选择冲突。该限制牺牲恢复自身再次失败后的可用性，换取本单元无重复执行，不能称为多代恢复已完成。发布/后审计可能失败，调用方必须同时看 error、Result 与来源材料，不凭 result 文件存在宣布成功。

[审计 v4](../../internal/audit/README.md#恢复执行代次)重新推导收据和权限，检查旧调用前缀、预算累计、Run 绑定、新请求时间窗口、发布顺序、新 Run 身份/终态及原场景 Inspector 证据。依赖账本损坏时先阻断后续检查，避免无效切片导致审计 panic。原 execution_state 保持历史，另输出 recovery_execution_state；一致性不足时后者为 unknown。CLI 和 audit.md 展示两项，既有归档不回写。
