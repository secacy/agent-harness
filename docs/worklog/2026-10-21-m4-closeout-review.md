## 1. 本步目标与取舍

此前各单元分别验收，交付入口仍有“恢复、清理待实现”的旧描述。继续扩展执行机制会使交付边界越来越难说明；仅把模块通过相加，又会遗漏里程碑原本要求的故障窗口和评测材料。

本步对照原验收条件核查历史证据，整理当前可交付范围、剩余工作和正式评测草案。不修改原验收标准，不重跑模型，不把历史测试计为本轮新测试。

| 方案 | 对当前目标的影响 | 本次选择 |
| --- | --- | --- |
| 按模块通过宣布 M4 完成并进入 M5 | 推进最快，但缺少引擎故障实测、部分持久化窗口及实际留出，无法支撑总体验收 | 不采用 |
| 等留出准备完成后再做所有收尾 | 保持完整冻结的含义，但把可独立完成的故障核对和交付说明也一起阻塞 | 不采用 |
| 先核对工程证据并确定协议草案，材料齐备后整体冻结 | 能交付现有工程能力且不虚构评测有效性；代价是草案和冻结版必须明确区分 | 采用；本轮只完成核对和草案，冻结门仍关闭 |

## 3. 当前能够交付什么

新计划在首次执行前声明恢复权限、绝对期限和 Docker 资源协议。中断后，取得原锁，审计固定输入及账目，精确核对并清理所属容器，重新实时确认静止，再提交检查点、继承累计预算，为明确选择的未完成 Target 新建 Run。原控制和候选保留；任何无法证明的创建状态阻塞恢复。

这条链已有真实 Docker 宿主强杀和受控模型的新 Run 交付证据。它是工程可靠性证据，不是供应商付费恢复或模型迁移效果实验。默认一次尝试的旧批次不能事后添加恢复权限；旧 v1 只读审计。恢复自身再次中断、未知创建、任意 Local 后代、掉电保证及 Linux 实机执行仍不在已验收范围。Linux 只有交叉编译证据。

M3 三仓原实验保持 Completed / NeedsAttention，S/N=0/3、A=0、错误放行率无定义；81 次准入、1,060,890 已知 Token。后续开发校准、M4 的脚本候选与故障试验都不能改计原效果数据。M3 A6/A7 仍部分满足，本次不是 M3 正式移交。
