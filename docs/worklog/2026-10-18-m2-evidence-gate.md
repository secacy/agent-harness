# M2：证据驱动的判定设计

- 日期：2026-10-18
- 状态：M2 在冻结 rpcx 场景与声明配置内已验收（2026-10-19）；收尾依据及 M3 移交见第 25 节。
- 对应里程碑：[M2](../MILESTONES.md#m2证据驱动的判定)

## 1. 当前缺口与本次交付

已有 [v0.1.0 规范](../../scenarios/rpcx/specs/v0.1.0.md) 明确不包含默认超时，[v1 SDK](../../scenarios/rpcx/fixtures/rpcx-v1/client.go) 的 Call 直接使用 Background；不能把它解释成已经包含 T3。当前 [Evaluate](../../scenarios/rpcx/checks/evaluate.go) 绑定该规范摘要，检查依赖、保护路径、构建、业务测试、测试保留与 context 传播。

现有不足：

- Check 只有 status/detail，没有稳定的条款、位置、覆盖缺口及证据引用结构。
- 测试名保留且通过，不能证明断言未被削弱。
- 有限 context 语法检查与六个行为探针，不等于调用链完整性证明。
- 已有 NeedsAttention 聚合，但缺少能在构建、测试都通过时稳定触发的“不确定”案例。
- oracle 仍为空；公开 cases 的预期比较不能作为独立迁移效果评测。

M2 交付新增 T3 场景、结构化检查结果、有限完整性分析、可信行为验证、审核材料和 L1 参考标准。不扩展批量调度，不增加门禁反馈驱动的第二套修复循环，不建设通用静态分析平台。

## 2. 决策依据、证据与待验证项

### 2.1 目标优先级与决策状态

本阶段按以下顺序处理目标冲突：

1. 已知违规不能因已有测试通过而被放行；执行失败与证据缺口必须可见。
2. 不把“尚未证明”误写成“已经错误”，保留人工判断所需的条款、位置和证据。
3. 在前两项成立的前提下，让声明支持范围内的正确候选可自动放行，控制人工确认负担。
4. 选择完成上述目标所需的较小实现，控制开发与运行成本。依赖少、代码行数少不是独立的优先目标。

前两项来自项目的可信性要求；第三项避免以全部 NeedsAttention 获得表面上的低错误放行率。具体支持范围和人工确认负担尚无实测数据，不能宣称当前方案已取得最佳平衡。

| 决策项 | 当前状态 | 依据或缺口 |
| --- | --- | --- |
| 新旧场景资源独立，历史输入不变 | 已确定 | v0.1.0 明确没有默认超时，已有实验引用其规范与夹具摘要 |
| 明确违规拒绝，证据不足交付 NeedsAttention | 产品契约及证据聚合已验收 | M2.2 聚合、第 19 节开发对照及第 20 节冻结 L1 独立交叉验收 |
| 有限分析与行为探针组合 | 冻结 L1 范围内已验收 | 第 14 节显示互补缺口，第 19/20 节验证组合；尚无 L2 人工确认负担统计 |
| 纯 AST 或带类型信息的分析 | 选用 AST + go/types，有限边界已实现 | 第 14 节对照及第 15 节真实 Docker 加载；完整规则集尚未验收 |
| 受限测试变换比较与独立可信测试副本 | 冻结场景结构比较、可信行为与门禁组合已验收 | 第 17/18 节分别核验结构及运行时事实，第 19 节组合，第 20 节独立交叉验收 |
| 快检查加真实 30 秒慢检查 | M2.1 已采用；M2.3 行为模块按第 18 节执行 | 快阶段通过后运行真实到期，未运行项显式记录；其他场景的频率仍需成本证据 |
| 时间窗口、观察时限及慢检查并发 | 场景及行为检查分别记录 | 第 12 节参考验收和第 18/19 节运行时联调已有实测；不据单机结果宣称其他环境稳定或参数最优 |

“已确定”表示有足够理由进入实现，不表示实现已验收；“暂定”需满足下述验证条件才落实为后续实现前提。第 3—9 节中的接口和分析范围按此状态理解。

### 2.2 为什么新建场景，而不直接修改旧夹具

要求是新增真实的超时语义，同时保留 M0/M1 的可复验输入。原规范明确声明没有隐式 30 秒超时，旧 SDK 也没有该行为；在原路径直接改行为，会使按现有说明运行的场景与历史条件不同。仅靠 Git 检出历史版本虽可复现旧代码，却使两个场景无法在当前版本下直接回归比较。

因此确定新建独立场景资源、复用执行代码。代价是两个小 SDK 与业务基线存在重复，需要分别维护摘要和版本。立即建设通用场景配置引擎虽然可以减少部分重复，但只有两个已知版本时尚不足以决定通用接口，而且配置本身不能替代对 SDK 行为的版本管理。

验证：旧资源摘要不变，旧五个 case 原样回归，新场景体现新增超时差异。改选条件：后续出现多套场景的重复维护错误，再考虑抽取生成或共享机制；无论如何仍须保存每次运行的确切输入。

### 2.3 为什么暂选组合验证，而不是只跑测试或只做静态分析

有限行为探针只能观察执行到的路径。例如 Reserve/Release 的已测路径正确，但另一个相关分支遗漏超时，已有探针可能全部通过。静态结构分析可以列出新增调用点或未支持的路径，但识别到 WithTimeout 并不能独自证明错误没有被吞掉、订单状态没有错误更新。

因此暂选分工：分析列出迁移位置和覆盖缺口，探针检查具体路径的行为。相比只跑测试，增加分析与人工关注成本；相比全程序数据流分析，接受无法证明的动态调用进入 NeedsAttention，避免以当前两个封装的需求承担通用控制流建模成本。这里没有证据证明完整分析永远不值得，只是当前需求尚不足以支持其投入。

进入 M2.3 前，用同一组正反例比较三种结果：仅探针、仅分析、二者组合。至少包含：未被原探针执行的新增调用路径、期限正确但吞错的路径、正确直接写法、语义正确的 helper 写法。分别记录错误放行、正确候选被拒绝或需关注的原因，以及执行成本；构造样例的计数不能解释为实际业务成功率。

采用条件：组合能够处理两类互补缺口，直接写法正例可放行，无法证明的正例明确记录缺口。若分析仅重复探针已有结论、不能发现额外缺口，缩减分析职责；若合理写法大量进入人工确认，重新评估支持范围与分析技术，而不是宣布组合方案已经有效。

### 2.4 为什么纯 AST 还不能确定

要解决的具体问题是识别 SDK 方法接收者、导入别名、局部变量遮蔽、常量值与 context 的来源。仅按名称匹配不满足要求；而类型信息也不能自动证明跨函数 context 传播和所有控制流。

| 备选实现 | 可能收益 | 必须承担的成本 |
| --- | --- | --- |
| AST 与有限词法作用域分析 | 对极窄语法支持可以较快实现，不必加载完整包类型 | 需要自己处理标识符绑定、接收者歧义和常量；复杂后可能重复实现类型检查器的一部分 |
| AST 加 go/types 等类型信息 | 可借助对象与类型区分同名方法、别名和遮蔽，降低一部分误识别 | 需解决离线包加载、依赖导出信息、构建配置和错误分类；不能因加载失败直接放行 |
| 在类型信息之上做 SSA/跨函数摘要 | 可能覆盖更多间接调用和数据流 | 增加加载、控制流、摘要维护及验证成本；当前尚无必须使用它的样例证据 |

选型前做有界对照原型：直接调用、导入别名、同名非 SDK Call、局部遮蔽、常量表达式、helper/函数值调用、未激活 build tag。前五类是拟支持范围，后两类至少要显式报告未知。每个原型记录识别结果、离线加载条件、自己实现的绑定/常量逻辑及失败行为，不仅比较代码行数。

选择规则：若 AST 为满足前五类而需要不断添加名称特例，或不能可靠区分同名非 SDK 调用，优先采用类型信息；若有限 AST 已满足声明范围且类型加载成本显著更大，可采用 AST 并公开范围。类型信息也不足以满足需求时，再决定缩小范围或试验数据流分析，不默认升级到 SSA。

设计此节时尚未写原型；后续对照及选择见第 14 节。M2.1 的场景建设不依赖该选型；M2.3 先完成对照，再实现正式分析器。

### 2.5 为什么保留 NeedsAttention

“全部拒绝”把合法但暂不支持的改写与明确违规混为一谈；“模型再审后放行”在当前项目中没有可校验的正确性证据。项目又明确需要业务维护者审核，因此采用 NeedsAttention 表达尚未证明的部分，保留已通过的证据。

代价是人工确认工作可能增加。验证不能只统计错误放行：必须包含正确直接写法、正确等价写法和明确违规，分别检查可放行、需关注及拒绝的原因。若连约定支持的正确写法都不能放行，则是支持范围或实现的问题，不能靠 NeedsAttention 算验收成功。后续有充分、可复验的新证据时可将对应缺口转为通过，不要求永久维持人工确认。

### 2.6 为什么暂定测试变换检查加独立可信副本

这里有两个不同问题：候选是否削弱了原测试，以及候选生产代码是否满足业务要求。运行可信测试不能证明原测试没有被删除；原测试未变也不能证明新增超时要求正确。

禁止修改测试会阻止本任务必须的 ctx 参数适配；只比较名字和通过事件会漏掉删除断言；任意测试语义等价证明超出本阶段范围。因此暂定允许小范围已知适配，其余变化如无法证明则需关注。删除某个断言并不总等于削弱：若同时替换为等价 helper，不能仅按 AST 节点消失判为违规。明确无替代地删除已识别断言可作为反例；存在替代但等价性未知时标 unknown。

可信测试有两种实际可行组织方式：直接与候选测试同包运行，或在仅含候选生产代码的副本中运行。前者能复用测试 helper、复制成本低，但候选 TestMain、init 和 helper 参与可信检查流程；后者排除这些候选测试代码，却需要宿主提供独立测试装配，且可能与正常测试编译环境不同。对当前小型 demo-orders 暂选后者，因为可信测试可自行构造 SDK/Service，依赖候选测试 helper 的收益较小。

验证后才能推广：用删除断言、合法 ctx 适配、等价 helper 重写、TestMain 提前退出、测试 init 干预以及正常候选做对照。要求可信测试不依赖候选 helper，生产文件集合与摘要准确对应，缺失预期事件不能算通过。检查带构建约束的测试文件，不能在比较时无条件忽略语义注释。若副本改变了所需生产构建语义，先修正装配或报告不支持，不发布充分验证结论。

接受的边界：生产代码本身仍参与测试进程，不保证抵御任意恶意伪造；同包可信测试也不能提供此保证。若未来需要更强的进程内对抗能力，必须另行权衡外部观察协议或威胁范围，不能用“移除了 _test.go”宣称已解决。

### 2.7 为什么 M2.1 保留快慢两种检查

本步需要同时证明期限配置与实际到期。只检查源码常量无法证明派生 context 被传入；只观察 Deadline 无法证明 Done 会在期限到达时关闭；每次都等 30 秒又会增加调试成本。因此日常快检查观察期限和传播，正式场景验收补真实到期检查。

缩短业务超时会更快，但不能独自证明固定 30 秒这个迁移要求；fake clock 有利于内部单元测试，但需要可控时钟边界，不能直接替代对候选公开行为的观察。两者以后可以作为补充，首轮端到端参考标准先用实际时间，接受慢检查耗时。

验证：缺失超时、错误期限及正确候选必须可区分；另外验证“声明合理 Deadline 但 Done 不到期”的构造参考样例确实无法通过慢检查。若快检查经常因调度产生未知，先查看测量区间和环境，不任意放宽业务语义；若慢检查成本成为瓶颈，再评估可注入时钟，同时保留真实时间集成证据。

250ms、40s、90s 与三个慢观察并发都是初始实验参数。实现时先在声明的本地/Docker 条件下按预设次数联调，保存窗口宽度、耗时、未知次数和回收结果，再决定正式配置；当前没有数据支持这些数值最优或足够稳定。

这些取舍在本文保留推进过程。形成稳定的长期技术约束后再整理 ADR；本轮不为待验证的分析技术作 Accepted 决策。

## 3. T3 契约草案：先明确迁移后的行为

新场景建议放在 `scenarios/rpcx/t3/`，包含自己的 fixtures、specs、cases、oracle；代码仍复用 scenarios/rpcx 下的 checks 和 runner。旧 `scenarios/rpcx/fixtures/`、v0.1.0 规范和五个补丁保持不变。新场景目录和正式规范在实现阶段创建，本文不是已冻结规范。

建议新规范为 v0.2.0，完整包含 T1/T2 要求并增加下列条款。规则标识先用于设计与 case 关联，正式规范发布时固定。

| 条款 | 拟定要求 |
| --- | --- |
| TIME-001 | 对每次实际发起的 RPC，补回 v1 隐式的 30 秒调用超时，不以整个订单流程的单一计时替代 |
| TIME-002 | 保留请求 context 的值、取消和更早的 deadline；有效期限为 `min(父 deadline, 本次 RPC 边界时间 + 30s)`，无父 deadline 时取后者 |
| TIME-003 | 派生超时 context 的资源在调用结束时释放；不能在 RPC 发起前提前取消，也不能复用上次已取消的 context |
| TIME-004 | 超时/取消错误保持 errors.Is 可识别；失败时不新增订单、不删除原订单，不吞掉错误伪装成功 |
| SCOPE-001 | 报告所支持的构建配置、调用路径、识别位置与未覆盖部分；必需范围的证据缺口不能自动放行 |

新 v1 SDK 仍保留无 ctx 的 Call 签名，内部为每次 Call 创建 30 秒超时 context 并 defer cancel；新 v2 沿用 Call(ctx, ...) 且不补隐式期限。两者都是内存、协作式取消夹具，handler 应观察 ctx.Done/Err；不承诺强制中止忽略 context 的任意函数。

**这里包含两个要求，而非完全复刻旧行为：**恢复 v1 的 30 秒上限，同时履行 T2 新增的请求 context 传播要求。旧 v1 无 ctx，不能声称旧版已保留父 deadline。首版不引入显式超时配置、重试默认变化或 T4/T5。

建议的可识别迁移形态是在 inventory 的 Reserve/Release 中、临近实际 Call 处 `context.WithTimeout(ctx, 30*time.Second)`，`defer cancel()`，然后传入派生 ctx。允许规范上等价的其他写法，但不在分析器支持范围内时交付 NeedsAttention；规范不强制某一段参考代码。

需覆盖的行为：无父 deadline、更短父 deadline、更长父 deadline、已取消请求、执行中取消、连续两次独立调用、返回后派生 context 释放、库存参数与订单状态。Reserve 和 Release 均需覆盖；Cancel 测试先完成订单准备，再启动目标 Release 的观察，避免初始化 RPC 污染计数。

运行时探针在 RPC 封装入口前和后端到达时记录时间，用有依据的区间核对默认 deadline，父 deadline 较短时核对原期限；不以恰好相等的 time.Now 结果作断言。区间过宽而无法区分错误超时值时，记录不充分，不放宽到“有 deadline 就通过”。默认超时是否真实到期由离线补充测试验证，不能宣称期限字段检查已证明计时器行为。

## 4. 判定契约与证据结构

宿主根据规范版本建立固定必需检查集合，覆盖已有六类检查及 timeout_behavior、migration_coverage、test_integrity。不能仅遍历候选返回的检查项作聚合；少一个必需项就不是全部通过。

检查结果建议包含：

| 字段 | 含义 |
| --- | --- |
| ID / RuleIDs | 稳定检查标识及规范条款，条款来自宿主支持的规范 |
| Status | pass、fail、unknown、blocked、skipped、not_run；unknown 表示分析完成但无法证明 |
| Applicability | applicable / not_applicable；不适用必须由宿主规则给出理由，不能由 Agent 自报 |
| Findings | 稳定原因码、说明、候选文件相对路径及行号、关联条款、证据 ID |
| EvidenceIDs | 指向本次检查的命令、探针事件、结构分析记录或差异材料 |

Evaluation 增加结构版本、验证器版本/材料摘要、构建配置、覆盖清单和结构化证据索引；继续绑定规范、基线与候选摘要。证据项记录种类、产物相对路径及摘要，命令项保留参数、退出码、后端和日志。路径必须指向本 Run 的实际材料，不接受 Agent 任意填写。报告内容只从实际检查生成。

覆盖清单记录每个已识别 RPC 位置的所属函数、来源配置、验证状态和未知原因。它不是 Agent 自填的调用点清单；从可信基线及候选分别发现并比较，不靠“两个探针都通过”推断所有调用点已覆盖。

聚合顺序：

1. 输入不可信、基线失败、取消、OOM、命令启动或产物写入失败等执行问题：返回 error，最终质量判定为空，保留已收集事实。沿用现有执行错误与质量判定分离契约。
2. 完成评估后存在明确违反条款的 fail：Rejected；同时展示其余证据缺口，不被 unknown 掩盖。
3. 无 fail，但必需范围存在 unknown、blocked、缺失检查或无正当理由的 skipped：NeedsAttention。
4. 所有适用且必需的检查有 pass 证据，未覆盖范围为空；不适用项有有效依据：ReadyForReview。

skipped 表示未执行，not_applicable 表示规则不适用，不能互相替代。构建失败会使行为探针 blocked，但已有构建 fail 足以 Rejected；无法解析不支持的 Go 结构与分析器自身崩溃也不能混成一种 unknown。

新增记录采用版本化 schema；旧 v0.1.0 回归判定保持原结果，不追溯提升旧报告可信度。新增严格检查只在新规范对应的检查集合中启用，不能给旧规范静默追加 T3 要求。首版使用明确的结构体和函数，不引入插件注册中心或可配置规则 DSL。

## 5. 有限完整性分析：支持什么，遇到什么停止证明

具体分析技术尚未确定，按第 2.4 节比较有限 AST 与带类型信息的方案；暂不建设跨仓库通用调用图或 SSA。宿主使用执行后端取得已声明配置的 Go 文件清单；分析器读取副本，不自行执行候选。默认配置外的 build tags、平台文件、cgo 或无法确认的导入关系列为覆盖缺口。分析基础设施失败返回 error。

拟支持的初始形态（需原型证明，尚非实现能力）：

- 本场景固定包边界下的 SDK 导入、构造与 `*rpcx.Client` 字段；直接的 Reserve/Release 调用及 HTTP → Service → inventory 调用链。
- 函数内直接从传入 ctx 派生 WithTimeout，常量可确认为 30 秒，紧随可达路径注册 defer cancel，派生值传入目标 Call。
- 只对完整匹配支持形态的函数给覆盖通过；发现遮蔽、重新赋值、分支别名、函数值调用、接口动态分派或未知封装时记录 unknown。不能靠变量名字相同确认 context 来源。
- 基线和候选的生产文件均扫描；新增 SDK 调用、删除封装、改变调用拓扑都进入差异清单。无法配对的变化不得因为旧路径探针通过而忽略。

结构检查只支持上述形态，不证明所有控制流。纯重构或抽取 helper 即使语义正确，也可能 NeedsAttention，这是首版接受的人工审核代价。类型信息是否用于首版需先完成对照；跨函数摘要或其他扩展只有在新增样例提出明确需求时再权衡。

完整性分析回答“哪些应迁移位置已被识别和验证、哪里还未知”；语义探针回答“被执行路径上的期限、取消、参数和状态是否正确”。二者共享位置和规则标识，不要求单独两个框架。

## 6. 测试完整性与可信验证的边界

候选业务测试保留用于反馈和构建证据，但不能独自证明质量。暂定验证副本分为候选测试副本和可信测试副本，需通过第 2.6 节对照验证：后者从同一候选生产代码生成，移除候选的 `_test.go`，仅安装宿主维护的最小 v2 适配基线测试和可信探针。两份生产代码摘要必须对应同一候选，测试材料分别绑定摘要；仍通过现有 Docker 后端执行，不共享可写状态。

这样可以避免候选 TestMain、测试 helper 或 init 直接控制可信测试流程，但不能保证候选生产代码不会识别探针或伪造输出。生产侧测试环境探测、异常退出等已知绕过模式纳入反例；超出所声明威胁模型的任意恶意 Go 代码不在首版证明范围内。可信探针必须检查预期测试事件、实际到达 RPC 的计数和关键状态，不能只看进程退出码。

测试修改检查暂定采用受限 AST 比较：忽略格式和不影响构建/执行的普通注释，保留构建约束及工具指令的检查；只允许明确列出的导入/API 替换和 context 参数适配。原测试及其既有 helper 的控制流、条件、期望值、错误断言应保留；新增测试允许。新增 TestMain、改动原 helper、改变断言表达式或添加控制原测试执行的逻辑，无法由允许变换解释时记为 unknown。明确删除原测试、跳过必需测试、无替代地删除已识别原断言等有充分证据的违规记 fail；断言被改写但无法确认是否等价时记 unknown。

比较整个原测试及 helper 的相关结构，不能只统计断言数量；不能因新测试补了相同数量断言而认定原断言保留。合理的大幅测试重构也可能需人工确认。可信适配测试另行验证原业务契约，但不能覆盖掉 TEST-001 本身的未知或违规。

### 11.2 SDK 行为与计时边界

新 v1 的最小改动为在 Call 内部创建 `context.WithTimeout(context.Background(), 30*time.Second)`，立即登记 defer cancel，调用后端并原样返回错误。保留 Register、构造函数、请求结构以及错误包装约定；新增私有常量表达默认超时，不增加环境变量、可变全局计时器或专供测试的公开参数。

新 v2 的 Call(ctx, ...) 检查预先取消，然后把 ctx 交给协作后端；不主动增加 deadline。两版都不为后端另起 goroutine，也不承诺中止不合作的处理函数。

迁移后的 30 秒计时从 inventory 每次 Reserve/Release 准备实际调用时开始，不从 HTTP 请求到达、订单构造或 Client 创建时开始。服务锁等待时间不计入这段 SDK 默认预算；父请求若已取消仍应阻止 RPC。业务中如果未来增加显式超时配置，需要新规则，不能套用本步固定 30 秒契约。

常规请求错误继续使用 `%w` 包装，服务层检查 errors.Is，HTTP 层检查既有失败状态码和订单状态，不要求从 HTTP 文本还原错误链。

### 11.4 快速参考检查：观察期限但不等待 30 秒

先检查 inventory 的两个实际 RPC 边界，再检查 service 与 HTTP 的传播和状态。入口后端记录参数、次数、ctx 及 deadline；每个断言必须有实际调用或明确的“不应调用”计数，避免 callback 没执行却显示通过。

| 条件 | 检查内容 |
| --- | --- |
| 无父 deadline | 后端观察到本次调用的 30 秒期限，而非仅存在一个任意 deadline |
| 父 deadline 为 5 秒后 | 保留这个绝对期限，不能重置为 30 秒；请求值保留 |
| 父 deadline 为 60 秒后 | 收紧为本次调用的 30 秒期限 |
| 已取消或已过期的父 context | 不进入后端；错误分别可识别为 Canceled 或 DeadlineExceeded；订单状态不提交 |
| 后端触发父取消 | 派生 context 能观察取消，错误沿调用链传递；失败的 Cancel 保留订单 |
| 调用正常返回或后端返回普通错误 | 捕获的派生 context 已被释放；父 context 仍有效，不被误取消 |
| 同一个 Client 连续两次调用 | 第一次派生 context 已取消，第二次仍可进入后端并有有效期限；不复用失效 context |

期限区间计算：记录封装调用前的 t0 和后端入口的 t1，要求观察到的期限落在 `[t0+30s, t1+30s]`；较短父期限以同一个绝对值比较。测试夹具初始允许的观察窗口宽度为 250ms，作为环境参数写入报告，不作为业务语义容差；窗口超宽则该次测量记为 inconclusive，不据此通过或误判候选。该方法不能证明区间内极小偏差，报告需保留此限制。

连续两次调用测试主要排除共享已取消 context；仅靠两次接近的期限不能证明所有请求都独立计时，后续仍需结构分析和补充反例。不得把本步行为覆盖扩大为全调用图证明。

### 11.5 实际到期：保留真实 30 秒，单独运行慢检查

权衡后不把业务规范的 30 秒缩为毫秒，也不向候选注入 fake clock；否则只证明替换后的测试模型。快速检查用于日常反馈，正式 M2.1 验收还必须跑实际到期检查，缺少它就记录尚未完成验收。

慢检查验证新 v1 的隐式超时，以及正确候选的 Reserve/Release 无父 deadline 调用。后端等待 ctx.Done 后返回 ctx.Err；捕获 deadline、实际返回时间、错误链和订单状态。每个独立观察先确认期限合理，再开始等待；已明确缺失或错误的期限由快速检查给出违规证据，不让缺失超时的反例无限阻塞。

正确候选的 Place 和 Cancel 到期场景分别使用独立 Client/Service，Cancel 先用成功后端建单，再只阻塞目标 Release。三个独立慢观察可在有界测试并发下进行，避免串行等待累计 90 秒；记录实际并发配置，避免未来共享注册地址。

初始时间预算：实际到期观察上限 40 秒，整个 Go 测试进程的测试时限 90 秒；Docker 启动和冷编译另由更宽的命令 deadline 覆盖。不能沿用旧检查的 `go test -timeout=30s`，否则合法 30 秒场景会被外层抢先终止。

观察到错误期限、错误取消类型、吞错或不当状态更新为 fail。若截止观察上限仍未获得可靠结果，输出 inconclusive 并保留记录，不认作通过；外层进程 deadline/OOM/容器故障为执行 error。后端还监听测试拥有的退出信号，超时后使协作后端返回并等待调用 goroutine 结束；若无法回收，由执行后端终止整个检查进程，不能只结束等待而留下 goroutine。

观察到返回时间晚于 deadline 可能包含调度延迟，不使用“恰好 30 秒返回”作为要求。重复检查只按预设次数运行并保存所有结果，不自动重试到通过。

### 11.6 参考标准与验收驱动的职责

oracle 测试从规范独立编写，不导入 checks 的判定或探针。场景驱动先复制基线、应用补丁、运行候选原业务测试，再创建独立参考副本：保留候选生产代码，移除候选 `_test.go`，安装参考测试。保存原候选全树摘要、生产文件摘要与参考测试材料摘要，参考注入不回写候选目录。

oracle 是开发可审查的 L1 标准，不是隐藏留出集，也不提供未来真实任务的通用正确性证明。之后运行时 timeout 探针另行实现，不能直接复制 oracle 文本后声称二者独立；另写代码也不自动保证独立，需要不同输入与反例，并核对两者是否共享相同盲区。现阶段可共享执行基础设施和规范事实，不共享判定逻辑或期望结果。

阶段输出先采用小型场景报告：代码版本、Go/镜像信息、输入/规范/补丁/参考材料摘要，每个阶段的命令和日志、业务测试事件、参考检查 pass/fail/inconclusive、关联条款、预期匹配结果及执行错误。报告不包含最终运行时 quality verdict。

驱动先执行实际检查再读取 expected 比较。预期反例确实失败且正确候选通过，整套场景验收可以成功；但 inconclusive、执行错误、必需测试未运行或预期不匹配均使本次验收不通过。候选被拒绝与测试程序出故障不可共用一个“预期失败”分支。

## 13. M2.2：证据与聚合的具体选择

- 状态：已验收（2026-10-18）；限聚合机制、旧验证器实际证据与 Runner 联调。

### 方案比较与当前选择

将所有字段继续加在 rpcx/checks 中，改动集中，但后续 Runtime 复用聚合时容易依赖 SDK 场景。立即建立规则注册、DSL 或插件接口可扩展更多策略，却没有第二套实际生产者证明需要这些机制。采用折中方案：internal/quality 仅提供数据结构与普通聚合函数；场景宿主提供固定 Policy、执行检查和收集材料。接受一个小包及适配代码的成本，避免两套独立判定算法并存。

本轮改造旧 Evaluate 为结构化证据的实际生产者，保留其检查行为；T3 的三个新增检查尚未实现，不从 oracle 的通过结果伪造 runtime pass，也不提前接受 v0.2.0。旧规范已声明测试断言及行为覆盖限制，新增结构不会追溯增强它的语义保证。

每个检查保留可读 detail，并增加关联条款、适用性、Finding 和证据 ID；日志、输入快照、测试清单及 context 语法结果成为证据材料。证据索引记录相对路径、SHA-256 和规范/基线/候选绑定。Findings 可以带代码位置；命令级结果不编造行号，完整调用覆盖清单留到 M2.3。

聚合遍历宿主 Policy 的固定必需集合，不从实际返回项反推要求。pass/fail 需要有效材料及条款关联；unknown/blocked/not_run/skipped 保留缺口。宿主可明确声明允许不适用的检查，但仍须说明理由和证据；当前 rpcx 六项均必需且适用。

缺少必需检查、证据引用或判定说明，属于证据不足，交付 NeedsAttention；已有充分违规证据时仍 Rejected，并保留其余缺口。证据记录绑定错误候选、实际文件摘要不符、重复 ID、规则/状态非法或路径越界属于宿主记录不可信/契约错误，返回 error 和空 verdict，而不是把坏记录解释成候选违规。

代价是增加证据落盘及哈希读取；收益是能复核“这个 pass 依据哪份材料”。哈希只证明文件绑定与完整性，不证明生产者的业务判断一定正确，也不抵御任意宿主篡改。若未来证据数量或远程存储确实造成瓶颈，再评估流式或存储接口；本轮采用本地相对路径，不引入抽象存储层。

### 比较方式与选择依据

## 15. M2.3：隔离类型加载与有限边界分析

- 日期：2026-10-18。

- 实现：[analysis 包](../../scenarios/rpcx/analysis/README.md)，入口为 Inspect；长期执行边界见 [ADR-004](../adr/004-analysis-execution-boundary.md)。

### 要解决的问题与方案取舍

上轮原型直接读取宿主 Go 缓存中的导出文件，无法原样用于一次性 Linux 容器。优先保证包选择、编译与类型查询来自相同构建环境，再考虑加载耗时；宿主与容器可能使用不同平台，路径和缓存不能假设一致。

| 方案 | 具体收益 | 当前约束下的代价与问题 |
| --- | --- | --- |
| 搬回导出文件，在宿主查询 | 可以保留宿主查询原型 | 新增有界材料传输、路径映射、工具链/格式核对；现有后端没有缓存导出能力 |
| 在宿主重新加载目标 | 减少容器侧程序 | 需重建目标平台与依赖环境，宿主默认配置不能代表容器实际选择的源码 |
| 同一后端命令内加载并查询 | 导出数据与消费工具链一致，沿用一次性回收 | 编译可信程序与依赖增加冷启动开销，需要跨进程协议与宿主校验 |

选择第三种：宿主嵌入两份可信 Go 源码，在单独只读根部署；执行后端内运行程序，程序调用 go list 并使用其导出数据完成 go/types 查询。只把配置、源码摘要、位置和规则事实带回宿主。保持现有 Executor，不增加缓存搬运、可写挂载或新的执行接口。

当前固定 SDK 与普通离线包已能用 Go 元数据加载。暂不引入其他包加载库；这不代表 stdlib 方案足以支持所有仓库。遇到 vendor、overlay 或复杂依赖需求，再按样例比较加载方式；执行位置可以保持不变。冷编译成本以后以实际数据决定是否优化，不能先引入长期缓存而改变隔离语义。

### 实际能力与契约

Inspect 接受业务模块、显式 SDK 根、空证据目录、tag 和执行后端。整个输入树与两份程序源码分别绑定摘要；宿主与程序均核对输入不变。实际命令、后端镜像、容器 ID、配置、原始输出和逐文件摘要保存为材料。协议缺项、越界路径、错摘要、无 Gap 的 unknown 或伪造覆盖事实均不能成为可用结果。

基线 v1 与候选 v2 都发现真实方法位置，提供包路径、相对文件、行号及函数身份。有限规则只支持整个函数匹配的直接形态：context 参数派生 WithTimeout、常量 30 秒、对应 defer cancel、派生对象传入 Call，结尾直接返回或使用夹具的错误分支。支持导入/类型别名、跨文件字段和常量表达式；helper、方法值、接口、未经证明的父 context、参数调用副作用及控制流保留 unknown。明确的错误超时常量记录 violation 及实际数值。

covered 只代表这个 SDK 边界匹配声明的结构关系，不代表已证明 HTTP/service 全链路或 TIME-004 等业务规则。当前没有最终 quality verdict，也没有接入旧 Evaluate。完整基线/候选位置差异比较、可信运行时探针和测试完整性检查仍待后续；不把本工作单元标成整个完整性检查已完成。

活跃文件必须绑定实际输入摘要；未激活文件记 inactive_build_file。逐文件补扫处理 go list ./... 完全不列出的目录，记 unlisted_build_file。宿主再次要求每个生产 Go 文件被活跃包或缺口解释，不能默默遗漏；这不是证明所有其他配置都已执行。

加载普通非零退出记 load_failed、实际退出码与诊断，包和调用结论为空。加载失败可能来自候选、依赖或环境，后续须结合独立构建和后端信息分类；不能直接据此 Rejected。取消、OOM、启动及协议错误通过 error 返回。输入在程序结束后变化时清空可用结果，撤回已发布 analysis.json，保留 stdout/stderr 等原始证据。

### 目标、缺口与方案取舍

本步首先要求各检查消费同一输入，充分违规优先拒绝，未证明范围不能被其他检查通过覆盖；其次保留旧规范的语义；最后控制副本、命令和真实到期的成本。

接入时确认：analysis 能识别 RPC 封装中的有限超时形态，却没有证明任意 handler/service 改写的传播关系。仅组合已有三个模块，就可能让未被探针触发的调用链变化进入 ReadyForReview。因此增加单独 request_scope，明确自动审核边界。

### 实现与判定契约

T3 精确绑定 v0.2.0，要求显式后端，并认证完整业务基线及两个 SDK 的冻结文件集合。两套输入布局与输出/缓存不得重叠，输入拒绝非普通文件和超限。基线先实际运行原十个测试，未成功执行属于验证错误，不给候选 verdict。候选 SDK 修改为 DEP-001 fail；执行副本使用基线侧可信 SDK。

八项必需检查为 dependencies、protected_paths、build、candidate_tests、test_structure、request_scope、migration_analysis、trusted_behavior。候选测试的必需事件独立核验：显式 skip/fail 为违规，缺失/重复/异常入口退出为未知，新增测试失败也拒绝。结构检查另外判断原断言保留，可信副本另行检查行为；三者不能互相替代。

request_scope 比较完整生产结构与受限适配后的基线。两处 RPC 函数体由类型分析及行为检查验证，函数签名、构造、其他声明、调用方逻辑和新增文件仍需解释。位置、格式、普通注释忽略，语义指令不消除；生成代码交给 PATH-001，go.mod 交给 DEP-001。超出支持范围只记 unknown，不把合法重构直接当作违规。

依赖或生产构建失败阻断下游检查；有其他充分违规后保留已有检查，停止可信行为。未执行项记录 blocked 并引用前提材料。未知仍继续行为检查，因此可以得到“行为通过，但测试重写或传播范围不明”的 NeedsAttention。每项都有条款、解释和实际材料引用；分析中未知配置与位置差异不会因另有 fail 消失。

三个生产者的摘要与主判定对齐：结构报告核对原/候选完整测试集合；Inspect 的 input_sha256 对应副本业务加两个 SDK；behavior 的基线、候选、SDK 及适配测试对应本次输入。来源记录、原始日志、工具材料及实际副本均关联本次 Spec/Baseline/Candidate Binding。返回前再次核验原输入和执行副本，有变化则撤销 Verdict。后端、取消、资源、写入、协议或绑定错误均返回 error，不包装成质量结果。

材料目录保存门禁及复用代码摘要，三个生产者也各自保留材料摘要。证据根增加独立 go.mod，避免落盘工具源码加入项目根模块扫描。Evaluate 继续不创建 Run、不自动保存最终 Evaluation；调用方负责保存，本轮联调用 evaluation.json 持久化。Runner 仍选旧场景，新场景选择在 M2.4 实现。

## 23. 真实实验后的支持边界评审与测试导入扩展

- 日期：2026-10-19；设计先于实现，验证结果在本节末补录。
- 目标优先级：已知错误不能放行；能够解释每项支持条件；减少可证明无关的人工确认；控制分析器维护成本。
- 当前代码基于 dc5227b（模块路径已改为 github.com/secacy/agent-harness）。实验 04 的候选及判定作为历史记录保留。

### 为什么拆成两个问题

公共 call helper 把 Reserve/Release 中两个物理 RPC 位置合成一个，operation 从常量变成参数。支持它需要证明每个入口到 helper 的对应、参数替换、父 context 的来源、每次调用的新期限及取消、错误传播；还需让 request_scope 认可被证明的新增声明。仅消除 call_added/call_removed，或因行为探针通过而忽略 unknown，会丢掉原有完整性保证。

测试新增导入则可以限定为不改变原声明绑定的局部语法变化。当前原声明 AST 未变，但文件导入集合不同就转 unknown，未区分增加常用测试工具包与改写原导入。这一问题能在现有比较器内修正，不依赖跨函数分析。

| 问题与方案 | 收益 | 代价及风险 | 本步选择 |
| --- | --- | --- | --- |
| 保留所有导入变化为 unknown | 实现最简单，维持现有边界 | 普通新增测试需要 time/errors 也增加人工确认 | 不选；可给出更小的充分条件 |
| 允许任意新增导入或所有标准库 | 覆盖面广 | 标准库也可能有初始化副作用；别名、点导入可能改变原绑定 | 不选；“属于标准库”不构成充分依据 |
| 有限包清单＋原导入完整保留＋原声明名称检查 | 可解释、无需重新加载候选包，范围小 | 清单需维护；保守名称扫描可能拒绝其实安全的局部同名 | 采用；只支持 errors/time 的默认名称导入，显式别名、点/空白导入和其他包仍 unknown |
| helper 只靠探针通过或函数名模板认可 | 实现快、可让当前样本减少 unknown | 漏掉动态分派、参数错配或未触发路径；针对单个样本放宽 | 不选 |
| 有限一层 helper 的类型摘要与调用展开 | 有望覆盖当前形态，边界可以明确 | 同时改变位置配对、语义检查和生产范围三个证据环节；需专门正反例 | 作为后续候选方案，本步不实现 |
| 直接引入 SSA/通用跨过程分析 | 将来覆盖更多封装 | 显著增加依赖、模型和维护成本，仍不能证明任意业务等价 | 当前只有一个开发观察，收益证据不足，暂不采用 |

errors/time 清单只表达本场景接受这些测试辅助包，不宣称它们的任意调用都安全。冻结 SDK 使用 context，当前工具链的 context 已间接依赖 errors/time；可信执行环境提供标准库，候选不能替换它们。原声明保持结构比较，新增测试的共享状态/顺序影响仍是既有边界，原测试事件和可信生产副本继续独立检查。

### 阶段验收与实验成功分别判断

第 9 节预先规定了四个工作单元的完成条件，并要求按固定协议进行一次真实实验、记录全部结果；没有要求该次实验必须自动成功。里程碑的五项条件检验正例可放行、违规可拒绝、缺口不放行及证据可追溯。实验 04 则另有更严格的自动交付成功判据，原 Run 必须 ReadyForReview。

对公共 helper，审核人仍需从两条业务入口核对实际调用关系及参数，确认传入请求 context、每次 RPC 独立派生 30 秒期限并释放、错误不被吞掉、业务状态更新顺序保持。行为探针和独立参考是这些路径的辅助证据，不能代替未覆盖分支的检查。原审核报告记录的 unknown 与人工意见分别保留，不手工把原 verdict 改为 ReadyForReview。

实验 04 的新增取消测试有潜在调度问题，部分回调断言未证明回调必达，另有格式提示。原补丁保持原样；以后若修复，应产生新候选并重新验证，不能沿用旧摘要和结果。本次未记录审核开始/结束时间，因此审核耗时未知，不能事后估算节省了多少人工。

### 下一工作单元：M3 具体设计

先设计接口、预算和数据边界，再实现批量调度。进入 M3 不代表已有多仓库能力。

1. 明确 Campaign → Target → Run 的输入和结果契约；把通用执行管理与 rpcx 的基线装配、质量策略区分，不能把 demo-orders 的摘要/路径规则直接用于其他仓库并称为验证充分。
2. 在创建 3—5 个异构 L2 仓库时按同源分组划分开发/留出样本；开发只消费开发子集。每个仓库先有基线及可放行正例和应拒绝/未知对照，避免用“全是 NeedsAttention”完成批量验收。
3. 权衡付费调用的额度单位、输入/输出上界、调用前原子预留和未知用量结算，再启用并发。无法证明严格上界的估算不能称为费用硬上限。
4. 固定候选先验证并发与故障隔离，明确杀的是执行子进程、worker 还是整个 Harness；批次预算耗尽的预期影响另测。进程恢复与通用离线审计仍归 M4。
5. 在开发子集实验前固定指标和审核记录方式：同时报告样本数、放行/拒绝/关注、独立参考、未知原因、调用成本及实际人工审核时间；零放行时错误放行率标不可计算，不填 0%。

如果约定支持的正例不能放行、已知错误被放行，或不同开发仓库反复因同类 helper 缺口无法形成有效交付，暂停扩大批次，回到有限摘要方案与正反例对照；不在留出集上调分析器。不设缺少业务依据的人工成本阈值：先采集开发数据，再在正式协议中固定判据。
