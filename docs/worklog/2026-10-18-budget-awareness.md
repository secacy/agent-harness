# 预算感知与及时提交

- 日期：2026-10-18
- 状态：机制与本地联调已验收；40 次上限的真实对照实验完成一次合格交付
- 对应里程碑：[M1](../MILESTONES.md)
- 当前结论：预算通知与收尾提示已实现，机制及根模块回归通过；20 次上限的实验 02 失败，40 次上限的实验 03 使用 31 次调用完成修复、提交和独立验收。该单次对照不证明软提醒有效或 40 为最优预算。

## 问题与目标

[实验 01](../experiments/2026-10-17-rpcx-real-model-01.md) 在第 17 次模型调用已有构建、测试通过的候选，后续继续补充测试，在 20 次模型调用预算内没有正常提交。循环执行了硬限制，却没有告知模型剩余调用次数。事后门禁通过不能替代原 Run 缺失的提交。

本步目标是让模型获得准确预算并据此安排工作，明确迁移候选的提交方式，保留完整通知记录。验收首先检验通知、计数、消息顺序和退出边界；真实模型是否更能及时提交，需要新实验检验。

本次只涉及模型与工具调用次数。整体 deadline 仍由 context 执行，单次输出 Token 上限仍由适配器配置；不增加总 Token 预算、重试、自动收尾或门禁拒绝后的修复流程。

## 方案与取舍

关注预算内交付、补丁质量、执行成本和行为可审查性。这些目标存在冲突：催促结束可能降低验证充分性，扩大预算可能提高成本，强制收尾可能阻断必要修复。

| 方案 | 收益 | 代价与选择 |
| --- | --- | --- |
| 增大调用预算 | 为探索、修复和验证留出更多空间 | 费用可能增加，仍缺少预算信息；留作单独对照条件 |
| 告知预算并提示收尾 | 模型可自主安排工作，沿用既有执行与提交规则 | 有消息开销且不能保证遵守；本步采用 |
| 强制预留最后一轮总结 | 限制最后一轮继续改动 | 可能阻断必要修复，需要额外控制工具协议；暂不采用 |
| 超限后自动冻结并验证 | 可回收没有正常提交的候选 | 需要明确超限回收与自主提交的状态、指标；另行设计 |

采用每轮简短通知，接受少量上下文开销，换取持续准确的信息和直接的审计记录。只在临近上限通知开销较低，但模型前期缺少规划依据。通知追加为现有 user 消息，不修改原任务或工具结果；相比覆盖一条动态消息，追加能保留每次请求所见预算。通知只有在整批工具结果完整后才追加，不打断工具调用与结果的配对。

剩余模型调用不超过 3 次时给予软提醒；这个阈值是待验证的初始策略，用命名常量表达，暂不增加配置项。通用循环提供预算与一般收尾提示，rpcx Runner 提供迁移、验证和候选提交要求；不引入策略接口或新的模型接口。本次是既定循环中的行为改进，取舍记录在本 worklog，暂不单独编写 ADR。

## 行为与实现顺序

1. 在每次调用模型前检查取消和硬预算，再根据本次已使用计数生成通知。模型剩余次数包含即将发起的本次调用；历史调用不计入新运行预算。
2. 通知包括当前运行的剩余模型、工具调用次数。剩余 2–3 次模型调用时建议优先必要修复、验证和总结；剩余 1 次时明确这是最后一次响应，执行工具后没有后续模型调用。工具额度为 0 时明确只能总结。
3. 通知作为 `RoleUser` 追加到 `Result.Messages`，然后增加模型尝试计数并发起请求；请求失败仍保留实际发送的通知。模型和工具计数不包含通知本身。
4. 原有硬限制继续生效：最后一次回复可正常结束，也可执行预算内工具；后者执行完仍未结束时返回 `limit_reached`。超额工具批次整批拒绝，不通过提醒自动续轮或转为成功。
5. Runner 提示要求完成规范内的必要改动，修改后运行相关检查，检查后再修改应重新验证受影响内容；预算紧张时减少非必要扩展。如实总结实际检查和遗留问题，无工具调用的最终回复提交当前候选。候选仍由独立门禁判定，不要求模型虚报成功才能结束。

## 验收计划

| 完成条件 | 验证方式 |
| --- | --- |
| 首轮、普通轮、临界轮及最后一轮预算准确，包含本次调用 | 循环模型替身检查每次输入；覆盖已有历史和未知工具尝试 |
| 通知不打断工具配对，旧通知保持原值 | 多调用批次后检查消息次序，并校验保存的完整历史 |
| 最后一轮结束、继续工具及整批超额行为符合原契约 | 原有预算边界测试回归 |
| 工具额度为零时仍可正常结束 | 循环替身验证通知与执行次数 |
| 错误、取消与截断仍保留通知和已有证据 | 原有异常测试回归及失败请求记录检查 |
| 通知实际进入 HTTP 请求，错误和工具反馈仍可用 | 本地模拟 DeepSeek API 与真实文件工具联调 |
| Runner 保存通知，最终判定不由提醒替代 | 串行迁移交付与未迁移候选被拒绝的集成测试 |

先运行相关包测试，再运行根模块回归；如出现执行后端问题，再针对问题验证。此阶段不需要修改冻结规范、场景夹具或公开补丁。

## 实际实施与验证

**实际改动：**

- `internal/agent/loop.go` 在每次模型请求前追加预算通知；`wrapUpModelCalls = 3` 表示软提醒阈值，独立辅助函数只生成消息。现有 `Model`、`Limits` 和退出原因无需扩展。
- `scenarios/rpcx/runner/run.go` 补充修改后验证、预算紧张时优先必要工作，以及最终回复提交候选的约定。该提示不会强制模型停止，也不替代独立门禁。
- 更新已有消息顺序断言和可执行示例，明确最新消息是预算通知，前面才是完整工具结果。
- 新增五轮预算测试：包含已有历史、同轮多个工具、未知工具尝试和工具额度归零，检查每次通知与保存记录一致。原有最后一轮提交、最后一轮执行工具、超额批次、取消、异常及截断测试继续通过。
- 模拟 DeepSeek API 检查每个 HTTP 请求的通知及工具反馈；Runner 使用三次模型调用预算，在最后一次提交，确认保存三条通知、独立门禁通过、补丁可还原；同一测试也确认未迁移候选提交后仍被拒绝。

本次未改变设计中的硬限制、规范和门禁。没有因通知而增加调用额度，也没有自动把超限候选计为完成。

## 真实模型实验与后续

新建实验 02，保持实验 01 的模型、基线、规范、Docker 配置及 20 次模型 / 80 次工具调用预算，单独引入本次通知和任务收尾提示。保留原失败记录，记录是否预算内提交、最终改动后是否验证、门禁结果、调用次数和 Token 用量。

上述计划已执行一次。20 条通知逐次核对正确，剩余 3、2、1 次时提示均在，但模型仍在第 18–19 轮新增测试，第 20 轮检查失败，随后无法修复或提交。原有 10 个测试和可信 context 探针通过，新增测试自身初始化有误；原样候选事后诊断为 Rejected。未修改候选或增加预算重试，M1 继续保持部分实现。

下一步应重新权衡预算安排：增加预算、强制预留总结机会与减少重复探索分别影响成本、候选质量和自主执行行为，需要先明确目标后单独检验，不能从本次失败直接认定某个改动必然有效。

本次组合改动同时包含数字通知与收尾提示，复测只能观察组合行为，不能分别归因。真实服务未固定模型快照，也存在生成波动，单次成功不能证明总体成功率提高或该方案最优。

## 下一步设计：模型调用预算对照

实验 01 和 02 都在第 17 轮完成一次测试，剩余轮次用于新增测试，最终未提交。实验 02 最后一次测试已返回可修复错误，但没有下一轮消费反馈。现有证据支持检查预算是否过紧，尚不足以决定增加复杂的执行阶段或强制提交机制。

本步优先目标是检验现有 Harness 能否在明确上限内完成一次质量合格的单仓库交付，并记录相应成本。20 次是当前配置，并非项目要求必须满足的固定成本指标；最终默认预算仍需更多任务与成本证据支持。

| 可行方案 | 收益 | 代价与本步选择 |
| --- | --- | --- |
| 仅提高模型调用上限 | 直接给修复、复查和提交更多机会；现有命令已支持 | 调用成本可能上升，也可能继续扩展范围；优先用于诊断预算是否过紧 |
| 强制预留最后一轮总结 | 为正常结束保留响应机会 | 可能阻断必要修复；获得提交仍可能被门禁拒绝，需要改变工具调用控制；暂缓 |
| 超限后自动冻结并验证 | 可以交付已有补丁和质量证据 | 改变候选交接及任务完成口径，无法解决实验 02 的错误测试；另行设计 |
| 更早提醒收尾或提供更完整的初始文件清单 | 可能减少后期扩展或重复探索 | 改变提示策略或初始信息，影响轨迹且效果不确定；作为后续独立条件 |

选择一次 40 次模型调用的对照运行。40 是粗粒度诊断点，为额外修复和验证留出明显空间，不表示最优预算。无需修改循环、模型适配器或新增策略接口；执行时使用现有 `--max-model-calls` 参数。此次选择是实验安排，记录在 worklog；尚未形成需要长期固定的预算策略，不新增 ADR。

### 当前进度

上述设计已执行一次，见[正式实验记录](../experiments/2026-10-18-rpcx-real-model-03.md)。实际使用 31 次模型调用、54 次工具调用，耗时 126.809 秒。第 20 轮新增测试失败，模型随后修复错误的 deadline 假设，第 27 和 30 轮检查通过，第 31 轮正常提交；原 Run 的六项门禁均通过，20 个业务测试通过，补丁摘要与还原一致。

本次保留候选的一项 gofmt 格式提示；部分单项测试的回调断言需结合原有调用检查与可信探针理解，未将其单独视为完整覆盖证明。没有人工修改原候选或掩盖前两次失败。

总 Token 为 342697，高于实验 02 的 146531。额外轮次在这次轨迹中确实用于处理测试失败，但轨迹起点已知预算不同，不能作严格因果归因；提交时剩余 10 次，未触发临界收尾提示。M1 最小闭环完成一次真实验收，40 仅为实验配置，默认上限仍为 20，成本优化与重复性继续留待验证。本次没有改变运行代码，设计与实际结果一并提交。
