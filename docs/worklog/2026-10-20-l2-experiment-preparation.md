## 目标与本次取舍

已有批次入口、三个开发 Target、独立参考及轮次汇总。本次准备模型能力材料、真实预算审查和运行清单，使一次尝试的开发实验可以在生成前审查。三个开发任务继续使用 goddd、translation、workouts；早期设计中的长任务名仅为描述，正式纳入以实际配置 ID 为准。

现有 batch 查询能力后会直接继续生成，无法先审查真实容量。直接运行整个批次会把能力摸底和正式实验混在一起；临时 HTTP 脚本可完成查询，但容易绕过既有端点、字段、重定向及脱敏限制；新增独立供应商命令又会重复参数组装。因此增加 `harness batch --config ... --probe-model`，复用同一配置和 Discover。接受探测也需要配置有效 Target 的小成本，避免新增另一套供应商入口。

探测只执行一次应用层 Models 查询，不执行构建、Agent 或生成 POST，不创建 Campaign/Run/预算账本。使用配置中的新输出目录，独占保存 `models.json`、`capabilities.json` 与规范化配置；材料保存失败保留目录，不复用。`--probe-model` 与完全离线的 `--check` 互斥。探测不要求 Token 额度已能预留 Q，便于先获知真实 C 再审查预算；实际 batch 仍严格检查两级额度。

能力查询仍使用终端环境凭证，命令不自动读取 `.env`。准备了一次只读 Models 查询：受控启动脚本只提取 `.env` 的凭证和模型字段，将凭证交给子进程用于既定 DeepSeek 端点鉴权，35 秒内停止且不重试；不发送仓库、规范或对话。首次启动被自动审批拒绝，理由是已有授权仅限此前 T3 实验，未覆盖本次新查询，进程未创建。随后用户明确回复“授权这一次能力查询”，在相同约束下完成唯一一次实际查询，结果见下文。过去单次 T3 实验或此次 GET 的授权均不扩展为新的 L2 付费批次，生成须在完整实验条件确定后单独确认。

## 待审查的实验参数

沿用已有模板的起点，不宣称最优：三任务各一次、并发 2、执行槽位 2；每任务 40 次模型尝试、80 次工具、10 分钟；输出 O=4096。次数依据是已有 M1/T3 的 40 次调用实验经验，跨场景是否足够仍待本轮观察，不因某任务失败追加尝试。

Token 暂议每任务 2,500,000，全批 6,000,000；不是实际消费预测或金额上限。每次保守预留 Q=C+4096，必须根据真实能力确认每任务能预留一次，全批至少允许两个并发预留。已知消耗加 Q 超过剩余额度时会提前拒绝，即便尚有调用次数；未知用量保留整笔 Q。共享池不承诺公平分配，任务耗尽额度仍进入 N=3 的失败统计。

这些参数在能力查询与环境准入完成前均为准备方案，不是已冻结协议。本次不查询余额、不估计货币账单、不自动调用收费生成接口。
