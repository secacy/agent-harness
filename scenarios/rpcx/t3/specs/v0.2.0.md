# rpcx v1 → v2：T1/T2/T3 迁移规范

- 版本：v0.2.0
- 场景：本目录的独立 T3 夹具；不适用于旧 v0.1.0 SDK 副本。
- 冻结：首次正式验收前将本规范及场景材料摘要写入 freeze.json；引用后不原地修改，语义变更另发版本。

## API、context 与保护要求

| 条款 | 要求 |
| --- | --- |
| DEP-001 | 导入 example.com/rpcx/v2，依赖 v2.0.0，replace 指向 ../rpcx-v2；移除 v1，不新增依赖或修改 SDK。 |
| API-001 | NewClient(addr) 改为 Dial(addr)，构造返回值约定不变。 |
| CTX-001 | Call 增加 ctx 首参数；当前函数无 ctx 时增加参数并更新调用方，直到已有 ctx 的位置。 |
| CTX-002 | HTTP 请求从 r.Context() 取值，沿 service 和 inventory 向下传递；允许派生。 |
| CTX-003 | 保留请求值、取消及更早的 deadline；请求生产链路不得用 Background、TODO、WithoutCancel 断开传播。 |
| TEST-001 | 原包路径＋测试名、原断言与业务要求保留，实际执行通过且不跳过；允许 API/context 适配与新增测试。 |
| PATH-001 | internal/pb/ 的文件清单及内容不得变化，包括增删改名。 |
| BEHAVIOR-001 | 保留 RPC 方法、SKU、数量、错误传播与订单更新规则；RPC 失败不得新增订单或删除已有订单。 |

## 超时契约

| 条款 | 要求 |
| --- | --- |
| TIME-001 | 每次实际 RPC 补回 30 秒上限，从 inventory 准备该次调用时计时；不以 Client 构造或整个订单流程计时替代，不跨次复用超时 context。 |
| TIME-002 | 有效期限是父 deadline 与本次调用开始后 30 秒的较早者；无父期限则为后者。保留父 context 的值和取消；已取消或过期请求不进入后端。 |
| TIME-003 | 调用返回后释放派生 context 的资源；不能提前取消、误取消父 context 或复用上次失效的 context。 |
| TIME-004 | context.Canceled、context.DeadlineExceeded 可通过 errors.Is 沿 inventory/service 识别；RPC 错误不得吞掉，订单状态遵守 BEHAVIOR-001。HTTP 使用既有错误状态码，不要求错误文本可反序列化。 |
| SCOPE-001 | 检查材料说明构建配置、调用路径、已检查行为及缺口；未覆盖范围不能宣称充分验证。 |

## SDK 与业务边界

v1 Call(method, Request) 内部从 Background 派生 30 秒期限并在返回时 cancel。v2 Call(ctx, method, Request) 不补隐式期限，预先取消时直接返回 ctx.Err，否则将 ctx 传给后端。Register 为测试注册内存后端，不做真实网络调用。

两版后端均为协作式取消：等待 ctx.Done 后返回 ctx.Err。SDK 不强制中止不响应 context 的函数。迁移同时恢复旧 30 秒上限和满足新增请求 context 传播要求；不声称旧 v1 已传播父 context。锁等待不计入默认 RPC 超时，但父请求取消仍有效。

规范约束行为，不强制参考代码写法；有限分析器无法证明的等价改写应保留证据缺口。首版不含显式超时配置、重试、类型化错误或接口拆分。

## 本阶段验收边界

M2.1 以四个手工候选和独立参考检查验证场景：原 10 个业务测试不覆盖默认超时；仅做 T1/T2 的候选应仍通过这些测试，但违反 TIME-001。期限字段、父取消、资源释放、参数及订单状态由快速参考检查观察；真实默认到期由独立慢检查观察。

参考检查只覆盖本场景的列明行为，不证明任意业务等价性，不输出 ReadyForReview 等运行时质量判定。时序测量无法区分观察区间内的微小期限偏差；环境原因导致观测不充分须标记 inconclusive，不能当作通过。
